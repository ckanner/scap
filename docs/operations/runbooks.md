# 运维手册

> 状态：当前 `scap-server` 的运行步骤与后续平台运维合同并列。已有三节点 daemon、显式 Initialize/OpenExisting、SQL/Node SDK、结果查询、leader owner 恢复和有界 S3 冷生命周期；本轮受控 Join/成员替换的验收状态见 [ADR-0016](../adr/0016-durable-membership-replacement.md)。通用控制台、自动坏盘运维、PITR/DR 和 GC 仍为 planned。实际故障记录见 [服务实验](../../experiments/service-network/README.md)与 [成员实验](../../experiments/membership-network/README.md)。

## 1. 使用规则

先根据 [故障矩阵](failure-matrix.md) 判定故障范围，再选择手册。先保全已确认事务和证据，再恢复服务。短时不可用可以接受；伪造成功、让旧 writer 继续写、删除无法证明可回收的日志不可接受。

涉及数据库的每次操作必须绑定 `tenant_id`、逻辑数据库 ID、当前 incarnation、cell ID 和期望 epoch。涉及节点的操作必须绑定节点持久身份与故障域，不能只依赖临时 IP。操作发起时与生效时都应核验预期值；值已变化则停止并重新评估。

### 1.1 当前能力与计划运维合同

当前可运行命令、完整配置和证书要求见 [服务工程说明](../engineering/sqlite-service.md)及 [server README](../../crates/scap-server/README.md)。下表区分自动流程、已公开接口与尚无工具的目标；不能因为 cell 内已有命令就假定存在同名外部管理 API。

2026-11-04 的按库执行、增量磁盘块和 peer 连接复用边界见 [ADR-0015](../adr/0015-incremental-blocks-and-isolated-execution.md)。下表中的 SQL 调度采用按需创建的每库串行 lane；目录检查、cell 与宿主资源仍共享。

| 能力 | 当前状态 | 完成条件与边界 |
| --- | --- | --- |
| live/ready 与数据库 status | 已实现 | status 经 READ/ReadIndex 返回有限元数据；ready 只是节点选择提示，没有公开全量 Raft/owner 管理查询 |
| 请求结果查询/取消 | 已实现 SDK lookup/resolveOrCancel | 当前权限与原 statements/request ID 校验；unknown 不等于未提交，取消不撤销已提交事务 |
| 进程关闭 | 已实现 SIGTERM/Ctrl-C 的停止准入、取消和 join | 关键线程异常退出使节点整体停止；没有通用按库排空管理接口 |
| owner 栅栏与接管 | 已实现同 cell leader 自动恢复 | Claim、新视图、新目录、Activate 与最终校验；手工迁移/跨 cell 调度 planned |
| 授权撤销 | cell AuthFence 已实现，外部管理 API planned | 静态旧 auth_epoch 不能绕过当前策略；改 JSON 不等于完成复制授权变更 |
| SQL 准入 / 执行隔离 | 已实现按库 lane 与双层额度 | 最多 32 个活动/退出中 lane；全局 32 请求 / 8 MiB、每库 8 请求 / 2 MiB，排队和执行共同计量；无加权公平保证 |
| 冷唤醒 | 已实现请求驱动 | 本库 lane 先复核调用者，精确 hydrate 后 Claim/Activate；status/lookup 不唤醒 |
| Suspend / 释放 worker | 已实现 idle 维护 | owner/head 匹配且 Suspend 已接受才释放；不等待 S3，writer 关闭且队列为空后 lane 退出 |
| Cold / 物理历史卸载 | 已实现有界 Publish/Prune | 保留 receipt/result/fence；共享日志另经全 cell Checkpoint，所有对象不删除 |
| 归档检查 / 重试 | 已实现精确对象校验与后台有限退避 | status 可见冷状态/归档 revision；没有通用任务查询或人工重传 API |
| 副本加入 / 成员替换 | 已有受控 CLI 和独立 loopback 管理 API | 新 ID/新目录 Join，完整 genesis 核对、learner 追赶、joint 替换；精确持久完成才成功；自动坏盘发现和采购未实现 |
| DR checkpoint / S3-only 恢复 | planned | 完整身份、应用位置、来源和引用闭包可独立验证；单库归档不足 |
| GC、PITR、删除、按库历史切换 | planned | 必须先完成保留/pin、tombstone、新身份与恢复证明 |
| 滚动升级和能力协商 | planned | v2 写入后不支持旧 binary 降级，当前无混版本协商 |

后续通用管理任务必须幂等、可查询、可中止到安全边界，并记录状态转换。当前后台队列只是可重建的工作提示；进程退出或任务被丢弃，不撤销已经进入 cell 的 Suspend/Publish/Prune。

### 1.2 通用事故记录

记录 UTC 时间、事件 ID、受影响租户/库/cell、症状、最近发布、已确认位置、归档可恢复位置、未知事务范围、quorum 状态、当前冗余和每一步操作。敏感 SQL 参数、token、密钥不能进入普通日志。恢复完成后保存去敏的证据和验证结果。

### 1.3 当前 daemon 的实际启动与重启

从仓库根目录构建后，新部署对每个尚不存在的数据目录显式 Initialize；原节点重启使用同一配置的 OpenExisting，不再加初始化 flag：

```bash
cargo +1.90.0 build --release -p scap-server --locked
./target/release/scap-server --initialize /absolute/path/node-1.json
```

上面的初始化进程结束后，才在原节点执行重启命令：

```bash
./target/release/scap-server /absolute/path/node-1.json
```

三节点配置、私钥/leaf DER pin、目录权限和 SDK 示例完整列于[工程说明](../engineering/sqlite-service.md)，不要复制一个节点的数据目录给另一个身份。OpenExisting 遇目录缺失、RocksDB/状态校验失败或身份/limits 不符会拒绝，禁止改用 Initialize“修复”。SQLite cache 是可丢弃执行副本，和承载权威的 RocksDB 不同。

客户端用 `db.status()` 检查当前 revision、suspended/cold 与归档位置，用 `db.query()` 做新的强读。不要用普通 SELECT 保活来检测休眠：它可能触发恢复；status 本身不唤醒。出现 `ScapError.request` 时保留原请求身份，按 RB-06 查证。当前 HTTP 非 loopback 监听需要明示已配置外部 TLS 代理；peer 始终执行 mTLS 与 pin 检查。

## 2. RB-01：worker 退出、节点丢失或本地文件损坏

**触发：** 进程退出、持续不可达、checksum/SQLite 完整性错误、本地卷丢失或恢复无法完成。

**前提：** 所属 cell 仍有健康 quorum。没有 quorum 时转 RB-03，不执行 owner 重分配。

**当前实现：** 幸存 leader 的维护/请求路径自动执行 owner fencing 和新目录恢复，不需要管理员手工指定 epoch。发现 SQLite cache 内容不匹配时退休 writer，后续恢复仍使用相同权威历史；路径/symlink/清理异常需人工检查。若坏的是 RocksDB/WAL/状态机，当前没有自动坏盘重建，停止该节点并保全介质。以下通用健康、排空和手工迁移步骤中未开放的接口仍是 planned，不能通过修改数据文件代替。

1. **确定范围。** 通过计划健康查询取得该节点承载的数据库列表，记录各库 incarnation、epoch、owner 与最后已确认/已提交位置。区分单库文件损坏与整个宿主机故障。
2. **停止错误流量。** 从入口摘除故障 worker 的服务路由，停止向该节点分配新库。入口摘除本身不是 fencing，后续仍必须做权威栅栏。
3. **保全诊断。** 损坏文件、staged WAL、核心转储和错误日志按保留策略封存。未经确认不得把这些文件上传成新恢复基线。
4. **更新权威。** 当前由 leader 自动按当前 incarnation/epoch 执行 Claim；将来手工栅栏/迁移同样必须有条件提交。若条件不匹配，重新查证当前权威，禁止手动覆盖或盲目递增。
5. **重建状态。** 新 worker 从已发布且校验通过的基线和 cell 已提交日志重建。只重放已提交事务；本地 staged tail 不得直接发布。若恢复链缺失，保持该库不可用并升级事故。
6. **验证旧 writer。** 即使旧节点重新出现，它携带旧 epoch 的提交必须被 cell 拒绝。存在疑问时不要开放新 owner。
7. **开放路由。** 新 owner 完成重放、权威校验及强一致读屏障后，标记 ready。先放少量流量，再恢复完整配额。
8. **处理在途请求。** 用原幂等键查询提交结果。没有键或记录已过保留期的写请求转业务核对，禁止自动重放。

**完成标准：** 已确认事务仍可读；新 owner 唯一；旧 owner 不能提交；归档重新追赶；未知事务状态有记录。该路径应恢复相同已提交历史，不应降低恢复位置或改变 incarnation。

**停止条件：** quorum 不成立、恢复位置倒退、校验失败、旧 writer 仍可写或成员状态不明。

## 3. RB-02：一个 Raft 副本或一个 AZ 故障

**触发：** 一个存储副本失联、日志持久化失败，或整个 AZ 中的节点不可用。

**当前边界：** 原目录有效的成员按 OpenExisting 重开、日志追赶或接收完整 snapshot；永久损坏副本在仍有健康多数派时，按 [成员操作流程](../engineering/membership-operations.md)使用新身份替换。本机进程测试不是跨 AZ 故障域认证。新身份、证书与故障域放置由 operator 准备，不能编辑 peers 伪装已完成成员变更。

1. 记录 leader、term、三成员位置及 AZ 分布。确认其余两个成员构成健康 quorum；只见到两个 Pod “Running”不足以证明 quorum。
2. 宣布冗余降级，暂停该 cell 的滚动升级、计划搬迁和其他成员变更。检查剩余两 AZ 容量是否承受 worker 接管和副本 I/O。若发生实际 fsync 失败，确认故障成员已经停止投票及服务，不能只从负载均衡摘除。
3. 若 leader 丢失，等待正常 Raft 选主；通过线性化健康查询验证新 leader，不手动指定一份旧日志为主。
4. 对丢失 AZ 内的 worker 按 RB-01 恢复 owner。对仍健康的 owner 避免无意义迁移。
5. 若故障短暂，优先恢复原成员并追赶；确认其持久身份、日志和成员资格一致。若盘损坏，先保全证据再重建。
6. 需要更换成员时，先在所有原 voter 部署支持 ADR-0016 的版本并预注册身份，再串行执行新目录 Join、AddLearner、追赶、ReplaceVoter、LeaveJoint。每次使用新鲜完整配置 CAS，未知结果先查询；不得重用旧 ID、降低 quorum 或把普通配置编辑当作成员变更。
7. 仅在新成员追赶到规定位置、稳定观察期通过、AZ 冗余恢复后，解除维护禁令。

**完成标准：** 三成员有效、AZ 分布合规、已确认事务保留、无异常 tail、写入和强读正常。记录选主和 owner 恢复的实测 RTO，不宣称固定秒数。

**停止条件：** 第二个成员健康恶化、成员配置冲突、磁盘水位不安全。转 RB-03，优先保持介质与历史。

## 4. RB-03：cell 失去 quorum

**触发：** 多数副本不可达、磁盘损坏、网络分区，或成员配置无法判明。

1. 确认写入口已经 fail closed。检查没有 Gateway、worker 或 leader 在缺乏 quorum 时继续返回成功；标准强读也应拒绝。
2. 冻结该 cell 的生命周期和成员操作，保留全部节点、卷、快照及日志。不要删除 Pod 所依附的持久卷，也不要初始化新 Raft 身份。
3. 分别采集可达节点的 term、成员配置、commit/applied 位置及日志完整性。采集是读操作；不能因为某节点“日志最长”就将其选为权威。
4. 排查网络、DNS、证书、I/O、CPU 饥饿与最近发布。优先修复原有健康成员之间的通信或恢复其原持久介质。
5. 能恢复原多数派时，按正常 Raft 规则完成选主，重新建立读屏障。核对已确认事务账本和未知事务，再按渐进流量恢复。
6. 只剩少数派但其他介质尚可能恢复时，继续保全和修复，不执行单副本强开。
7. 证明多数介质不可恢复时，转 RB-08。必须人工确认进入“可能损失尚未归档已确认事务”的灾难恢复流程。

**绝对禁止：** 自动 force reset；删除 Raft 目录让系统“自行重建”；从 S3 的最近日期文件启动并当作最新；降低 quorum 来恢复成功响应；在不了解原集群是否仍可写时另建同身份 writer。

**完成标准：** 恢复原 quorum 且已确认历史保留，或经过明确批准完成带缺口声明的新集群灾难恢复。两种结果必须在事故报告中区分。

## 5. RB-04：S3 不可用、归档积压、磁盘水位升高

**触发：** 对象存储超时/拒绝、凭证故障、manifest 不推进、GC/compaction 停滞或磁盘达到告警线。

**当前实现：** 后台归档在独立有界线程执行，S3 黑洞时任务失败/退避并保留未归档物理历史，热库仍走原 durable quorum。已 cold 的前景 hydrate 在本库 lane 等待对象或在原 deadline 内失败，对象 I/O 不持有共享任务队列锁；其他库可通过自己的 lane 继续服务。status/lookup 不访问 S3。

排队和执行中的请求共同计入全局 32 请求 / 8 MiB、每库 8 请求 / 2 MiB 的预算，额度用尽返回 `OVERLOADED`。本库 lane 正在退出时，已准入请求保留原预算，等待成功 join 后由新 lane 按序执行，等待也受原 deadline 和取消约束；这些等待不允许启动重叠 writer。UNKNOWN 仍按 RB-06 查证。目录扫描及活动 lane 的维护仍同步访问 cell，排障应同时检查元数据延迟、quorum、CPU 和磁盘，不能只观察 S3。当前没有加权公平调度、GC、DR checkpoint、百分比磁盘自动背压或恢复空间预留，下面相关步骤是目标运营要求，不是已有命令。

1. 检查 PUT、GET、校验、manifest 发布和 DR checkpoint 生成分别是否成功，区分“对象上传慢”与“已经上传但发布失败”。分别记录普通归档位置与最后完成态 DR checkpoint 的可恢复位置，不能只记录最后 PUT 时间。
2. 查询每个 cell 的本地使用率、绝对剩余空间、未归档字节、增长速度、最大事务和预留预算。估算到停写线的时间并更新影响范围。
3. 按经验证的容量边界控制准入。当前有 command/state/history/queue 上限；70% 告警、80% 限流、90% 停新用户写是 planned 的 v0 水位，不是现有内置控制器。生产部署还需绝对空间预算和控制/恢复预留；空间不足时停止新写并扩容，不能等 ENOSPC 后手工删日志。
4. 先限制异常租户和大型事务，防止一个库占满共享 cell。停止非必要快照、重建或冷唤醒的并发扩张，但不停止必要归档和安全恢复。允许在完整 head/tail 已由 cell 持久保存时 Suspend 并释放 worker；fullyCold 的持久热数据卸载仍等待归档和 GC 证明，二者不能混为一个动作。
5. 修复对象存储依赖：核验网络、endpoint、权限、凭证有效期、配额、请求限流与校验失败。权限修复遵循最小范围，不能通过开放整个 bucket 绕过问题。
6. 当前等待后台按有限退避重新读取权威状态并生成新任务；没有人工“强制发布”接口。条件 PUT 后仍核验精确对象及摘要，不凭一次响应推断不存在，不覆盖同身份的不同内容；旧任务不能刷新 owner 来续办。
7. 当前仅在 Publish/Prune 的严格条件通过后推进冷状态，随后由全 cell Checkpoint 处理日志；不删除 S3 对象。GC/PITR 引用验证须在未来实现后才能启用。
8. 验证对象可读取、恢复链连续、积压持续下降，并降到较低水位后分阶段恢复写配额。不要在刚完成一次上传后立即解除所有限制。

**完成标准：** 可恢复归档位置持续推进，空间增长可控，绝对预留充足，停写和恢复有审计记录，最新快照及增量链通过抽样恢复。

**停止条件：** 剩余空间无法持久化已受理事务或控制记录。保持停写，扩容或恢复安全归档路径；不能手工删 WAL 腾空间。

## 6. RB-05：控制面、etcd 或鉴权依赖失联

**状态：后续动态控制面流程。** 当前 daemon 没有 etcd/外部身份服务依赖，使用静态 token/目录，auth_epoch 仍每次由 cell 复核。配置凭据错误或过期 epoch 应拒绝；不能因外部系统不可用自行扩权。下列 60 秒缓存、JWT、分发及目录 reconciliation 尚未实现，不适用于声称当前静态 token 有 TTL。

**触发：** 目录查询、调度、策略服务超时，etcd 失去 quorum，控制服务全部退出，或仅部分节点能访问控制面。

1. 分别检查 storage cell quorum、etcd quorum、控制服务和鉴权源。不要把“etcd 不可用”一律处理为“数据库必须丢弃 owner”。
2. 冻结创建、冷唤醒、删除、恢复、搬迁和需要新 owner 的任务。保留已知任务 ID、预期版本和最后状态。
3. 已有 owner、有效路由且能到达 cell quorum 的库，可在有效授权边界内继续。路由缓存只用于定位，cell 仍校验 db_id/incarnation/epoch；权限缓存单独检查 auth_epoch 和范围。没有路由的请求返回暂时不可用，不广播探测所有 cell 猜测数据库归属。
4. 验证正向授权缓存最长 60 秒且不晚于 token 到期，缓存命中不续期；JWT 尚未过期也不能越过该新鲜度上限。TTL / token expiry 在新操作准入和 leader 提案前检查；确定性 `apply` 不使用副本墙钟判断过期，已经接受的提交不因 token 随后失效被撤销。管理动作要求新鲜授权，旧 TCP 连接不能绕过准入检查。撤销通过同一 cell Raft 中有序的 auth_epoch / fence 生效，控制面不能覆盖全部 cell 时记录未生效范围，不声称即时全域撤销。
5. 修复 etcd 时遵循其安全集群恢复流程，区分恢复原 quorum 与从备份建立新身份。不能把较旧目录备份恢复出来就立即开放所有调度。
6. 控制面恢复后，先以只读协调方式对照 cell 内 incarnation、epoch、owner、tombstone 及已提交控制任务。cell 已提交状态优先于旧目录。
7. 对响应丢失的任务按原任务 ID 查询结果；对不匹配任务转冲突状态，禁止重复创建、删除或迁移。
8. 对账完成、授权源恢复并验证缓存刷新后，逐步开放生命周期任务。保留分区期间被拒绝及已完成任务的审计。

**完成标准：** 没有重复 owner / task；目录与 cell 权威一致；授权窗口未越界；恢复期间没有把 tombstoned 库重新上线。

## 7. RB-06：提交结果未知及幂等重试

**触发：** 写请求超时、连接重置、Gateway/worker 崩溃，或响应在提交后丢失。

1. 收集原请求幂等键、tenant/数据库身份、原 incarnation、请求摘要和客户端错误。日志中不复制敏感参数；摘要应足以识别相同请求。
2. 使用正式 SDK 的 `lookup(error.request)` 或 HTTP request-outcome 入口，携带原 ID 和原 SQL/参数向权威侧查证。查询重新检查当前权限和原请求主体，冷库也无需先 hydrate，不能仅凭幂等键读取其他租户结果。
3. 若状态为已提交，返回保存的确定结果或可验证结果引用，不重新执行写入。
4. 若状态为确定拒绝/未受理，可在同一语义下使用原幂等键重试。若仍未知或权威不可达，保持未知并退避，不伪装失败后换键重试。
5. 相同键但摘要不同必须返回冲突。并发相同键只能有一个有效提交，结果记录与事务提交在同一权威事务中绑定。
6. 若数据库已经恢复到新 incarnation，旧在途请求不能自动作为新请求重放。返回明确的运行代变化，由业务核对后决定补偿或发起新动作。
7. 查无记录仍是 unknown；需要终止迟到提交时使用正式 `resolveOrCancel`，并等待有序结果，它不能撤销已提交事务。当前每库最多 128 条 accepted/cancel 记录且不淘汰；未来引入过期/退休时，窗口外返回“过期/无法证明”，不能把缺失解释为未提交。无幂等键的未知写入转业务核对。

**完成标准：** 同一有效键没有产生重复业务写；所有未知状态明确保留或解决。幂等只覆盖保留窗口内的数据库请求，不自动保证支付、消息或外部 Agent 工具调用恰好一次；这些动作需要各自的业务幂等或 outbox。

## 8. RB-07：按库恢复误删、错误 SQL 或逻辑数据错误

**状态：planned。** 当前 cold hydrate 只恢复同一库的当前已确认 head，不提供 PITR、任意时间点恢复或新 incarnation 切换 API。以下是实现相应工具前的安全合同，不能用旧 S3 对象覆盖当前库执行。

**触发：** 已提交的错误 DELETE/UPDATE、错误 schema 迁移，或误删逻辑数据库。

**前提：** 这不是 worker 文件损坏；正常复制已经保存了错误。恢复需要业务确认时间边界与影响。

1. 冻结受影响库的进一步破坏性变更，保留当前运行代。记录错误事务的位置、发现时间、最近正确状态、其他系统副作用和受影响业务操作。
2. 对相关快照、segments 和 PITR 范围创建保留 pin，暂停会影响该范围的 GC。pin 是计划管理能力，必须在权威中持久化，而不是临时运维笔记。
3. 选择明确恢复位置，优先使用已验证事务位置；墙钟时间只用于定位候选。列出该位置之后将不包含的正确与错误事务，请业务负责人确认。
4. 在隔离目标库/新 incarnation 恢复。验证 manifest、对象摘要、segments 连续性和目标位置，不改变生产路由。
5. 执行结构、行数、关键业务不变量、样本记录及 schema 版本校验。需要时从恢复库提取数据补偿原库，而不是整体回滚全部后续正确事务。
6. 如果选择整体切换，冻结源库新写、处理所有在途/未知事务，并记录切换边界；保持旧运行代只读封存。
7. 经新鲜授权和批准，通过 cell 权威发布新 incarnation 与路由切换。旧 writer、旧事务和旧内部授权不能访问新运行代；对客户端提供清晰的代际变化错误。
8. 恢复少量流量并核查业务指标。确认外部消息、支付或工具调用需另行补偿，数据库 PITR 不会撤销外部副作用。
9. 观察期结束后按保留策略释放 pin。完整保留源历史、恢复参数、校验结果和批准记录。

**完成标准：** 只恢复指定逻辑库；其他租户恢复位置不变；旧 writer 无法提交；数据和外部副作用核对完成。误删库恢复不得复用旧 incarnation。

**回退边界：** 切换前可以丢弃隔离目标；切换后若已有新写，不能直接重新指向旧运行代，需再次冻结、核对差异并制定新的恢复/补偿步骤。

## 9. RB-08：整个 cell / 区域灾难，仅有归档可用

**状态：planned。** 当前尚未生成完成态 DR checkpoint 或实现 S3-only 建群。永久丢失权威状态时保持不可用，保全全部介质/对象并评估缺口；普通单库归档不能证明整个 cell 的发布、权限与管理历史，禁止以 Initialize 原身份绕过。

**触发：** 证明原 quorum 持久介质不可恢复，需要接受异步归档边界。

1. 宣布灾难恢复事件并隔离原集群写入口。确认幸存的旧节点即使恢复网络也不能向客户端服务或写入新集群。
2. 保全原节点和卷的清单、可见日志位置、最近 ACK 证据及所有归档对象。暂停相关 GC。
3. **只从完成态 DR checkpoint 开始。** 按 [存储生命周期 §11.1](../architecture/storage-lifecycle.md) 找到候选完成清单，验证其受控来源/签名、格式、源 cell 身份、committed/applied 位置，以及状态机快照和全部引用对象的摘要与可读取性。独立验证解密和权限所需的密钥/配置。读取 checkpoint 内保存的数据库身份、head、epoch、auth_epoch、tombstone、幂等记录、曾被接受的 manifest 指针及未归档已提交 tail；不得从 bucket 零散 manifest 自行拼出权威目录。缺少完成标记、数据、来源证明、解密密钥或权限材料时，该候选不得用于开放服务。
4. 从**同一个校验通过的完成态 checkpoint**及其完整引用闭包，为每库确定可恢复提交位置。包含的未归档 tail 可用于重建，但 checkpoint 外更“新”的零散快照/segments/manifest 不能自动推进恢复点。最新 checkpoint 上传半途损毁时，仅可选择前一个完整完成态 checkpoint，并披露扩大后的缺口。将恢复位置与最后可知 ACK 位置比较；无法获得最后 ACK 位置时明确“损失上界无法完全证明”，不能报告 RPO 0。
5. 形成恢复计划：选定完成态 DR checkpoint 的精确身份及可恢复末端、缺失区间、受影响租户、预计业务补偿、原集群隔离方法及新集群身份。取得业务和事故负责人明确批准。
6. 在新集群身份中恢复，逐库校验数据与元数据。etcd 备份可以滞后；先在维护模式依据 checkpoint 的 cell 状态对账/重建目录，防止旧 tombstone、epoch 或凭证被错误复用。核查跨 cell 迁移 Seal，未完成迁移不能自动在两个位置解封。
7. 通过隔离环境验证读写、权限、幂等键历史和恢复边界。旧运行代在途请求默认拒绝，不当作未提交请求自动重放。
8. 按 tenant 批次切换路由并观察。报告可恢复位置、确认丢失/未知事务及补偿方案。
9. 原介质后来恢复时，先只读取证与差异分析，禁止与新集群自动合并。任何补回数据都需要业务级冲突处理。

**完成标准：** 从完成态 DR checkpoint 独立恢复成功，完整引用闭包可验证，权限和密钥齐备，缺口透明，原/新集群不会双写，批准和审计完整。此手册不提供自动 force reset。

## 10. RB-09：归档完整性异常或 GC 疑似误删

当前没有 GC；对象缺失/摘要不符会阻止发布或 hydrate，不能回退较旧 revision。当前可执行的是停止依赖该对象的恢复并保全证据，检查 bucket 权限、网络和外部生命周期策略；没有自动对象修复或人工改 pointer 接口。下面涉及 GC/pin/重新发布的流程在相应管理能力实现后才可执行。

1. 立即暂停受影响 cell/运行代的 GC 和新恢复发布；保留候选清单、manifest 版本、执行日志和对象版本信息。
2. 对照权威 manifest 和全部保留 pin，确定缺失对象是否仍被活动库、PITR、旧运行代、副本修复、保留的 DR checkpoint 或生成中 checkpoint 的持久 pin 引用。checkpoint 的快照、tail、来源证明和全部引用数据都应受同一保留闭包保护。
3. 如果实时 quorum 仍持有完整 payload，隔离坏对象并按内容身份重新生成归档；不能在校验前改写 manifest 来掩盖缺失。
4. 如果仅剩损坏归档，保持受影响恢复不可用，进入 RB-08 的缺口评估；不要跳过缺段启动数据库。
5. 复现发布与删除的并发历史，核查是否缺少 Raft 发布屏障、二次引用检查或孤儿对象保留期。
6. 修复代码与策略后，通过 GC/PITR 故障测试和恢复演练才恢复 GC；先运行只输出候选的预演，再小批量删除。

**完成标准：** 全部受保留约束的恢复点仍可恢复；未引用对象清理不会伤及活动或历史数据；若已发生缺失，影响如实记录。

## 11. RB-10：滚动升级、降级与版本门禁

**当前格式边界：** cell state/command/outcome 写入 v2；仅在相同身份与持久化 limits 下读取合法 v1 热历史，原管理操作 ID 的幂等结果继续有效。没有 limits 自动迁移或混版本滚动协商；写入 v2 后禁止直接启动旧二进制。下面的 canary、能力协商和格式启用开关是 planned，当前升级应先在隔离数据副本和合法恢复流程上验证，不假装这些开关已存在。

### 11.1 发布前

1. 建立兼容矩阵：Gateway 协议、worker RPC、libSQL/WAL 格式、Raft entry/snapshot 格式、manifest、认证证明、控制面目录 schema。
2. 标明支持的混合版本窗口、支持的升级路径以及首次不可逆格式写入的位置。仅“编译成功”不是兼容验证。
3. 确认 [发布门禁](../engineering/validation.md#8-发布门禁与证据) 通过、恢复点有效、无 cell 处于冗余或空间降级。确定每一步回滚方式。
4. 新 writer 格式默认关闭；先部署能够读取新旧格式的版本，再考虑启用新格式。未知必需字段/格式必须明确拒绝，而不是忽略后继续提交。

### 11.2 分阶段执行

1. 在隔离 cell 运行兼容性和故障回归，再选择少量低风险 tenant canary。
2. Gateway 逐副本排空并更新，始终保留可用入口。旧连接通过正常断连/重连机制处理未知提交。
3. worker 逐节点排空/迁移，更新时保留 epoch 栅栏和在途结果查询。禁止一个 cell 的所有 worker 同时重启。
4. Raft 副本串行升级：一个副本完成恢复、追赶和稳定验证后才动下一个；leader 转移也必须保有 quorum。发生单 AZ/单副本故障即暂停。
5. 控制服务按向后兼容的目录迁移步骤更新；etcd 自身版本变更单独处理，不与存储组成员变更混在同一发布批次。
6. 扩大 canary 前核查 ACK 保留、写延迟、错误率、cold wake、归档/GC 和权限拒绝。最后才经能力门禁启用新写格式。

### 11.3 回退

尚未产生旧版本无法读取的数据时，可按兼容矩阵回退二进制。已写入不可逆格式时，禁止直接换回旧版本；选择前向修复或经验证的数据转换/恢复。用户业务 schema 迁移有独立回退边界，不能用基础设施回滚代替。

**完成标准：** 每个阶段证据留存；所有成员版本和格式能力可查询；故障冗余恢复；冷库也覆盖升级后唤醒验证，而不只测试一直活跃的库。

## 12. RB-11：监控中断或就绪探针异常

当前 `/livez` 表示进程入口存活，`/readyz` 用于候选路由，不代替实际请求的 quorum/权限判断；数据库状态使用受鉴权 `status`。只有目录维护更新公开就绪提示，每库 lane 的私有就绪状态不覆盖该提示，关闭时始终未就绪。单库超时仍需检查该库的原请求结果；实际目录检查失败也不能由另一个库的成功请求掩盖。生产指标/告警平台尚未装配，以下记录和降级规则保留为运营要求。

1. 区分观测系统失联与数据面不可用，使用独立授权的只读健康检查；不得依赖缺失的监控自动判断数据丢失。
2. 确认磁盘背压、quorum ACK、epoch fencing、认证到期等安全保护由服务内执行。
3. 暂停升级、GC 策略修改及批量迁移等需要实时观测的高风险操作；正常事务不应因指标上报失败阻塞。
4. 检查日志缓冲有界，避免监控故障填满数据库磁盘。恢复采集后补齐事故窗口，明确无法重建的观测缺口。

**完成标准：** 安全保护未依赖外部监控存活；采集恢复；观测缺口和期间操作清楚记录。

具体故障脚本和已完成的真实执行记录见 [service-network](../../experiments/service-network/README.md)、[archive-s3](../../experiments/archive-s3/README.md)及 [G0 证据](../engineering/g0-evidence.md)。重启成功、功能恢复和满足生产 RTO 是不同验收项，仍按 [性能与恢复规范](../engineering/performance-slo.md)记录条件及失败样本。
