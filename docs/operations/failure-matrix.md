# 故障模型与组件可用性矩阵

> 状态：完整目标故障规范与当前有界实现并列。2026-11-02 已有可部署三节点 daemon、HTTP/Node SDK、独立强读、leader owner 恢复和 S3 冷生命周期。第 3.1 节保留底层 peer 实验证据，第 3.2 节说明当前服务行为；动态控制面、GC/DR 和完整生产矩阵仍为 planned。实际执行结果以实验记录为准，配置参数与功能测试不等于恢复 SLO 达标。

正式引擎的当前边界见 [SQLite adapter 合同](../engineering/sqlite-engine.md)：失败停止相应 writer；已接受而 native/最终 COMMIT 失败保留 receipt 并报告已提交不可用；有效历史 receipt 的坏结果同样不伪装成未提交。当前 leader 已自动从权威物理历史创建新目录并恢复 owner，旧 SQLite cache/sidecar 不直接复用。完整服务流程与容量边界见 [SQLite 服务实现](../engineering/sqlite-service.md)。

## 1. 适用范围和基本假设

SCAP 的目标服务为每个逻辑数据库提供一个可写 owner。Rust worker 承载 libSQL 执行，事务先生成未对其他请求可见的 staged WAL；所属 storage cell 的 Raft 多数副本完成持久化并提交后，worker 才能发布该事务并向客户端返回成功。目标部署让一个 cell 的三个 Raft 副本跨三个可用区；当前本机三进程实验不代表三个故障域。同一 cell 中的数据库共享这一个 Raft 组，而不是每库建立一个 Raft 组。

数据库的 owner、epoch、incarnation、auth_epoch 和事务提交资格在同一 cell Raft 状态机内判定。当前目录/凭据由静态 JSON 配置，etcd 不参与启动；后续 etcd 目录、租约和调度也不能成为提交权威。当前 S3 保存完整单库事务历史及 manifest，Publish 经 Raft 接受后才能成为恢复入口；Prune 与共享日志 Checkpoint 分开，“上传完成”不等于获准删除数据。分段归档、对象 GC 与 DR checkpoint 尚未实现。

共识库已按 [ADR 0006](../adr/0006-raft-rs-consensus-library.md) 采用 `raft-rs`，以下故障合同不因此降低。驱动循环、持久化、读取和恢复的具体约束见 [raft-rs 集成门禁](../engineering/raft-rs-integration.md)。

本文使用以下术语：

| 术语 | 含义 |
| --- | --- |
| 已确认事务 | 客户端已收到成功响应，且其 WAL 已经 Raft 多数副本 fsync 并提交；二者缺一不能声称“已确认” |
| 提交结果未知 | 客户端未收到确定结果，但事务可能已提交；断连、超时和 worker 崩溃都可能产生该状态 |
| 原始事务日志 | 足以重建事务结果的数据，而不是只包含“某个 worker 已写入”的确认标记 |
| epoch | 同一数据库运行代中的 owner 栅栏，拒绝旧 owner 后续写入 |
| incarnation | 逻辑数据库一次运行代的身份；删除后重建、PITR 切换等不得复用旧运行代 |
| auth_epoch | cell 权威中的授权版本 / 撤销栅栏；过期授权不能凭 JWT 尚未到期继续准入 |
| 目录 | 路由、生命周期及调度的索引；可能短暂滞后于 Raft 权威状态 |
| 冷唤醒 | 为尚无运行中 worker 的数据库分配 owner，并加载已提交的恢复基线及日志 |
| Suspend | 通过 cell 封存并释放 worker 执行资源；已确认但未归档的数据仍由 cell 持久状态及尾部保存，不要求等待 S3 |
| fullyCold | 归档完整并获得安全回收证明后，进一步卸载不再必需的持久热数据；不能仅凭 worker 已停止判断 |
| 完成态 DR checkpoint | 包含已提交 cell 状态及所需数据的可独立验证恢复包；仅剩 S3 时的恢复入口，格式和来源要求见存储生命周期 §11.1 |
| 强一致读 | 相对该数据库已提交历史的线性化读；必须有 cell 权威证明，不能直接相信旧 worker 的本地文件 |

### 1.1 必须一直成立的安全规则

1. **没有 quorum 不产生新的成功写响应。** 单个副本本地 fsync、S3 PUT 成功、etcd 租约有效都不能替代 quorum。
2. **staged WAL 在提交前不可成为其他请求可见的数据库状态。** 本地执行成功不等于提交成功；崩溃后清除或重新判定未提交 staged 状态。
3. **epoch / incarnation 校验与 commit 在同一 Raft 组内排序。** 旧 owner 即使仍持有文件、连接及目录缓存，也不能在新 epoch 生效后提交。
4. **只有客户端断连，不代表服务器回滚。** 客户端或网关必须用原幂等键查询结果，不得把未知结果当作安全重试许可。
5. **标准读取不得从失去权威的旧 owner 继续服务。** v0 采用经 quorum 确认的读屏障及 owner 校验；若将来引入读租约，必须另行说明时钟、到期和分区证明。
6. **manifest 发布先于数据回收。** 发布还不足以单独批准删除：保留策略、PITR 窗口、备份 pin、保留的 DR checkpoint、生成中 checkpoint 的持久 pin、其他引用和副本修复需求均需满足。
7. **恢复不得伪造最新位置。** 缺失 quorum 时不得自动把某份旧 S3 快照标为最新，也不得自动 force reset Raft。
8. **数据面失去控制面时，只能在已有授权和已有权威的范围内继续。** 不自行创建 tenant、扩权、跨 cell 搬迁或重建已删除数据库。

## 2. SLO 边界

| 场景 | 数据保护目标 | 可用性目标及限制 |
| --- | --- | --- |
| 单 worker / 单宿主机故障 | 已确认事务 RPO 0 | 按 R0/R1/R2 的恢复档位验收；实际 RTO 待测，活动事务可能结果未知 |
| 单 AZ 故障 | 在另外两个 Raft 副本健康且持久化正确的前提下，已确认事务 RPO 0 | 允许短暂选主与 owner 重分配；R2 有初始分级目标，实际 RTO 待测 |
| 一个 Raft 副本落后或损坏 | 由其他健康 quorum 保存已确认事务 | 降级运行且停止扩大故障范围；修复期间不再容忍第二个副本同时丢失 |
| 多数 Raft 副本不可达 | 保持安全，禁止新的成功写响应 | 可写性不可用；强一致读同样不能绕过 quorum |
| 单 cell 全部持久介质不可恢复 | 取决于最后完整、校验通过的完成态 DR checkpoint 及其引用数据 | 不承诺 RPO 0；必须显式灾难恢复决策 |
| 区域灾难、仅剩 S3 / 跨区域副本 | 仅保证完成态 DR checkpoint 可验证覆盖的事务，含其中保存的未归档 tail | checkpoint 生成/上传和跨区域复制均可能有缺口；恢复位置和数据损失范围必须报告 |
| 误删、错误 SQL、应用逻辑错误 | HA 会保留这些已提交错误；需 PITR / 业务补偿 | 不能用自动切主撤销已提交业务操作 |

RPO 0 的目标范围不包含“永不损坏的云基础设施”假设。必须验证 fsync 语义、AZ 反亲和、quorum 配置、故障晋升、日志恢复以及底层持久介质。客户端没有收到成功但最终发现已提交的事务属于结果未知，不应被错误统计为“恢复多出了数据”。

初始内部目标见 [性能与恢复目标](../engineering/performance-slo.md)：writer 故障的 R0 经济档（完整恢复 ≤1 GiB、有效恢复带宽 ≥100 MiB/s、tail ≤64 MiB）p95/p99 为 20/30 秒，R1 完整文件预置缓存档为 8/15 秒，R2 跨 AZ 热备执行档为 5/10 秒；R2 单 AZ 故障目标为 10/20 秒。R1/R2 是 **G4 拟实现选项**，必须先验证预备副本与接管容量，不能当作当前已具备的能力，也不能据此跳过 quorum、claim 后重读 head 或激活校验。

RTO 按 `检测 + 判定/栅栏 + 调度 + 恢复重放 + 就绪检查 + 客户端重连` 分段测量，从故障发生计到连续稳定恢复窗口的起点，后续 30 秒验证通过才确认该起点；第一次成功另记。至少 100 次/场景样本并保留超时和 UNKNOWN，正式 p99 建议至少 1,000 次主要场景样本。目标尚未实测，只有给出完整条件、证据和失败样本后才可评估对外 SLA；任意大库的完整恢复不承诺固定几秒。

## 3. 组件故障矩阵

下表中的“自动”描述目标行为。实现前必须通过 [验证规范](../engineering/validation.md) 中对应场景。

独立 Gateway/控制服务、etcd、自动坏盘调度、磁盘百分比背压、GC/PITR/DR 等行仍为 planned；不要把目标矩阵当作当前已安装的组件清单。受控成员替换按 [ADR-0016](../adr/0016-durable-membership-replacement.md)提供，当前服务的准确行为单列于第 3.2 节。

| 故障 | 写入与标准读取 | 自动处理目标 | 运维边界 / 禁止行为 |
| --- | --- | --- | --- |
| 单个 Gateway 进程退出 | 新请求可由其余 Gateway 接受；该进程上的连接中断，事务可能结果未知 | 负载均衡摘除；客户端重连；原幂等键用于查结果 | 不重放无幂等键的写请求；Gateway 不是事务持久化节点 |
| 全部 Gateway 不可用 | 对外入口不可用；已受理事务可能在后端完成 | 重建至少一个入口并通过端到端就绪检查 | 不因入口超时删除后端事务；不得绕过鉴权暴露 worker 端口 |
| Gateway 重启 / 升级 | 原连接中断；新连接只使用有效目录和授权 | 清空不可信的内存状态；重新获取配置；按有界缓存规则服务 | 不从本地旧路由推断 owner；不把重启当作取消事务 |
| 单 worker 崩溃 | 该 worker 的数据库暂不可用；cell 已确认日志仍在 | 经 cell 权威更新 owner/epoch，重新加载已提交状态 | 不先在旧 epoch 启动第二个 writer；不把 staged WAL 当作已提交 |
| worker 本地盘损坏 / 丢失 | 本地缓存与文件不可直接使用；相关库暂停 | 隔离损坏副本，从已验证的基线及 quorum 日志重建 | 不以损坏文件覆盖其他副本或上传为新快照；不直接做 PITR 回退 |
| worker 卡住、OOM、无限查询 | 受影响库超时；其他库依赖资源隔离继续工作 | 查询预算、内存/CPU 限额；终止执行；必要时替换 owner | 杀进程前后都可能存在提交结果未知；不得把一次 OOM 扩大成全 cell 重启 |
| 旧 worker 与控制面断开，但仍能访问 cell | 已有授权内可向 cell 请求提交；epoch 过期会被拒绝 | 以 cell 权威为准；收到 stale-owner 后自我隔离 | etcd 旧租约或缓存不能越过新 epoch |
| 旧 worker 被隔离，连不到 cell quorum | 禁止新的成功写和强一致读 | 返回不可用；保持 staged 状态不发布，等待查询结果/回收 | 禁止离线写后向客户端返回成功；禁止继续提供无屏障的“最新读” |
| 一个 Raft follower 退出 | quorum 健康时继续 | 限制维护并重建该副本；恢复追赶 | 追赶前不视作健康，不同时滚动第二个副本 |
| Raft leader 退出 / 重启 | 选主期间短暂不可用；已确认日志应保留 | 新 leader 按 Raft 规则恢复；读屏障重新建立 | 未提交 tail 可被覆盖；不能将本地最长日志等同于已提交日志 |
| Raft driver 次序校验失败、持久完成错配或 apply 失败 | 对应副本停止正常服务，不发送尚无持久依据的确认；其他健康副本形成 quorum 时可继续 | 保留故障证据，按完整 HardState / ConfState、日志、snapshot 与实际 applied 状态恢复 | 不忽略 `LightReady`；不提前调用持久/应用推进接口；不凭内存 applied 或取最大水位修复不一致 |
| Raft 组失去多数派 | 新写和强一致读停止 | 等待恢复多数派；报警并保全所有介质 | 禁止自动降为单副本、强制新集群、从 S3 覆盖现有日志 |
| 一份 Raft 日志 fsync / checksum 失败 | 故障副本停止持久化确认及投票，退出正常服务；另两副本健康时可继续 | 将副本标为不可用，保留诊断证据，再替换/重建 | 吞掉 I/O 错误后继续 ACK 或投票会破坏安全性；健康检查须暴露失效原因 |
| Raft 日志磁盘接近满 | 按 cell 水位逐级限流，达到停止线拒绝新的用户写 | 排查归档、compaction 和热点库；保护控制记录预留 | 禁止手动删除 WAL 或未确认可回收的 segments；控制记录也无法安全写入时整体停写 |
| 单 AZ 失效 | 剩余两 AZ 若组成 quorum 可恢复写入；故障 AZ 内 owner 需迁移 | 有剩余容量时重新分配 worker；选主与恢复 | Gateway、etcd、控制面不能全部同 AZ；冗余耗尽时暂停升级 |
| 一台 etcd 节点失效 | etcd quorum 在时目录操作正常；cell 提交无变化 | 依 etcd 运维规范更换节点 | 不混淆 etcd quorum 与 storage cell quorum |
| etcd 多数派不可用 | 已知路由、已有 owner、有效授权且 cell quorum 健康的库可继续；新建、唤醒、迁移、删除及需新分配的恢复冻结 | 控制服务转只读降级；恢复 etcd quorum 后协调目录 | 不依据各自缓存并行分配 owner；不将目录缓存长期当作权威 |
| 控制服务部分副本退出 | 已有数据面不受影响；其余控制副本按协调约束处理请求 | 去重和重试幂等的控制任务 | 多副本不能让同一个迁移、删除、恢复任务重复生效 |
| 控制服务全部退出 | 活跃、已有 owner 的库可在授权边界内运行；冷唤醒与生命周期任务不可用 | 重启后按任务 ID 和 cell 状态协调未完任务 | 不认为控制任务“响应失败”就一定没生效 |
| 控制面与部分 Gateway / worker 网络分区 | 可达 cell 的已有数据面在有界授权内继续；需要新路由/新 owner 的操作冻结 | 拒绝不确定调度；网络恢复后以 Raft 状态修正目录 | 分区两边不能各自任命 writer；禁止以“服务恢复”为由跳过 fencing |
| 鉴权 / 策略服务不可用 | 仅允许仍在有效期内且匹配 cell auth_epoch 的已验证授权缓存；到期后拒绝新操作 | 使用下面的 60 秒上限；源恢复后正常刷新 | 新租户、新权限、管理动作不能离线授权；TCP 已连接或 JWT 未过期不等于无限期授权 |
| S3 PUT / GET / LIST 超时、错误或凭证失效 | 活跃且数据完整在 cell 内的库可继续到磁盘边界；依赖对象的冷唤醒/恢复可能不可用 | 有界退避重试、归档积压告警、背压 | 不把 PUT 超时当作成功；不依 LIST 结果选择最新恢复点；不静默丢弃积压 |
| Suspend 时 S3 不可用 / 归档落后 | 若 cell 已安全保存完整 head 和未归档 tail，可封存并释放 worker；后续唤醒仍需足够恢复数据 | 在 cell 中记录 head/epoch/生命周期，保留 tail 和恢复索引 | 不要求 worker 常驻等 S3；不能把 Suspend 当作已获准删除持久热数据 |
| fullyCold 卸载中断 / 重试 | 未取得完整归档与 GC 证明时保留持久热数据；释放 worker 与该卸载独立 | 幂等恢复任务；复核已发布 manifest、引用和保留 pin | 禁止仅按空闲时间或进程已退出删除 tail |
| S3 对象缺失 / checksum 不匹配 | 受影响恢复链不可用；健康的实时数据面视本地/quorum 完整性继续 | 停止相关 GC 和恢复发布；隔离异常对象，尝试健康来源重建 | 不能跳过缺段重放，也不能悄悄恢复到更老位置 |
| 归档进程崩溃 | 不直接影响已确认事务；积压持续增长 | 按内容身份幂等重传；检查 manifest 是否已提交再继续 | 不凭本地任务状态认定对象已发布；不重复递增恢复位置 |
| snapshot / compaction 进程崩溃 | 已发布状态不变；未发布产物不得当作基线 | 重启后核对引用关系，继续或清理未引用产物 | 清理需经过孤儿对象保留期；不得删除可能仍在发布中的对象 |
| DR checkpoint 生成 / 上传中途故障 | 先前完成态 checkpoint 仍是 S3-only 恢复候选；半成品不能提升恢复位置 | 保留生成任务的持久 pin，核验并幂等继续或经安全取消释放 | 不清理正在被 checkpoint 捕获的 tail / 对象；不以零散 manifest 拼凑“更新”的灾难恢复状态 |
| GC 进程退出或重试 | 数据保留增加，成本上升；用户正确性优先 | 幂等恢复清理任务 | GC 失败可延迟删除，不能反向选择“先删再确认” |
| 监控、告警或日志收集不可用 | 不应成为事务提交或读路径依赖 | 本地有界缓冲、恢复采集；暂停高风险人工操作 | 关键安全阈值必须在服务内执行，不能依赖监控系统替服务停写 |
| DNS / LB / 集群调度不可用 | 新连接、节点替换或 cold wake 受影响；已建立健康数据面可能继续 | 冗余基础服务；按真实故障定位 | 不因服务发现缺失直接变更数据库 incarnation |

### 3.1 固定成员 peer 运行层的独立验证范围（2026-11-01）

本节对应 [正式网络运行层](../engineering/raft-network-runtime.md)、[八项真实 mTLS 契约](../../experiments/raft-network/README.md)及其独立单元测试。真实契约使用同一宿主机上的三个独立进程与 RocksDB 目录，应用内容为合成 opaque payload；它不执行 SQLite SQL，也没有 Gateway、etcd、S3 或自动 writer 接管。以下证据不把上面的目标矩阵整体改为完成。

| 情况 | 已实现和实际检查 | 证据层及剩余边界 |
| --- | --- | --- |
| follower 连接拒绝、断连、双向黑洞 | 健康多数派继续；少数派未提交后缀不能增加 commit，新读不成功；连通恢复后追赶 | 三进程真实 TCP/mTLS；UNKNOWN 由后续有序状态解析，不把超时当回滚 |
| 单向 Raft 回复通路失联 | 反向路由切为黑洞、正向保持 Open，新读请求不能返回成功，多数派继续 | 未导出失败 read ticket、未逐条观察 cut 后 receipt；精确旧 ACK 重放由受控集群实验承担 |
| leader SIGKILL、整组三进程 SIGKILL 后重开 | 使用原目录保留已确认 cell 历史，重新选举、继续提交并使用新 boot 的读屏障 | 真实进程崩溃；不证明掉电、丢盘、跨 AZ RPO 或自动 SQL owner 恢复 |
| 副本落后到日志已压缩 | 通过正式网络安装完整有界 snapshot，durable snapshot/applied 前进，再次重开仍保留 | 未实现大快照流式传输、成员替换或损坏盘自动重建 |
| 无证书、错误 CA、过期/未授权 leaf、伪造身份 | mTLS 与当前 policy 拒绝输入；node、cell incarnation、本地 Raft 事件不能靠字段伪造绕过 | 真实网络加有限解析/日期单元；签发与 CA/授权分发控制面尚未实现 |
| pin 轮换后旧连接和旧队列 | 原连接新请求被拒，已准入未消费消息在到期前因 policy 复核丢弃；合法替换 pin 可使用 | 同一真实连接和队列的撤销证据；不代表动态 Raft 成员变更已实现 |
| inbox 数量/字节用尽、发送 deadline 已过 | 明确拒绝额外准入；过期发送不占新槽；只有 Received 的消息可在持久应用前消失 | 真实契约；Received 只是内存排队，不能当作已交 driver、durable quorum 或 SQL ACK |
| 迟到/重复反馈、取消和关闭 | attempt ID、deadline、term 与 snapshot attempt 过滤；实际 worker payload 预算保持到释放；关闭新准入并取消 async 任务 | 独立受控单元与正常真实退出；同步 fsync/应用回调无法被网络 shutdown deadline 强制中断 |

2026-11-04 起，正式 worker 按 [ADR-0015](../adr/0015-incremental-blocks-and-isolated-execution.md)在每个 peer 的 ordinary/snapshot lane 各有界复用一个 mTLS client，RPC 前后重新检查实际证书链、DNS、时间与当前 pin；失败、取消、超龄和迟到均丢弃。入站旧连接仍按每请求和消费时的当前 pin/日期检查。握手 CPU、连接 churn、TIME_WAIT 与资源释放成本仍待生产负载验证。自供 incoming 的 accepted socket 已显式开启 NODELAY，设置失败拒绝连接；复用和 NODELAY 均不构成吞吐或 p99 证明。故障检测到稳定业务窗口的 RTO 仍须按第 2 节独立测量。

### 3.2 当前正式服务的故障行为（2026-11-04）

本节对应正式 `scap-server`、`scap-service`、`sdk/node` 和 `scap-archive`，不是实验专用恢复算法。测试场景、原始证据及测量限制分别见 [service-network](../../experiments/service-network/README.md)与 [archive-s3](../../experiments/archive-s3/README.md)；此表描述实现合同，不自动宣称每个云产品、故障域或 SLO 已验证。

| 情况 | 当前处理 | 剩余边界 |
| --- | --- | --- |
| leader/daemon 退出或与多数派分区 | PreVote/check_quorum 后由合法 leader 取得新 owner，重读 head、恢复新目录、Activate；旧 owner 被 epoch 拒绝 | 同一 cell 的 leader 驱动恢复，没有跨 cell 调度、热备执行器或固定秒数承诺 |
| 少数派继续收到 SQL | 新提交/强读仍须 durable quorum / Safe ReadIndex，不能由 ready、旧文件或本地租约授权 | 没有 stale read/离线写降级；已接受请求可能为 UNKNOWN |
| 所有进程重启、原 RocksDB 完好 | OpenExisting 验证持久身份、limits、镜像及应用位置；重选 leader 后恢复活跃库，休眠状态保留 | 进程重开证据不等于设备断电、跨 AZ 或介质损失验证 |
| SQLite cache 丢失或页面不匹配 | 停用失效 writer，后续从相同已确认历史重建新目录；不以本地页覆盖权威 | 命名、symlink 或清理异常会停止准入要求人工检查 |
| RocksDB/WAL/状态镜像坏、目录丢失或身份不符 | OpenExisting 拒绝，保全介质；其他健康多数派可继续；operator 可用新身份经过 learner/joint 替换 | 不自动发现/采购替换机器，不在坏目录 Initialize；无 quorum 时不强开 |
| learner 落后或 joint 期间进程退出 | 未追到 commit 拒绝晋升；ConfState 与 applied 原子持久，原目录重启保留 joint；同时满足两组多数派后退出 | 管理超时可能已提交，必须强读查证，不能盲重发或删减成员 |
| 被替换旧节点重现 / 旧 ID 换空目录 | 真实成员资格约束选举与 SQL；新 ID 单调递增；Join 在建目录前核对健康 leader 新鲜配置及完整 genesis | 源 bootstrap 配置和单实例私钥由部署者保证；不提供拜占庭防护或旧身份强制复用 |
| S3 后台上传遇拒绝、黑洞或停机 | 有界后台任务失败/退避，保持未覆盖物理历史；健康热库继续原 quorum 提交 | 热服务仍受 cell 空间、CPU 和磁盘边界约束，没有无限积压 |
| 已 Cold 数据库在 S3 故障时唤醒 | 在该库独占 lane 等待精确对象或在原 deadline 内失败；不建空、不用更老对象；其他库可独立服务 | 全局与单库准入配额同时生效；未实现加权公平或恢复空间预留，dispatcher 元数据仍可能等待 cell |
| 归档上传后进程退出，尚未发布 | 对象保留但不成为恢复入口；重启按 cell 状态重建任务 | 所有对象保留，无 orphan GC 和成本收敛保证 |
| I/O 期间 owner/head 改变 | 原 Publish/Prune 的 owner/head/auth 条件拒绝迟到任务 | 队列丢弃或任务失败不等于撤销已经提交的管理命令 |
| Prune 恰好先于新请求 Claim | 明确 Cold 且 SQL 尚未执行时，原 deadline 下仅一次 fresh/hydrate/恢复 | 其他错误和 Unknown 不自动重试 SQL |
| 错库 token、旧 auth_epoch 或越权结果查询 | 静态凭据绑定后仍由新 cell view 复核当前主体/权限；写 apply 再检查 | 没有外部身份源、JWT expiry、动态配置或 60 秒策略缓存 |
| 关键 HTTP/peer/Raft/SQL/归档任务异常退出 | 节点 supervisor 停止整体服务，取消并回收其余资源 | native 同步 I/O 不能被异步 deadline 强制打断 |
| SIGTERM/Ctrl-C | 停止准入、取消当前任务、在关闭预算内 drain/join | 超时不冒充完成；进程管理仍需处理卡住的底层 I/O |

当前 Prune 仅移除数据库物理历史，完整请求结果、取消 fence、授权和 archive pointer 继续持久化。单库归档不能直接截断整个 cell 日志；所有 voter 由正式全 cell Checkpoint 保证恢复覆盖。profile 固定最多 32 库、每库 256 KiB 逻辑镜像和有界记录，无 GC、恢复空间预留或无限长尾承诺。

## 4. 控制面与鉴权降级边界

本节描述后续动态控制面和外部策略源的目标合同。当前 daemon 使用静态目录/token；每个请求仍复核 cell auth_epoch，但没有 etcd/外部鉴权依赖可供降级。当前自动同 cell 接管/唤醒不需要等待不存在的外部调度服务；不能因静态配置成功而绕过 quorum。

### 4.1 控制面失联时的数据面准入

一个操作只有同时满足以下条件，才能在目录不可用时继续：

1. Gateway 已有该逻辑库的可验证路由，目标 cell 可达。
2. 该库已处于可服务状态；不需要创建、冷唤醒、新 owner 或跨 cell 调度。
3. cell 仍能完成 quorum 提交或强一致读屏障。
4. 请求携带的 tenant、库身份、incarnation、auth_epoch 和权限与授权快照及 cell 权威一致。
5. 认证缓存未到期，且未已知收到撤销事件。
6. worker 没有被 cell 中的新 epoch、删除标记或恢复切换替代。

不满足任一条件即返回可辨识的暂时不可用或权限拒绝，不回退到旧文件、旧路由或旧 S3 快照。目录恢复后必须从 cell 对账，不得用旧目录覆盖已经提交的 owner/删除状态。

**路由缓存和权限缓存是两种不同缓存。** 路由命中只说明“请求可以发送到哪里”；cell 仍需校验 db_id、incarnation、epoch 及当前生命周期，发现旧路由应拒绝或提示重新定位。它不授予读写权限，也不延长权限缓存。权限缓存则决定已验证身份在有界新鲜度内可以做什么，仍受 cell auth_epoch 和请求范围限制。

### 4.2 有界认证缓存

planned 的 v0 初始上限为 **60 秒**，允许配置得更短；当前静态 token 不具有这套 TTL/JWT 能力。未来有效期取 `策略验证时间 + 上限`、token 到期时间、凭证到期时间的最早者；缓存命中不得延长有效期，源不可达时不得续期。即使 JWT 还有数小时才到期，权限新鲜度仍受上限约束。

- 缓存必须绑定身份、tenant、数据库身份、权限范围和 auth_epoch / 策略版本；不能只缓存“这个 token 曾经成功”。
- 已建立连接在每次新操作准入及 leader 提交提案前重新检查 TTL / token 有效期。进入确定性 Raft `apply` 后，只依据有序复制的 auth_epoch、fence 及授权范围判定，不使用各副本墙钟再决定 token 是否到期；否则副本可能对同一条目作出不同结果。正在运行的查询受执行预算限制；已经接受的提交不因 token 随后失效而撤销。
- 新租户、新数据库授权、权限扩张、删除、恢复、force recovery 等管理操作必须获得新鲜验证，不接受降级缓存。
- 时钟状态不可信时 fail closed；不得因时钟回退无限延长缓存。实现必须规定单调时钟及进程重启的缓存失效语义。
- 撤销目标通过 cell 中的 auth_epoch / fence 变更持久化。写提交按该变更和事务条目在同一 Raft 组内的顺序确定是否接受，读准入校验当前权威版本；不能只等待 Gateway 自愿刷新缓存。变更前已经合法接受的事务不被追溯撤销，TTL 到期同样不撤销已经接受的事务。
- 撤销事件已到达时本地缓存立即失效。控制面无法连接全部目标 cell 时，不承诺即时全域撤销；未收到撤销的缓存最多在上述窗口内继续准入，之后因无法取得新鲜权限而拒绝。该上限限定新的准入，不宣称已经受理的操作在同一时刻全部消失。
- Gateway 转发的内部授权证明不得比外部缓存存活更久，worker/cell 的准入检查不能只依赖某条长期内网连接。

## 5. S3 失败、磁盘水位与背压

### 5.1 初始阈值

以下使用率阈值是 planned 的初始设计值，当前没有启用按 70%/80%/90% 水位自动治理。已有实现依赖 command/state/history/queue 上限及真实 I/O 失败拒绝；恢复与控制记录的绝对空间预留尚未实现。未来使用率阈值也不能替代绝对剩余空间条件。

| 状态 | 初始触发线 | 服务动作 |
| --- | --- | --- |
| 正常 | 低于 70% 且归档延迟处于预算内 | 正常流量；保持空间和归档趋势监测 |
| 告警 | 70% | 告警；预测达到停写线的时间；定位热点库、归档或 compaction 停滞 |
| 限流 | 80% | 减少写入准入与大型事务；限制新冷唤醒；按租户配额隔离热点；保留恢复能力 |
| 停用户写 | 90%，或绝对预留不足 | 拒绝新的用户写事务；读仅在数据及强一致屏障可用时继续；尽量完成已受理事务和归档 |
| 无安全空间 | 无法保证已受理事务 / Raft 控制记录的持久化 | 停止相关持久化确认，不再声称可正常服务；人工恢复容量 |

预留必须覆盖：最大允许事务、已受理未完成事务、Raft 元数据及 owner / 授权撤销 fencing 记录、GC 发布记录、成员变更、快照/compaction 的临时重叠空间、副本追赶及恢复开销。90% 只停止新的用户写，仍应利用预留完成这些安全控制动作；若绝对预留不足，必须提前阻塞用户写。单纯“剩余 10%”不能保证这些需求。接入实现时，应以空间预算公式和上限配置约束事务准入，不等发生 `ENOSPC` 再保护。实际 fsync 失败的副本须退出投票及正常服务，不能仅报警后继续运行。

恢复到较低水位且观察到归档持续追赶后，才逐步放开写入；使用滞回避免反复停启。每个 cell 是独立背压域，单租户速率/容量限制先于 cell 全体停写。不能为了腾空间牺牲该 cell 的已确认事务。

### 5.2 允许截断日志或删除对象的条件

当前仅实现经完整状态覆盖的 Raft Checkpoint 和受 exact archive 覆盖的单库 Prune；不删除任何 S3 对象。下面的历史引用、PITR/DR pin 与 GC 删除任务属于启用回收前的 planned 合同。

删除候选必须同时满足：

1. 替代的快照及所需 segments 已上传，完整性校验通过。
2. 指向它们的 manifest 已在所属 cell Raft 提交，且恢复链连续覆盖目标位置。
3. 当前活动库、历史 incarnation、PITR 保留窗口、备份 pin、克隆/分支引用、所有保留 DR checkpoint 及生成中 checkpoint 的持久 pin 均不再需要被删对象。完成 checkpoint 的状态机快照、未归档 tail、来源证明和全部引用对象属于同一保留闭包。
4. Raft 日志裁剪仍可让落后/新建副本安全追赶；不能删除仅存在于这些日志中的已提交 payload。
5. 删除任务具有可审计候选集，执行前再次校验引用与发布版本，避免发布/删除竞态。
6. 不是依靠墙钟或对象文件名推测“足够老”。

## 6. 文件损坏、数据错误与灾难恢复的区别

表中按库 PITR、删除恢复、成员重建和区域 DR 是目标运维路径，当前没有这些通用管理工具。当前可自动完成的是从仍然有效的 cell 权威重建 SQLite cache/owner；权威介质损坏或永久失去多数派必须保持失败。

| 问题 | 正确处理 | 不应采用 |
| --- | --- | --- |
| worker 文件被截断、磁盘丢失 | 隔离本地副本，从相同已提交历史重建；正常 failover 不改变业务时间线 | 自动恢复到昨天的快照并宣称无数据损失 |
| 单 Raft 副本损坏 | 保留证据，从健康 quorum 重建副本 | 先删除所有副本再初始化 |
| 用户误删记录 / 错误 UPDATE | 在隔离的新运行代恢复到明确历史位置，校验后按库切换或导出补偿 | 切主；复制会忠实保留错误写入 |
| 用户误删整个逻辑库 | 在 tombstone/保留策略允许的条件下恢复到新的 incarnation，显式处理凭证和旧请求 | 复用旧 incarnation，让旧 writer 自动重新连入 |
| 区域全部介质不可恢复 | 人工声明灾难，仅从完成态 DR checkpoint 取得 cell 身份、tombstone、已接受 manifest 和数据 tail，报告缺口后恢复新集群 | 自动 force reset、独立挑选零散 manifest，或把最后一次 S3 LIST 中的对象视为完整最新状态 |

仅剩 S3 时，必须按 [存储生命周期 §11.1](../architecture/storage-lifecycle.md) 验证完成态 DR checkpoint。当前 cell 全部损毁后，不能仅从普通数据 manifest 证明它曾被 Raft 接受；更新但不在所选完成 checkpoint 中的零散对象，不自动推进恢复点。

常规故障处理见 [运维手册](runbooks.md)。任何改变恢复时间点、删除保留数据或接受归档缺口的动作，都必须留有操作者、批准者、恢复边界和影响范围的审计记录。

版本升级须同时遵守 [ADR-0014](../adr/0014-sqlite-service-and-cold-lifecycle.md)：新状态写入 v2，合法 v1 热历史仅在相同身份/limits 下兼容读取；无旧 binary 降级或混版本滚动协议。服务可部署与完整生产 SLO/故障矩阵通过是不同结论。
