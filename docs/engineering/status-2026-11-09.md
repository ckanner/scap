# 2026-11-09：SQLite on S3 实施状态

## 目标与判断

目标仍是 **S3 为唯一持久权威、计算和本地 SQLite 镜像可全部丢弃的多租户数据库服务**。
目标工作负载是大量独立、低活跃比例的用户或工作区数据库，允许有界冷启动。
单库事务由同一 HEAD 的条件发布排序；扩容计算节点不会自动提高一个热点库的写入率。
完整阶段与退出条件继续由[主方案](../architecture/object-storage-native-proposal.md)
和[机器合同](../../contracts/design-contract.json)约束。

方案已落到正式 Rust/native/S3/HTTP/SDK 代码，不能再按“只有设计文档”描述。
同时，安全物理回收、PITR、完整资源预算、真实 AWS 和生产 SLO 尚未闭合，
不能按“整个目标已经完成”描述。

## 本轮修复了什么

### 超时后的工作不能提前退款

原来的 HTTP 生命周期结束并不证明后台 Job 已经结束。现在在鉴权后、读 body 前，
原子预留全局与 `(deployment, tenant)` 的请求数量和原始 body 额度。
额度绑定原 principal、真实 admission class 和一次 Job，跟随排队、实际执行、
响应 body 及最后的 Bytes clone/slice。超时、断连和丢弃接收者都不授权重放 SQL。

data、control、recovery、catalogue 各自保留池。不同 principal 共享同 tenant 配额，
拒绝的 tenant 不进入无限增长的 map，零使用条目回收。完整 body 读取结束后才缩减
未使用的原始字节预留，不能在仍有副本存活时提前退款。

### 小 wire 结果也可能占用大量 typed 内存

NULL、小值、短行和列名的内存不等于编码后的字节数。共享结果预算现在计入
`Vec` 容器、实际 capacity、String/Blob payload 及扩容时旧、新缓冲重叠，
在分配前检查并使用可失败分配。默认一次 typed materialization 为 128 MiB。
native 编码后明确释放旧 graph，再进行 publication 后的 decode。

历史结果格式有效但当前预算不足时，保留原 receipt，返回已提交但结果暂不可用；
不能将本地内存不足标成权威数据损坏，也不能重复执行原 SQL。
这个预算仍是一次物化的预算，不是跨 actor 的存活字节租约或进程 RSS 上限。

### 未认证连接也有边界

HTTP/1 accept loop 在创建连接任务前检查上限，完成但尚未 join 的任务仍计数。
header 数量、总字节、解析缓冲和原始读取 deadline 分别受限；保持显式 HTTP/1，
不因共享依赖启用了 HTTP/2 feature 就扩大入站协议范围。
默认连接数 128、header 数 64、header 字节 16 KiB、解析缓冲 32 KiB、header deadline 5 秒。

这不替代 body 预算，也不在同一个 listener 上给 control 保证独立 TCP 槽位。
慢响应仍可能延长优雅关闭；必须根据部署需求另行冻结强制关闭及 UNKNOWN 合同。

### 路由不授予提交权，超时不授予重放权

`RoutedClient` 先取得 fresh status，只能选择静态可信 worker registry 中的地址，
整个调用使用一个绝对 deadline，最多发送一次业务 SQL。FENCED/UNKNOWN 后保留
原 request，用 lookup/cancel 查证，不自动换地址重试执行。

`OwnerClient` 需要 READ+ADMIN，使用固定原观察、目标 worker、revision 和 nonce。
新意图只有一次进程内 dispatch 能力，保存并恢复的意图只能检查。
显式协调至多做一次 takeover 和一次 activation；原响应丢失不能生成新的接管身份。
更换明确配置的只读 bootstrap 可以检查原意图，但不能改变可信 worker 地址映射。

已有 takeover/activate 接口新增可选 `expected_worker_instance`。
不匹配时在缓存路径、S3 访问和恢复之前返回 `TARGET_MISMATCH`。
这一步解决显式协调与路由；自动故障探测、抑制接管振荡和后台 controller 仍未实现。

### 每次不可变对象访问绑定原观察

`ObjectContext` 捕获原后端、完整逻辑 Scope 和共享隔离状态；建库使用明确独立的
bootstrap 路径。数据树、请求索引、保留结果以及 catalogue 恢复不再在中途通过
通用 Database 重新决定对象地址。原 Snapshot、ETag、对象上下文、request 和绝对
deadline 一起保存在一次 AttemptContext 中，贯穿准入、native publication 和 gate。

本批保持 HEAD 4、对象帧 2、字节/hash/key 和回执不变，尚未增加物理世代或 pin。
现有 publish wrapper 仍会读 manifest，维护状态不能直接复用它；PR #42 另建立
只捕获原条件的 metadata-only PreparedHead 边界。当前普通操作回收方案正在验证
世代 fence 与可中止读取，不默认依赖永久 PinAdd/Release，以避免崩溃 pin 耗尽准入。
保留快照根和当前 copy plan 仍需要独立保护；有限模型通过后才推进生产实现。

## SQLite、NFS 和 S3：解决的具体故障

[SQLite 官方网络文件系统说明](https://www.sqlite.org/useovernet.html)指出远端文件
锁、缓存和同步语义的不可靠性；[WAL 文档](https://www.sqlite.org/wal.html)要求
访问同一 WAL 数据库的进程位于同一主机。不能把多节点共享 EFS/NFS 上的 `.db/WAL`
当成可靠的数据库服务架构，也不能把所有 NFS 实现概括为必然立即损坏。

SCAP 不把 S3 挂载为 SQLite 文件系统。每个执行镜像使用私有本地 `.db/WAL/SHM`，
目录与临时目录有文件系统准入；跨节点的原子顺序来自同一 HEAD 的
[ETag 条件写](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html)。
依赖对象先条件创建并 exact GET 校验，再条件发布 HEAD，native publication 完成后
才确认。旧 owner 的原候选不能换新 ETag 重绑，网络超时不能当作撤销远端写入。

这移除了共享网络卷锁的依赖。它不修复不可靠的本地 I/O、不消除 S3/IAM/KMS 故障，
也不把本地 cache 配在 NFS/FUSE 上变成安全行为；详见[部署存储边界](../operations/sqlite-storage-safety.md)。

## native WAL-reset 核查

固定 libSQL `d8bc862` 的 native SQLite 是 3.47.0，未包含官方 WAL-reset 修复；
核查时的 libSQL main 也没有带入。当前服务每个私有新文件只有一个受控连接，
写入、查询和 checkpoint 串行，源代码判断排除了官方所述多连接竞态拓扑。
这不等于 native 已修补，也不覆盖旁路打开文件的 embedding host/sidecar。
[精确评估](../architecture/sqlite-wal-reset-assessment.md)记录版本、源码哈希、官方
补丁和升级门禁；漏洞复现与修复执行仍为 NOT_RUN。S3/hash/CAS 不能自动修复 native
已算错但字节自洽的数据。运维继续禁止任何额外连接打开活动 cache 文件。

## 单进程与吞吐：保留的约束

SQLite 并非只能服务一个进程；本项目当前选择一个 actor 串行拥有一个私有 native
连接。不同数据库可以并行，控制和冷恢复有独立准入；同库发布仍是一个串行点。
同一热点库不能通过增加 pod 自动获得多 writer 吞吐。

写入已按 128 KiB chunk 和 COW 路径增量更新，请求索引也是分段树。
串行关键路径仍含执行、不可变依赖 PUT/readback、HEAD CAS、native publication
和本地 checkpoint。普通强读每次 fresh HEAD；冷恢复仍下载完整闭包并做结构检查。
不能把单元耗时、本地兼容后端延迟或历史容量验收当成 AWS 生产 TPS/p99。

本轮 1 GiB 复验中，三次点更新分别产生 24、27、27 次对象请求，PUT 字节为
292,764、424,287、313,440；完整冷恢复仍需 8,338 次 GET、约 1.084 GB GET 字节。
这证明该固定负载下增量写入已生效，也直接显示请求放大和整库冷恢复仍需优化。

Turso 的 [libSQL bottomless](https://github.com/tursodatabase/libsql/blob/main/bottomless/README.md)
异步备份、[Cloud 对象持久化](https://turso.tech/blog/how-does-the-turso-cloud-keep-your-data-durable-and-safe)
和[新 Rust 引擎 MVCC](https://turso.tech/blog/turso-0.8.0)是不同组件。
可借鉴分块缓存、对象持久化后确认和批量日志；不把其专有 Cloud 协议、另一引擎的
并发能力或 S3 Express One Zone 故障域当成 SCAP 已有能力。
本轮另固定上游 commit，检查了 `DurableStorage` 的提交前持久化挂点和 bottomless
的批次/上传/任务生命周期；具体源码与取舍见[SQLite/S3/Turso 复核](../architecture/sqlite-s3-turso-review.md)。
