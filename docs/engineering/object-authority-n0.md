# N0：对象权威协议的有界可执行模型

- 日期：2026-11-05。
- 基线：[ADR-0020](../adr/0020-object-storage-native-authority.md)与[完整方案](../architecture/object-storage-native-proposal.md)。
- 本次交付：明确的逻辑身份、发布/查询/取消/接管/退休语义、有限模型、独立历史判定器和可重复探索。
- 状态：本地模型门禁通过，证据见下文。模型不是 S3 adapter、SQLite 引擎、服务或 SDK；不表示整个 N0 已退出，更不表示 N1–N4 已完成。

## 1. 目标及证据边界

目标架构以对象中的单库 HEAD 为权威。本轮先验证竞争与故障发生时，哪个状态可以生效、什么结果可对调用方确定，以及旧身份为什么不会再次被接受。模型使用离散状态和有界合成值，不执行 SQL，也不调用云服务。

模型的 `Store` 只提供按键对象和 ETag 条件替换。业务校验发生在可信协议的候选构造阶段；模型不能让存储替服务拒绝旧 owner、错误权限或非法数据库转换，否则会把真正需要实现的协议误算成 S3 的能力。对象上传成功和 HEAD 发布成功是两个步骤，应用响应也是后续独立步骤。

[AWS 条件写文档](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html)描述 `If-Match` / `If-None-Match` 与条件冲突；[一致性文档](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Welcome.html#ConsistencyModel)描述按键读写一致性。查询日期为 2026-11-05。这里将正确实现的条件替换抽象为单个线性化动作，**这个抽象及本地模型结果不能证明实际账号、region、IAM、KMS、SDK 或云端满足运行要求**。真实端点属于 N1 独立门禁。

不从 LIST 推导最新 HEAD，不把 ETag 解释为业务序号或内容摘要，不删除并重建 HEAD，不恢复旧 HEAD bytes。所有合法转换必须推进单调 metadata revision，并产生不可复用的完整 transition identity。模型编码为 `scope + (new_metadata_revision:operation_nonce)`，genesis 为独立特例；本地句柄释放后可以复用 nonce，但不能复用原版本和完整身份，也无需永久保存所有已使用 nonce。模型将不同合法 HEAD 的比较令牌视为无碰撞；真实适配器须从同一次 GET 取得 body/ETag，正确编码条件，并对内容使用独立摘要校验。

## 2. 冻结的逻辑身份与回执

| 身份 | 内容和用途 |
| --- | --- |
| Authority scope | deployment、tenant、database、incarnation、authority generation；不可用名称或缓存路径替代，不复用旧运行代 |
| Request identity | scope、request epoch、request ID、原主体、规范业务指纹；发出前由调用方保存，所有 UNKNOWN 查证沿用原值 |
| Owner identity | owner epoch、worker instance、Recovering/Active；调度、墙钟和路由不是写权 |
| Conditional attempt | 原 HEAD body/ETag、原 transition ID、不可变候选和依赖；任何重发仍是同一尝试，不能只换新 ETag |
| Control intent | 原 scope、expected metadata revision、control ID 与规范控制意图；UNKNOWN 后不能把同 ID 配上新的 expected revision 当重试 |
| Commit receipt | scope、request identity、db sequence、transition ID、数据/结果摘要；不使用伪造的 Raft term/index |
| Cancel receipt | scope、request identity、已发布取消转换的 metadata revision / transition ID；没有成功发布就没有确定取消 |

每次查询与候选构造都检查当前 HEAD 的权限。结果查证及取消还必须匹配可信调用者与原主体，不能让另一个有 READ/WRITE 权限的主体冒用原请求身份。当前权限撤销不抹除既有业务效果，但可以阻止继续获取原结果。

控制结果若已被后续转换覆盖且没有保留精确证明，只能报告无法确定的原结果或原 expected revision 已被越过，不伪造原控制操作成功/取消。新的协调任务须有独立的新意图，不能藏在对原 UNKNOWN 的 retry 函数中。模型不依赖进程内永久 seen-ID 集合维持这一点，重开后的旧控制意图仍受原版本栅栏约束。

最新控制查证还比较 HEAD 中完整 ControlIntent 的摘要，不能仅看到相同 control ID 就把不同参数、主体或动作报告为 applied。下一转换可以覆盖这一个有界证明，不生成永久行政日志；原客户端仍须保留自己的完整意图。候选发布前后使用同一封存内容；对外观察返回独立副本，不让调用者修改已校验的快照或候选来增加授权。

本轮固定的是逻辑语义。正式字节编码、最大 HEAD 字节数、索引分段/深度、引擎 envelope、具体 HTTP schema 与 SDK 持久化接口仍须在 N1 实现前冻结并验证；当前模型展开的结果表是逻辑索引的观察形式，不是把所有结果内联进 HEAD 的线上格式。

模型中的主体和业务指纹是可信准入已验证/规范化之后的符号。它验证同一身份的绑定及冲突，未实现凭据验证、SQL/参数规范化或真实 engine 指纹；实际用户不能自报可信主体、控制角色或摘要来绕过这些入口。

## 3. 发布、失败与查证

候选绑定它实际执行所依据的数据根、owner、auth 和请求接受范围。先上传并校验完整数据/结果依赖，再尝试 HEAD CAS；数据根和原结果索引由同一转换生效。控制转换不增加 SQL sequence，成功业务转换增加 sequence，即使业务内容没有变化也必须原子保存原结果。

| 观察 | 可得结论 |
| --- | --- |
| 已 stage，或部分/全部依赖上传 | 尚不能确认业务提交；只能成为未发布对象 |
| CAS 明确成功 | 权威已提交；之后的本地发布失败不能撤回它 |
| CAS 成功响应丢失 | 保留 UNKNOWN，通过原身份读取权威；不能重跑业务 |
| 本次条件不匹配 | 本次条件替换没有发生；同请求之前的在途尝试仍可能已经提交 |
| 当前 epoch Lookup absent | UNKNOWN；旧 CAS 可能尚未到达，不能宣称取消 |
| 已发布的取消记录 | 确定 cancelled；迟到原提交被原 ETag 和请求终态阻止 |
| closed 但保留的 epoch 中 absent | `EPOCH_CLOSED`，该身份不能再新接受；不制造取消回执 |
| 已退休的 epoch | `RESULT_EXPIRED_OR_RETIRED`；不判断原请求成功、取消或从未接受 |
| 权威不可达或恢复依赖缺失/损坏 | 失败关闭；不返回旧缓存、不创建空库、不推定业务未提交 |

模型将 CAS 响应、native materialization 和业务 reply 分开。只有已发布且完成本地物化的成功路径可以产生业务成功响应；请求成功响应丢失后，原权威结果仍可在保留合同内查证。全计算状态丢失只清除候选、缓存和本地执行状态，不能清除对象中的已发布数据或控制状态。

## 4. 提交、取消与控制竞争

Commit 与 ResolveOrCancel 可以同时从同一 HEAD 构造候选；条件替换决定顺序。取消先成功时旧提交失效；提交先成功时取消必须读取原提交结果。任何一路响应丢失都保留原身份和 UNKNOWN，不自动重新生成业务 ID。

接管由 HEAD CAS 推进 owner epoch 并进入 Recovering，保持数据、结果和权限。恢复完成后重新核对权威，再单独 CAS Active。恢复前准备的旧写候选不能通过更新 ETag 获得新资格；接管期间也不能提前接受正常业务。权限、维护、删除与提交使用同一 HEAD 序列，竞争时只有合法直接后继成功。

强读在调用期间选择新鲜 HEAD，检查当前 READ 权限并固定完整数据根。之后发生的权限撤销可以排在读快照准入之后；新的读请求必须重新准入。模型不实现生产 pin/GC，读取安全仅在对象不被物理删除的假设下成立；N3 必须补充受保护根与 GC 竞争。

本轮 Maintenance 是阻止新业务提交的逻辑门控，动作表如下；它**不是 N3 的 GC 冻结协议**。后续如引入物理删除，须扩展 gc generation、pin 和恢复保护，不能直接沿用这里允许维护期读取的条件。

| 动作 | Ready | Maintenance | Deleted |
| --- | --- | --- | --- |
| Commit、Takeover、Activate / Recover | 校验各自 owner/权限/前序后可执行 | 拒绝 | 拒绝 |
| Strong read、Lookup | 校验当前权限与完整根 | 同样校验后允许 | 拒绝 |
| Cancel | 校验原身份、当前权限和容量 | 同样校验后允许 | 拒绝 |
| Auth、Maintenance、Delete 控制 | 当前 ADMIN 与固定控制意图 | 同样校验后允许 | 拒绝新转换 |
| Close | 可信协调器、原版本和满窗口 | 同样校验后允许 | 拒绝 |

## 5. 本轮选择的结果留存合同

本轮用**完成的世代数量**定义最低留存，避免在模型中引入未经证明的分布式时钟。它是新目标的一个明确小规模合同，替代旧原型的逐条 ACK 与人工 ADMIN 轮转要求。它不承诺任何正的墙钟留存时长，不提供“一定能在几分钟/几天内找回结果”的 SLO；需要这样的业务合同必须另加经验证的时间条件，不能从本模型推导。

### 5.1 接受范围与自动关闭

- 候选小规模 profile：每个 current epoch 最多 **128** 条 committed/cancelled 终态；有限探索使用更小窗口并单独报告。
- 保留 **current + 最近 2 个完整 closed epochs**。全部记录共享同一个库的预算；其他主体的合法提交或取消也会消耗这些窗口。
- Close 只在 current 的终态槽位已满时允许，不允许通过空 Close 或跳号迅速退休。
- 可信协调器通过一次原 ETag / 原 expected epoch / 原 transition ID 的 CAS，关闭原接受范围、推进 current、切换保留索引并单调推进退休水位。租户不获得任意轮转接口。
- Close 是模型中的显式动作；未来 daemon 可以在满窗口时自动调度。模型并不声称真实调度器、SDK 或后台服务已经存在。

epoch `e` 在 current 为 `e`、`e+1`、`e+2` 时保留其终态；只有满额 `e+2` 关闭并进入 `e+3` 的同一次 CAS 才允许退休 `e`。因此，`e` 关闭后还要完成另外两个满窗口，才越过最低留存边界；历史 128 条计数 profile 对应另外 256 条终态，探索的 2 条 profile 对应另外 4 条。当前 v2 运行时还采用结果字节预算，可能在达到条数上限前关闭；该模型没有证明按字节或按墙钟的最低留存时间，运行时合同以 [ADR-0022](../adr/0022-production-capacity.md) 为准。多个窗口可以快速完成，甚至在原业务响应到达前退休；客户端必须接受该明确边界。

这个留存 profile 必须绑定创建时的 authority 配置，新实例重开不得把窗口或保留代数改小。上述可查证保障还要求同一 authority identity、未 Deleted、调用者仍有当前权限，以及权威与依赖可达且完整。撤权或删除返回明确的权限/生命周期错误，不泄露结果、不冒充 cancelled 或 retired；本轮删除只发布 tombstone 并保留原闭包，不执行数据物理删除。

### 5.2 满窗口取消与 UNKNOWN

当 current 已满，不能为了容纳一个 absent 请求的取消而挤掉原结果，也不能把它移入新 epoch。此时拒绝新记录并保留 UNKNOWN；协调器的 Close 与旧 CAS 排序后，原身份可以通过新的权威查询得到保留终态或 `EPOCH_CLOSED`。退休后只返回退休状态，不能伪造 cancelled。

Close/取消也需要实际元数据和对象资源。模型的对象总预算耗尽时允许明确背压，禁止以提前退休或隐式成功来解锁。N1 在实现编码和 I/O 时必须给接受、取消、确认/关闭及恢复建立真实预算与预留证明；本轮没有以模型计数代替 bytes、线程或网络配额。

### 5.3 客户端责任与存储边界

调用方在发出业务前保存完整身份，结果超出合同后以业务键、outbox 或外部订单号对账。`RESULT_EXPIRED_OR_RETIRED` 不授权 SDK 自动发起新业务。显式 ACK 可作为未来提前释放的可选协议，本轮没有实现第二套回收路径。

退休只释放逻辑结果索引的当前引用；业务效果继续属于数据库状态，退休屏障永久防止旧请求再执行。**模型禁止物理对象删除，达到对象总预算时停写。** 有限逻辑索引不等于对象容量或成本收敛；pin、compaction、GC、PITR 与跨运行代恢复仍属于独立 N3 工作。

## 6. 可执行验证与独立判定

[模型目录](../../experiments/object-authority-model/README.md)包含协议模型、场景探索和原始事件判定器。判定器不得导入被测候选构造或以它的返回值作为正确性证明；应从原始 HEAD 序列、对象、请求观察、成功响应和恢复结果重建约束。

最低验证包括：同 ETag 竞争和条件失败、两种提交/取消胜序、absent 之后迟到的 CAS、依赖上传与响应切点、接管/权限/维护/删除、请求指纹和主体隔离、新鲜读、满窗口关闭、两个 closed 窗口的保留、退休后迟到身份、全部计算丢失、缺失/损坏恢复对象。

判定器必须拒绝人为破坏的轨迹，包括提前成功、旧 writer 接受、数据与结果分离、缺依赖、给旧差分换新 ETag、未知结果伪装取消、空 Close 和提前退休。每次探索保留精确场景数、实际状态/转换数、完整失败与枚举边界。有限枚举不是无界证明，也不把一组预定并发场景表述为探索了全部可能协议状态。

## 7. 进入下一阶段的条件

本轮完成后可以把经过模型检验的语义作为 N1 的输入，仍须关闭以下门禁：正式 codec 和精确字节预算；真实 AWS 条件对象合同；生产 authority 与 SQLite precommit gate 的同实现接线；真实 SDK/多进程响应丢失及全计算丢失恢复；生产代码逐文件精确覆盖。

N0 的模型结果、原 Raft 的单元与故障结果、真实对象端点测试和性能/成本样本分开报告。PR17 的旧架构控制回收及其故障诊断没有被作为这里的先决条件或通过证据。没有运行真实 AWS / SQLite 的部分保持未验证，不把本地模型称为可上线服务。
