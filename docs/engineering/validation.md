# 验证规范与发布门禁

> 状态：测试设计，尚未执行。本文列出需要建设的测试框架、故障注入、oracle 和准入证据，不代表已实现的测试集，更不代表性能或 RPO / RTO 承诺。只有附带版本、环境、命令/入口、原始证据和结果的报告才能标记为通过。

## 1. 验证目标

验证对象是完整服务语义：Node.js 客户端、Gateway、Rust worker / libSQL、cell Raft、目录/调度、认证、S3 归档、恢复和 GC。只测试 SQLite SQL 正确性或 Raft 单元测试不能证明整个系统具备高可用。

v0 需要证明：

1. 单 worker / 单 AZ 故障不丢失客户端已经收到成功的事务。
2. epoch / incarnation 与事务提交在同一个 cell Raft 组排序，任何旧 writer 都不能绕过该排序。
3. staged WAL 不会提前可见，读屏障防止旧 owner 提供伪“最新”数据。
4. 结果未知的事务在有界幂等保证内不会因重试而重复提交。
5. 异步归档和 GC 不破坏活动恢复、PITR、旧运行代保留及副本追赶。
6. 控制面分区、鉴权源失联、S3 失败、磁盘满时按规范拒绝或降级，而不是静默降低安全性。
7. 高租户基数、冷唤醒风暴和热点库不会绕过配额、覆盖错误库或产生无界元数据/日志积压。

对应的处置行为见 [故障矩阵](../operations/failure-matrix.md) 和 [运维手册](../operations/runbooks.md)。

性能阈值与计时口径以 [性能与恢复目标](performance-slo.md) 为准；单元测试范围和准确测量规则以 [可测试架构与覆盖率](testability-and-coverage.md) 为准。三类证据独立：100% 单元覆盖率、真实正确性/故障验证、性能验收不能互相替代，当前均不得仅凭设计文档声明通过。

## 2. 测试环境与可复现记录

### 2.1 环境层级

| 层级 | 用途 | 必须具备 |
| --- | --- | --- |
| 状态机 / 模型 | 穷举关键顺序和验证不变量 | commit、owner、incarnation、manifest/GC、幂等状态的可控模型 |
| 单进程确定性模拟 | 高频复现崩溃点、重排和响应丢失 | 可控制时钟、I/O、网络与随机种子；重放相同 seed |
| 多进程集成 | 校验真正的 RPC、持久化和恢复路径 | 三个 Raft 副本、至少两个 worker/Gateway、etcd、S3 接口测试端 |
| 三故障域环境 | 验证单 AZ、分区和调度容量 | 明确节点/AZ 映射及反亲和，磁盘故障与网络隔离能力 |
| 灰度环境 | 验证真实 SDK、工作负载与运维流程 | 合成 tenant、真实连接池、容量/权限限制、可回收数据 |

本地三个容器不是三个 AZ；杀进程不能模拟断电后持久化丢失；mock 的 fsync 成功也不能证明实际存储兑现持久化。各层结果必须说明能证明和不能证明的范围。

### 2.2 每次运行必须保存

- commit SHA、依赖锁定文件、libSQL 版本及补丁、构建模式、配置摘要和所有格式版本。
- 基础设施、磁盘类型、fsync 策略、网络延迟/丢包模型、三个副本的故障域及 S3 实现。
- 测试种子、负载模型、库数量、活跃比例、事务大小、并发度、数据规模及测试持续时间。
- 客户端调用/返回历史、已确认写账本、超时/未知请求、cell 提交和 owner 历史、归档/manifest 记录。
- 故障注入时间线、恢复动作、oracle 输出、原始失败样例及缩减后的最小复现。
- 明确结果为通过、失败、未执行或不适用；没有输出不能解释为通过。

测试日志不应包含真实客户数据、token 或密钥。失败证据须在清理环境前保全。测试环境只能使用可销毁合成数据，不能用生产故障注入替代前置验证。

### 2.3 100% 单元测试覆盖率门禁

第一方生产代码要求 **单元行覆盖率 100%、单元函数覆盖率 100%、单元分支覆盖率 100%**，按实际整数计数判定，不依赖显示值四舍五入。Rust 分支必须由准确的覆盖报告实测；工具无法正确测量则标记 `TOOLING_BLOCKED` 并阻断，不用 region 或行覆盖率替代。各语言、构建配置及生产入口/适配器/异常路径的范围遵守 [覆盖率合同](testability-and-coverage.md)。

单元报告只使用单元测试执行记录，集成、故障注入和人工运行不能补进分子。没有某语言生产代码时记录 `NO_PRODUCTION_CODE` / `NOT_APPLICABLE`；有代码却零分母、文件遗漏或 profile 缺失则失败，不能记成 100%。为达到门禁应重构纯决策与副作用边界、注入时间/I/O/调度依赖，不能排除难测生产代码或删除必要保护逻辑。覆盖率达标仍不代表穷尽状态组合、并发顺序或真实持久化故障。

## 3. 独立安全性 oracle

oracle 应独立于被测服务的成功计数和内部日志；系统自己说“已成功”不是唯一证据。客户端应向独立的测试记录器记录 invocation、response、请求 ID、tenant/库/运行代、摘要与序号；记录器故障时运行结果应标记证据不完整。

### O-01：ACK 保留与原子提交

维护客户端已收到成功的事务集合 `A`。事务在测试表中写入唯一 ID，并在一次事务内更新多行不变量，例如余额守恒和审计行。

- 单 worker、单副本、单 AZ 故障恢复后，集合 `A` 中每个效果必须恰好保留一次且原子完整。
- 未返回成功的事务允许存在或不存在，但必须与查询到的确定结果一致，不能出现半个事务。
- 将“恢复后表行数相同”作为证据不充分；必须核对 ID、内容摘要和业务不变量。
- 在所有节点重启后重复检查，以识别仅在内存中可见、没有真正 fsync 的伪持久化。
- 区域灾难恢复另行按明确归档边界评估，不套用单 AZ RPO 0 判据。

### O-02：线性化与事务语义

对标准强读和单库事务生成并发读写历史，检查是否存在遵守真实时间顺序的合法串行解释。已返回成功的写之后发起的强读，不能无理由读到该写之前的状态。

数据库事务内部的快照、锁冲突和隔离语义应按选定 libSQL/SQLite 模式另行定义；不能把单语句线性化测试当作所有多语句事务行为的证明。跨库原子事务不在 v0 保证范围，测试不得隐含依赖。

必须覆盖读取旧 owner、本地文件、只达少数派的 Gateway、leader 刚切换和 worker 尚未重放完毕等路径。oracle 不使用各节点墙钟直接排列因果关系，应以客户端调用/响应关系及受控记录为准。

### O-03：旧 writer 与运行代

记录 cell Raft 中 owner 变更、epoch、incarnation 及 commit 的全序。对于任一事务：

- 若它在新 epoch 生效之前已合法提交，即使响应稍后到达也可成功；oracle 不能误判为旧 writer 越权。
- 若旧 epoch 的事务在新 epoch 生效后才进入提交判定，必须被拒绝。
- 删除/恢复之后，旧 incarnation 的事务、连接、快照上传和 GC 任务不能修改新 incarnation。
- etcd 中存在旧路由或旧租约时，上述约束仍成立。

该 oracle 必须检查存储实际结果及权威序号，不能仅检查错误码字符串。

### O-04：幂等与结果未知

同一有效幂等键加相同请求摘要在并发、超时和跨重启重试中最多产生一个业务效果，并返回同一确定结果。相同键不同摘要必须冲突。

结果记录必须与事务提交在同一权威提交边界绑定；注入崩溃验证不存在“数据已提交、幂等记录还没写入”造成的重复窗口。键的保留期、数据库运行代变化和记录过期必须具有可辨识结果；记录不在不能被自动解释为未提交。

无幂等键的未知写入不允许网关或 SDK 自动重放。只对安全的只读请求和明确未受理的请求测试自动重试。

### O-05：归档、manifest 与 GC

构建独立引用图：活动运行代、manifest、快照、segments、PITR 窗口、备份 pin、克隆引用、副本恢复需求、保留的完成态 DR checkpoint 和生成中 checkpoint 的持久 pin。每个 checkpoint 的来源证明、状态机快照、未归档 tail 及全部引用对象形成受保护闭包。

- 任何已发布恢复点必须形成连续且摘要一致的可恢复链。
- 对象上传但 manifest 未提交时，不得让它替代恢复基线，也不能据此删除旧日志。
- GC 后，引用图中所有受保留约束的位置仍须实际恢复成功。
- Raft 日志裁剪后，新副本和落后副本仍能安全追赶，不能只证明当前 leader 可读。
- 删除/发布/恢复并发时，不得出现短暂“无引用”误删仍被任务使用的数据。
- 生成 DR checkpoint 时先建立持久 pin，完成清单产生后引用闭包继续受保留策略保护；中途崩溃、取消或换版不能提前释放数据。并发 GC 不得删除生成中或保留中的 checkpoint 所需对象。

这个 oracle 需要实际读回并恢复对象；只检查对象名或 manifest JSON 格式不充分。仅剩 S3 的独立恢复只能从 [存储生命周期 §11.1](../architecture/storage-lifecycle.md) 的完成态 DR checkpoint 开始；其中的 cell 状态确定曾接受的 manifest、身份、tombstone 和 tail。更“新”的零散对象不能改变恢复点。

### O-06：PITR 与按库隔离

为每库生成可预测历史，在目标位置前后写入标记。恢复后，目标以前应包含的事务存在，目标以后的事务不存在，事务不可部分恢复。其他 tenant/库的状态和恢复位置不变。

逻辑误删恢复应生成新 incarnation，旧 owner 与旧请求必须失效；物理 worker 文件损坏重建则应保留原业务历史，不能悄悄回退到某个历史时间点。

### O-07：cold wake 与暂停安全性

对同一冷库并发发起唤醒，只能产生一个有效可写 owner。ready 前必须恢复到权威要求的位置并通过读屏障。旧快照、滞后目录、重复启动任务不得覆盖新状态。

暂停前后已确认事务都保留；未提交 staged tail 不得成为唤醒后的数据。对刚暂停、暂停中、新写到达、暂停响应丢失、worker 再次上线分别注入竞争。

分别验证两种动作：**Suspend** 在 cell 完整持久化 head 和未归档 tail 后，可以封存并释放 worker，不等待 S3；**fullyCold** 进一步卸载持久热数据，必须具备完整归档及 GC 证明。注入 S3 故障时，前者仍可完成且重新唤醒保留 ACK，后者不得提前删除 tail。不能以“worker 数量为零”证明数据已经安全全冷。

### O-08：授权与租户隔离

交叉使用 tenant、数据库 ID、连接、token、幂等键和内部授权证明，验证不发生越权读写或状态泄露。路由缓存命中不能代替权限缓存或 cell 的 db_id/incarnation/epoch 校验。鉴权源故障时，正向授权缓存最长 60 秒且不晚于 token 到期；即使 JWT 仍有效也不得越过新鲜度上限；命中不续期，进程重启不复活过期缓存。

验证已打开连接仍受操作准入和 leader 提案前检查，已到达撤销事件立即使缓存失效，新权限和管理动作不会被缓存放行。TTL / token expiry 仅在这两个准入阶段检查；确定性 `apply` 不得使用各副本墙钟产生不同接受结果。已经接受的提交不因 token 随后到期被撤销。

验证 cell auth_epoch / fence 与事务条目的同组有序判定；撤销前合法接受的事务保留，撤销后携带旧授权的提交被拒绝，不能只在 Gateway 测试撤销。模拟仅部分 cell 可达，报告未覆盖范围而不声称即时全域撤销。时间回退或时钟状态不可信不能延长准入授权。

## 5. SQL、事务与 Node.js 接入兼容性

具体 SDK 支持范围以仓库接口规范为准。验证必须使用实际声明支持的 Node.js 驱动/SDK，而不只使用内部 RPC 测试客户端。

必需用例：

- 参数绑定、NULL/BLOB/整数精度、Unicode、批量语句、错误码与错误对象、插入 ID、受影响行数。
- 显式事务、自动提交、事务内读己之写、回滚、约束冲突、繁忙/锁等待、取消与超时。
- prepared statement 在连接重建和 owner 迁移后的生命周期；不能假设旧会话句柄仍有效。
- schema 迁移与普通写并发，数据库升级后旧连接行为，动态扩展/PRAGMA 的允许和禁止范围。
- 事务中断后的未知提交语义、原幂等键重试、不同请求复用键、保留期过期。
- 连接池大量 idle 连接、进程重启、网关切换、冷启动超时预算，以及不会无限创建每租户连接池。

SQLite 文件 API、SQL 方言、C API 和远程 SDK 是不同兼容层；只通过 SQL 用例不能宣称原生文件驱动零改动可用。需要记录每种接入方式的实际限制和所需业务改动。

## 6. 性能、规模与资源隔离实验

性能数据必须与安全性 oracle 同时运行。关闭 fsync、减少 quorum、跳过鉴权/归档或无限保留内存得到的数字不能作为生产性能结果。

[性能与恢复目标](performance-slo.md) 给出参考硬件、网络/磁盘预检、数据量、负载和初始数值：热强读端到端 p95/p99 为 20/50 ms，小写为 50/100 ms；writer 故障 R0（≤1 GiB、有效恢复带宽 ≥100 MiB/s、tail ≤64 MiB）为 20/30 秒，R1/R2 为 8/15 秒和 5/10 秒。它们都是待验证目标；R1/R2 仅为 G4 拟实现的缓存/热备选项，不能把未实现保护算作已有性能。

### 6.1 必测维度

| 维度 | 变化因素 | 记录内容 |
| --- | --- | --- |
| 租户基数 | 库总量、活跃比例、每库大小、保留历史 | 目录、调度、Raft 状态、manifest、缓存的固定内存/磁盘成本 |
| 事务 | 小写、批量写、最大允许事务、读写比例 | quorum fsync 延迟、排队、apply 延迟、成功/拒绝/未知率 |
| 单 cell 共享 Raft | 热点库比例、活跃库数、事务大小偏斜 | head-of-line 阻塞、公平性、跨库尾延迟、控制记录预留能力 |
| 冷唤醒 | 缓存命中、快照大小、增量链长度、并发唤醒 | 排队、调度、对象读取、重放、ready 各阶段 p50/p95/p99 |
| 归档 | S3 时延、吞吐、错误率、PUT/GET 成本 | 归档积压、完整可恢复位置滞后、磁盘压力 |
| 故障恢复 | 数据量、日志 tail、剩余 AZ 容量 | 检测、栅栏、重建、重连阶段的实测 RTO |
| 隔离 | 单租户 CPU/内存/IO/连接耗尽 | 其他 tenant 的延迟、拒绝率、正确性和恢复能力 |
| 生命周期 | 批量建库、休眠、删除、保留期 GC | 元数据增长、任务积压、空闲成本和可回收空间 |

### 6.2 必须报告的测量口径

- 写延迟从客户端首次发起计时，客户端排队和有界重试均计入；分别报告服务端时间、确定成功、超时、UNKNOWN 和完整分母，不能只统计幸存成功请求或 worker SQL 时间。
- RTO 从故障发生到后续连续 30 秒稳定窗口的起点，窗口结束才确认；第一次成功单列 `T_first_success`，不能只测 Pod 重启时长。
- 常规归档滞后以连续已发布恢复位置衡量；S3-only 灾难 RPO 则以最后完整完成态 DR checkpoint 可恢复位置和已确认历史比较，不只用最后一次对象上传或某个 manifest 时间。
- 冷唤醒含排队和缓存未命中，明确是否提前预热。
- 峰值吞吐需同时报告错误率、未知率和 p99；不把被拒请求从分母中消失。
- 固定成本包括 Gateway、控制面、etcd、三个 Raft 副本、监控以及对象请求；库休眠不代表平台零成本。

初始磁盘阈值 70% / 80% / 90% 必须在最大事务、归档停顿、compaction 重叠和追赶场景验证。若绝对空间余量不足，应降低阈值或提高预留，不能为达吞吐目标推迟停写。

每种故障类型、恢复档位和大小至少 100 次独立样本，正式 p99 建议至少 1,000 次主要场景样本；报告置信范围、最大值、超标和删失数。保留带宽跌落、缓存失效及未恢复事件，不能事故后降档或删除慢样本。初始故障基准使用 500 请求/秒、50/50 读写及最多 100 个受影响库，逐库读写探针包含在总负载；具体稳定窗口和安全容量定义遵守性能文档。

## 7. 恢复与运维演练

每个计划运维能力在实现后必须有可审计演练：

1. worker 磁盘丢失后恢复相同已提交历史。
2. 单 AZ 退出，恢复 quorum 冗余及 worker 容量。
3. 失去 quorum 时保持停写并修复原集群，不触发自动强开。
4. S3 故障持续到限流与停写，修复后安全追赶并恢复流量。
5. etcd 从备份恢复后，先与 cell 对账，再开放调度。
6. 误删单库，在新 incarnation 校验并切换，其他库不受影响。
7. 在无原 cell、etcd、缓存及原对象索引的干净环境，仅以 S3 和受控恢复所需密钥/配置，从完成态 DR checkpoint 恢复，准确报告损失/未知范围；单独覆盖上传半途损毁和权限/密钥缺失。
8. manifest/GC 竞态及误删模拟，证明保留 checkpoint、生成中持久 pin 和完整引用闭包的保护有效。
9. 升级中途发生另一个节点故障，发布自动暂停，仍保有安全性。

演练报告必须注明使用的计划接口哪些已经实现、哪些由人工模拟。依赖人工修改内部文件才能通过的流程不得标为“自动故障恢复通过”。

## 8. 发布门禁与证据

阶段编号与 [实施路线](roadmap.md) 一致。以下是各阶段的验证出口，不是可互换的测试分组。

所有包含第一方生产代码的阶段均执行第 2.3 节的 100% 单元行/函数/分支门禁，单元覆盖与对应真实契约/故障证据同时满足才可进入下一阶段；不存在用集成覆盖补齐单元缺口的例外。

### G0：关键 WAL / SDK / store 可行性

- staged WAL 的生成、可见性、quorum 持久化、apply 与 ACK 边界明确。
- 使用锁定版本的真实 libSQL WAL 适配原型，验证提交前暂存/拒绝/确认、页恢复、DDL/savepoint/回滚和 I/O 错误；未证明该边界不能进入生产 HA 实现。
- 真实 Node.js SDK 兼容性与所选 Raft store / snapshot 持久化契约完成可行性验证；明确版本、许可证及备选 Go / No-Go 条件。
- tenant / 库 / incarnation / epoch / auth_epoch / 幂等键身份及错误语义明确。
- Raft payload 足以恢复事务，不能只是指向不可靠 worker 文件的引用。
- 鉴权降级、日志裁剪、manifest 发布及 GC 条件有确定规范。
- 单 cell 共享 Raft 的资源上限与控制记录预留策略明确。

### G1：一个可靠 cell

- 三副本日志、持久状态机、owner fencing、提交与强读屏障实现并验证；O-01 到 O-04 通过相关多进程故障测试。
- 全进程重启、断电模型和 fsync 错误模型通过；没有未解释的 ACK 丢失或旧 writer 提交。
- 线性化反例必须清零；不能以“极低概率”豁免数据正确性失败。
- auth_epoch 的有序状态机判定不依赖副本墙钟；未知提交结果不会重复接受。

### G2：多库、入口、权限、目录与调度

- 多库 Gateway、会话与错误语义、权限缓存、目录、调度和资源配额实现；跨 tenant 身份混用和资源耗尽测试通过。
- O-08 及控制面失效场景通过；认证失联和 CP 网络分区遵守 60 秒权限新鲜度与同 cell auth_epoch 边界。
- 目录缓存不形成写权，重复调度不形成两个有效 owner；响应丢失的控制任务可按原任务 ID 查询。
- 多库连接池、未知结果、幂等窗口过期和运行代变化有真实 SDK 可观察行为。

### G3：对象、冷库、PITR、DR 与 GC

- 快照、增量、manifest 发布、对象 GC、冷唤醒、PITR 与 DR checkpoint 实现；O-05 到 O-07 有实际恢复证据。
- 独立干净环境的 S3-only 恢复必须通过 F-28：不依赖原 cell/etcd/缓存/索引，从完成态 checkpoint 恢复曾提交 manifest、身份、tombstone 和未归档 tail。
- F-31 / F-32 覆盖 checkpoint 上传半途损毁、未完成发布、缺对象、缺授权材料或验证/解密 key；失败必须清晰，不得恢复成空库或绕过权限。
- F-21 及相关崩溃点覆盖 checkpoint 生成/保留和 GC races；保留 checkpoint 及生成中持久 pin 的完整闭包不可被提前回收。
- Suspend 不依赖 S3 完成归档；fullyCold 只有在完整归档及 GC 证明成立后卸载持久热数据，F-33 必须通过。
- PITR 单库切换与副本追赶通过，其他库不受影响；所有对象操作失败都不破坏已确认历史。

### G4：试运行、运营、HA 容量与滚动升级

- 三故障域环境通过单 AZ 及网络分区测试；成员变更、冗余恢复和滚动升级中再遇故障的行为已演练。
- 磁盘水位和绝对预留在最坏允许负载下有效；冗余降级时能停止发布。
- 按性能文档的初始目标验证 RTO、读写延迟、冷唤醒和安全容量，报告全部失败/UNKNOWN、未满足目标与完整平台成本；真实业务兼容与连接池行为有报告。
- R1/R2 只是 G4 拟实现选项，只有预备副本协议、跨 AZ 接管余量及相应故障样本通过后才可开放；未实现时只声明实际具备并验证的恢复档位。
- 从小范围、合成或低风险 tenant 开始，具备明确定义的回滚与停止条件。
- 运维手册的必要管理能力已实现且经过演练。
- 所有数据格式和混合版本窗口有兼容矩阵，首次不可逆写格式有单独批准门禁。
- 安全性失败、恢复链破坏、未知归属的 writer 或鉴权越界立即停止扩大灰度。
