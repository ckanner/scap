固定为 `fd508cc052c21dba0e3c54b8e8e82d11c167777a`，基线为

**当前结论：**两组实际配对均确认三个写入阶段合计少 160 个 Manifest GET，其他

## 1. 变化与不变量

原路径在生成新 Manifest 时已经 exact GET 或条件创建并完整回读，发布 HEAD 前又
读取同一不可变 Manifest。新路径将第一次验证封装为不可克隆的私有证明，在原操作
中消费，省去第二次读取。它不改变普通 query/read 或管理发布。

证明继续绑定原 ObjectContext、backend／handle lineage、Scope／物理世代、输入和
输出根、页数、原 deadline，以及原 HEAD body／ETag。配额、健康、格式、状态转换、
原条件 CAS、原结果和 native publication 顺序均保留；UNKNOWN 不重放 SQL，也不
刷新 ETag 继续旧候选。完整设计见
[原候选设计](https://github.com/ckanner/scap/blob/fd508cc052c21dba0e3c54b8e8e82d11c167777a/docs/architecture/verified-manifest-publication.md)。

生产改动仅位于 `crates/scap-object/src/{data_tree,object_context,lib}.rs`。它不是同库
MVCC、group commit、lazy VFS、异步 ACK、跨节点活动 WAL 或新恢复协议。

## 3. 请求数结果

以下计数在两组中分别重复出现，按每个候选的一次完整测量阶段统计：

| 场景 | 调用数 | 全部 S3 请求：基线 → 候选 | S3 请求／调用：基线 → 候选 | 少出的 Manifest GET |
| --- | ---: | ---: | ---: | ---: |
| 单库写，C1 | 32 | 593 → 561 | 18.531 → 17.531 | 32 |
| 单库写，C4 | 64 | 1,267 → 1,203 | 19.797 → 18.797 | 64 |
| 四库写，C4 | 64 | 1,152 → 1,088 | 18 → 17 | 64 |
| 单库暖读，C4 | 64 | 64 → 64 | 1 → 1 | 0 |
| 四库暖读，C4 | 64 | 64 → 64 | 1 → 1 | 0 |

补充分类器仅在原 oracle 和完整 controls 成功之后读取原 S3 账本。它逐 request_serial
配对请求／响应，要求原 phase、method、path 和请求描述一致，再核对对象 key、原
字节 SHA、SCAPOBJ2 长度和 payload kind；各阶段的方法总数回对原 oracle。

数据块、树节点、请求索引、原结果及 HEAD 的 GET／PUT 次数全部未变。普通暖读
仍每次读取新的 HEAD，未缓存授权或跳过强读。

这是五个 phase 的聚合分类证明，原 oracle 的逐 HTTP 区间绑定为 `NOT_REQUESTED`。
它与“每次新 execute 的发布路径省一次 GET”的代码设计相符，但不构成并发情况下
每个 execute 的单独运行时归属证明，也不把全程 S3 总数差额扩展为全部 185 个
execute 的逐类型证明。

四库写的单请求 p95，第一组为 534.341 → 710.359 ms，反向组为

四次独立实际的原结果核对、32 MiB 冷恢复、全部所需控制套件均成功。正确性通过、

## 5. 已查到的新增成本与下一步

静态审查确认 `publication_matches` 会重新计算原 HEAD 的完整序列化和 SHA-256；
ObjectContext 创建时本来已经计算过一次。证明还新增两份 64 字符根字符串的复制。
这是可定位的新增工作，但减少的 GET 同时省去对象读取、哈希和 Manifest 解码，
因此尚未测出净 CPU 或净分配变化，不能仅据静态差异解释约 24% 的下降。

原 `objects.healthy()`、`publish_healthy()` 与 `Knowledge::blocked` 的锁调用次数没有
增加，`PreparedHead::new` 的校验与候选序列化也原来就存在。backend、lineage、原
HEAD、Scope、generation 和 deadline 绑定不能为了更漂亮的数字删除。

对四份原代理账本的补充只读分析发现，本轮实际 HEAD wire body 为 759–769 bytes，
不能拿格式允许的最大 HEAD 大小代替真实样本估算指纹成本。四库写阶段的代理
request→response 区间如下。它从代理 request 事件计时至 response 事件，包含随后
日志、转发／后端及响应 body 保存，不覆盖前置接收、请求 body 落盘和签名字段解析。
这不是完整代理处理耗时、产品发送耗时或独立测量的 S3 服务时间：

| 实际 | 对象请求数 | p50（ms） | p95（ms） | p99（ms） | 最大值（ms） |
| --- | ---: | ---: | ---: | ---: | ---: |
| 第一组基线 | 1,152 | 7.870 | 19.076 | 26.402 | 90.839 |
| 第一组候选 | 1,088 | 10.378 | 24.282 | 37.231 | 127.907 |
| 反向组基线 | 1,152 | 7.056 | 17.974 | 27.782 | 76.037 |
| 反向组候选 | 1,088 | 8.533 | 22.039 | 67.984 | 595.172 |

候选中观测到的对象区间也更长，仍不足以分辨产品 CPU／调度、代理取证或后端的
贡献。该分析只读完整账本并核对原 SHA，没有产生第五次 actual；并发区间不能
相加作为端到端墙钟或因果占比。记录及脚本身份附在同一配对机器证据中。

下一步冻结一次有界 profile，回答以下问题，而不是继续重复小样本 TPS：

1. 产品进程中，完整 HEAD 指纹、serde、SHA-256、字符串／缓冲区分配各占多少
   CPU 与分配字节；同时记录真实 HEAD 大小和成功新 execute 分母。
2. SQL/native、数据树与索引更新、HEAD 验证、对象等待、native publication 和服务
   队列等待如何分布；采样身份必须绑定实际正式进程与二进制。
3. 多库并行时的 allocator／既有锁等待，与 Python proxy 请求检查、证据写盘、后端
   认证和宿主调度如何区分。该 proxy 只检查并记录签名字段形状／hash，完整 SigV4
   认证由后端执行。代理时钟区间不能直接称为纯 S3 延迟，并行区间之和不能当墙钟。
4. profile 自身与原计时验收分开。若数据支持修改证明表示或减少分配，新实现必须
   保留全部原绑定反例和实际正确性合同，再做独立冻结的性能验收。

产品 CPU／分配／等待 profile、真实 AWS、开环持续负载和生产 SLO 目前均未运行。
严格逐文件 branch 覆盖还有独立的测量阻断。PR #60 保持 Draft，已验证的请求数
减少和未排除的吞吐回退同时呈现；完整云端成本没有在本地实验中测量。
