## 确认的缺口

`Envelope::validate` 检查 Result 的身份、序号、摘要字段和字节数；`decode_object` 检查对象内容摘要和外层 framing。它们不解析内部 `SCAPRES1`，这是格式层的职责划分。

原 `Database::resolve_entry` 在这些检查通过后直接返回 `Committed { receipt, bytes }`。`lookup`、`cancel` 和 `verify_results` 复用该路径。后者统计精确结果字节数，但不会验证字节是否是完整合法的 SQL 结果。因此，一个身份和摘要均正确、内部结果编码非法的持久对象，可以通过旧的恢复闭包检查。原 `admit` 的历史事务重试会完整解码，因此已经拒绝该数据，但其他入口不一致。

测试必须让 Result/Index 的新摘要及 HEAD 引用全部正确，否则只是重复已有的外层摘要损坏测试。该场景不声称 SHA-256 碰撞，也不声称普通篡改可绕过哈希。

## 候选实现

新增正式 `scap_sql::validate_result`，共用既有 Decoder 的有界游标，检查：

- 精确版本、语句/列/全事务行数和结果字节预算。
- 列名及 Text 的 UTF-8、每值字节预算、已知类型标签。
- Integer 的完整 8 字节、Real 的有限值约束、完整尾部字段。
- 零列非零行、任意截断和多余尾字节。

该函数不构造 TransactionResult、String、Blob 或行集合，不重新编码原结果。请求或结果格式、零语句合法空结果、整数范围、负零、原 receipt 和原始结果字节保持不变。辅助空间只保留解析游标和计数；这不代表整个对象读取路径没有分配，也不提供进程级 RSS 或并发资源隔离。

`resolve_entry` 在外层身份/提交位置绑定之后、构造成功解析结果之前调用该检查，使用固定 `durable_sql_limits()`。不能使用当前本地的 SQL 准入预算：调低新请求限额不能使历史合法结果失效。

历史重试需要返回 typed 结果时仍经过独立的防御性 materialization helper，直接输入的坏字节也必须拒绝；两个解析入口都保留自己的单元合同。

任何内部编码错误映射为已存在的 `Error::Corrupt` 并经过 `observe`。这使同一 handle 和 clone 记住故障，阻止后续 HEAD 发布；不自动改写 HEAD、删除对象、激活旧版本、重放 SQL 或清空隔离状态。它不是跨 worker 的持久隔离协议，不能撤回已发出的 CAS。当前已验证快照的只读行为保持原合同。

`lookup`、针对已有提交的 `cancel`、冷激活、会话恢复和首次写的历史校验因此采用同一结果合法性判断。发现损坏不等于原事务未提交；不得据此重新分配请求 ID 自动重试。
