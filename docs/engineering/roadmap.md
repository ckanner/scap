# 实施路线与发布门禁

状态：G0 原型进行中。没有以日历时间替代验证结果，尚未实现可部署数据库服务。当前执行证据见 [g0-evidence.md](g0-evidence.md)。

## 1. 原则

先验证最可能推翻架构的接口与故障边界，再扩展控制面和规模。客户端演示成功、容器能够重启、正常情况下三副本数据相同，都不足以证明高可用。

任一阶段未达到持久性门禁，产物只能标为实验或备份恢复原型，不能对外承诺本仓库的严格 HA。改变产品保障范围须记录新的 ADR 和维护者决定，不能在实现中静默降级。

## 2. 阶段计划

| 阶段 | 交付 | 进入下一阶段的条件 |
| --- | --- | --- |
| G0：关键可行性 | 锁定依赖、libSQL WAL 原型、真实 SDK 兼容、存储契约验证 | 能在提交可见前暂存/拒绝/确认；页恢复正确；依赖许可和版本明确 |
| G1：一个可靠 cell | 三副本日志、持久状态机、owner fencing、提交与读屏障 | 故障注入证明 ACK 保留、旧写者拒绝、未知结果不重复接受 |
| G2：多库与平台入口 | Gateway、权限、目录、调度、多库配额、会话与错误语义 | 跨租户权限与资源测试通过；控制面失效行为符合合同 |
| G3：对象与生命周期 | 快照、增量、发布、GC、冷唤醒、PITR、DR checkpoint | 在干净环境恢复成功；任意上传/发布/删除点崩溃不破坏恢复链 |
| G4：试运行与运营 | 跨 AZ、升级、成员变更、容量、告警、演练、成本报告 | 实际业务兼容和 SLO 测量完成，所有阻断缺陷关闭 |

这些门禁与 [验证计划](validation.md) 同名阶段对应。可以并行开发独立模块，但不能绕过依赖门禁进入生产。

## 3. G0 的具体工作

所有生产代码遵守 [100% 单元覆盖率与可测架构](testability-and-coverage.md)，每个阶段同时核查 [性能与恢复目标](performance-slo.md) 的适用部分。当前窄提交策略和真实 WAL 探针已开始执行；OpenRaft 持久存储、完整事务暂存、SDK 返回边界等尚未完成，不能将部分探针通过视为 G0 整体通过。

### 3.1 引擎适配

固定 libSQL commit、SQLite compile options、page size、目标平台和 WAL 接口。验证普通事务、DDL、savepoint、回滚、checkpoint、数据库增长/截断、取消、I/O 错误及模拟 quorum 失败。

最重要的验收是：在 cell 未接受前，另一个读连接绝不能观察到成功提交；cell 接受但 worker 退出后，恢复必须得到同一结果。普通 `wal_hook` 不能作为该证明。

### 3.2 持久化适配

实现最小 OpenRaft storage adapter，运行上游契约测试和进程 / 存储故障测试。明确 RocksDB WriteBatch、sync、vote、last-applied、snapshot、log purge 的一致性关系。

### 3.3 客户端与备选基线

跑一套真实 Node.js 应用：`@libsql/client`、选定 ORM、可选 `libsql` 同步兼容包。记录实际改动，而不是只运行 `SELECT 1`。

对 dqlite 的现成同步复制、原生 SQLite + Litestream 的备份恢复分别做对照，验证自研存算分离带来的收益与复杂度。它们是技术对照，不改变正式 HA 合同。

### 3.4 Go / No-Go

如果 WAL 接口不能安全控制可见性，或持久存储契约无法证明，停止扩展产品功能，重新选择底座。可选择缩小兼容范围、集中维护引擎 patch，或重评已有复制引擎；不得在提交后上传数据来假装满足门禁。

## 4. G1–G3 的实现顺序

1. 不依赖 S3 的最小可靠 cell：短期保留全部已提交事务数据，先证明提交、读和换 owner。
2. 加入每库元数据和索引，验证大量数据库身份不会导致无限进程 / 文件句柄 / CF。
3. 统一入口、鉴权、幂等状态查询、明确错误和事务会话。
4. 引入对象归档；最开始不自动 GC，以独立恢复演练验证完整性。
5. 开启受控 GC、休眠和删除；每一步引入新的故障点测试。
6. 最后加入跨 cell 离线迁移、滚动升级和灾难恢复自动化。

禁止从一开始同时实现所有优化：按页远读、多写者、跨库事务、跨区同步、跨库对象打包、无限事务分块均留待后续 ADR。

## 5. 仓库开发顺序

第一批可运行代码进入仓库时，新增 Rust workspace、固定 toolchain、锁文件和许可证清单；随后按 [目录规划](repository-layout.md) 建立模块。TypeScript workspace 仅在 SDK / examples 开发时加入并锁定包管理器与依赖。

当前已建立无外部依赖的 Rust 核心 workspace、固定工具链和独立引擎实验 workspace，CI 分开执行单元覆盖率、工具检查与引擎探针。其余模块按实际实现建立，不创建会让人误以为数据库可运行的空服务、假 Docker Compose 或无实现 API stub。

## 6. 试运行标准

- 用非关键租户或可重放数据验证，但与生产使用同一持久化模式。
- 每次试运行产出构建标识、配置、原始指标、故障时间线和数据库不变量检查结果。
- 首次对外 SLA 来源于测量和演练，而不是设计文档中的期望。
- 回滚计划必须考虑磁盘 / 日志格式；不支持格式回退时采用恢复迁移，而非直接运行旧二进制。
- 关键正确性缺陷阻断发布；性能不达标先限额和缩小范围，不更改已确认写入保障。
