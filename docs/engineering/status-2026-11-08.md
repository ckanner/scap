## 目标与已交付能力

目标是 S3 作为唯一持久权威的多租户 SQLite 服务：计算节点、本地镜像和路由缓存均可丢弃；确认写入由不可变依赖、每库 HEAD 条件发布及 native publication 共同保证；客户端保存原意图，在未知结果时查证或取消。它适合大量独立数据库，单库仍按同一 HEAD 串行发布。无需为每个库维持独立持久计算实例，不等于一个热点库的写吞吐可以随 pod 数增加。

正式能力包括 Rust authority、签名 S3 adapter、固定 libSQL 提交 gate、增量 128 KiB 数据块/树、配额、原始结果留存、权限/owner/lifecycle、认证 HTTP、Node SDK、精确名称目录和有界数据库 actor。本批新增有界 deployment/tenant 枚举、带主体绑定 cursor 的 HTTP/SDK、无需预知数据库名单的全数据恢复，以及不可变分段请求索引。在线分页不承诺跨 key 快照，元数据枚举结束不代表数据恢复完成。

## SQLite/NFS 与吞吐

SCAP 不让多个节点打开同一份网络卷上的 `.db`/WAL/SHM。它通过对象条件更新协调发布，从协议上移除了共享网络文件锁这一依赖。本地 SQLite 镜像仍必须使用可信本地存储；打开描述符的文件系统准入拒绝网络/FUSE/未知类型，本批还检查 SQLite 固定 Unix VFS 的全部已存在临时目录候选及 host-global override。部署仍须固定 mount namespace、环境、cwd 和默认 VFS，并保证可信 overlay 的底层语义。S3 CAS 不能修复已被错误本地 I/O 污染的候选数据，详见[执行存储边界](../operations/sqlite-storage-safety.md)。

一个 actor 的私有连接由一个线程串行拥有；不同数据库独立并行。增加计算节点不改变单库 HEAD 的串行发布点。分段索引用于降低请求元数据随留存窗口增长的放大；后续批量提交必须另行证明 ACK、取消、UNKNOWN 和公平性，不能直接照搬其他引擎的 TPS 数字。

Turso 的新 Rust 引擎、旧 libSQL/bottomless 和新的 Cloud server 是不同组件。公开分段缓存、对象持久化后确认和合批设计可作参考；新 Cloud server 没有公开完整协调协议，不能作为本仓库协议或性能的直接证明。官方对照见[主方案 §3.4](../architecture/object-storage-native-proposal.md)。

## 正在推进的下一批

自动 owner 协调已经形成独立核心/HTTP/SDK 候选：可信配置的 controller、只读 owner 观察、有限次显式接管/激活，以及不重放 SQL 的路由策略；真实多进程故障合同仍在完成。单库暖 Session 与冷恢复分别约束，控制 UNKNOWN 不得变成重新接管的借口。

独立 storage generation/head serial 候选已完成 184 次真实 native 调用和独立历史审计，证明旧存储 PUT 暂停时切换仍可推进，释放后原 HEAD CAS 拒绝旧候选。该增量没有删除对象。下一步补共享 Runtime 的有界 pin、冻结和 drain；暂停进程的 pin、旧创建流程及迟到上传均必须进入回收证明，不能靠 TTL 猜测其死亡。

后续按[全目录发现方案](../architecture/catalogue-discovery-plan.md)与[持续存储方案](../architecture/storage-reclamation-plan.md)推进，每个生产文件保持四维精确单元覆盖，真实 HTTP/S3/native 合同单列。AWS 配置与资源未提供，相关真实云端门禁标为 NOT_RUN，不创建未经配置的付费资源。
