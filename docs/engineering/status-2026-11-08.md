## 目标与已交付能力

目标是 S3 作为唯一持久权威的多租户 SQLite 服务：计算节点、本地镜像和路由缓存均可丢弃；确认写入由不可变依赖、每库 HEAD 条件发布及 native publication 共同保证；客户端保存原意图，在未知结果时查证或取消。它适合大量独立数据库，单库仍按同一 HEAD 串行发布。无需为每个库维持独立持久计算实例，不等于一个热点库的写吞吐可以随 pod 数增加。

已交付正式 Rust authority、签名 S3 adapter、固定 libSQL 提交 gate、增量 128 KiB 数据块/树、配额、原始结果留存、权限/owner/lifecycle、认证 HTTP、Node SDK、精确名称目录和有界数据库 actor。已完成的本地合同包含原生故障、UNKNOWN、迟到候选、全计算缓存丢失、名称删除/重用及指定冷热隔离。

## SQLite/NFS 与吞吐

SCAP 不让多个节点打开同一份网络卷上的 `.db`/WAL/SHM。它通过对象条件更新协调发布，从协议上移除了共享网络文件锁这一依赖。本地 SQLite 镜像仍必须使用可信本地存储；现有打开描述符的文件系统准入拒绝网络/FUSE/未知类型，overlay 底层和 SQLite 其他临时目录仍需要部署约束。S3 CAS 不能修复已经被错误本地 I/O 污染的候选数据，详见[执行存储边界](../operations/sqlite-storage-safety.md)。

一个 actor 的私有连接由一个线程串行拥有；不同数据库独立并行。增加计算节点不改变单库 HEAD 的串行发布点。分段索引用于降低请求元数据随留存窗口增长的放大；后续批量提交必须另行证明 ACK、取消、UNKNOWN 和公平性，不能直接照搬其他引擎的 TPS 数字。

Turso 的新 Rust 引擎、旧 libSQL/bottomless 和新的 Cloud server 是不同组件。公开分段缓存、对象持久化后确认和合批设计可作参考；新 Cloud server 没有公开完整协调协议，不能作为本仓库协议或性能的直接证明。官方对照见[主方案 §3.4](../architecture/object-storage-native-proposal.md)。
