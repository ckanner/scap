# 性能指标、恢复目标与验收方法

> **新目标路线：**本文数值对应 Raft 原型参考档，不能直接继承给对象原生架构。新方案须按[性能与成本计划](<../architecture/object-storage-native-proposal.md#cost>)在实验前冻结自己的 profile 和目标；沿用完整分母及稳定恢复窗口的方法，不沿用未测结论。

> 状态：**生产参考档的内部验收目标尚未达标，也不是对外 SLA；已有单机小库诊断观测，见末节。** 本文给出可以阻断发布的目标数值与测试条件；不能将“目标已定义”写成“性能已达到”。目标修改须记录版本、原因和原始结果，不能通过删掉慢样本或缩小分母让结果通过。

本文遵守 [需求与故障合同](../architecture/requirements.md)、[一致性协议](../architecture/consistency.md) 和 [存储生命周期](../architecture/storage-lifecycle.md)：三 AZ 的共享三副本 cell、durable quorum 后接受写入、单 owner、CP、S3 异步归档不变。性能优化不得绕过这些条件。

## 1. 首批验收目标

以下目标只适用于第 3 节参考环境、第 4 节明确负载及已经锁定的数据库大小/恢复档位。数值是工程预算和验收出口，不是上游组件或云厂商的现成性能。

### 1.1 热请求与内部可用性

| 指标 | 初始 p95 目标 | 初始 p99 目标 | 限定条件 |
| --- | --- | --- | --- |
| 热库点强读，SDK 端到端 | ≤ 20 ms | ≤ 50 ms | 已建立连接；单行索引读取；含 cell 读屏障及 worker 追赶 |
| 热库小写事务，SDK 端到端 | ≤ 50 ms | ≤ 100 ms | 一个自动提交或一次提交的 batch；物理变更 ≤ 64 KiB；含 durable quorum、状态机接受和本地发布 |
| 热库点强读，服务端 | ≤ 15 ms | ≤ 35 ms | Gateway 收到完整请求至交出完整响应；排队与内部 RPC 全部计入 |
| 热库小写事务，服务端 | ≤ 40 ms | ≤ 80 ms | 同上；不能只报告 libSQL 执行时间 |
| 热库首次连接并完成点强读 | ≤ 250 ms | ≤ 500 ms | 同区域客户端；包含 DNS/TLS/鉴权；不包含库唤醒 |
| 内部请求可用性 | 30 天滚动窗口 ≥ 99.9% | 不适用 | 合法且在已分配配额内的请求，在约定 deadline 前取得确定、正确的结果；定义见第 2 节 |

写事务的默认热路径基准 deadline 为 **2 秒**。读请求使用相同 deadline 以便比较；50/100 ms 是分位延迟目标，2 秒是该基准的请求终止边界，二者不能混用。首批真实业务若需要其他 deadline，须作为独立负载档报告。

长查询、大结果、大事务、DDL、交互事务中的用户停顿、跨区域客户端、首次对象恢复不属于上面“小请求”分位目标。它们必须另行测量、设置执行预算和公平队列，不能被默默合并或从总可用性中移除。

### 1.2 故障后恢复

| 故障与恢复档位 | 初始 RTO p95 | 初始 RTO p99 | 恢复前提 |
| --- | --- | --- | --- |
| 单 worker / 计算节点失效，R0 经济档，库 ≤ 1 GiB | ≤ 20 s | ≤ 30 s | 完整恢复；有效恢复带宽 ≥ 100 MiB/s；待重放 tail ≤ 64 MiB；可读恢复基线与剩余容量正常 |
| 同类故障，R1 完整文件预置缓存档 | ≤ 8 s | ≤ 15 s | 其他 AZ 已有经校验的完整本地文件；追赶差距 ≤ 64 MiB；无需下载完整基线 |
| 同类故障，R2 热备执行档 | ≤ 5 s | ≤ 10 s | 其他 AZ 有预分配执行槽及有效完整副本；追赶差距 ≤ 16 MiB；短时追赶和激活即可 |
| 单 Raft leader 进程失效，worker 正常 | ≤ 2 s | ≤ 5 s | 另外两个 voter 健康、可持久化且形成 quorum；不同时搬迁 worker |
| 单 AZ 故障，受影响库均配置 R2 | ≤ 10 s | ≤ 20 s | 剩余两 AZ 的 cell、入口、目录/调度及授权依赖可恢复；全部受影响库有幸存热备和容量 |

R0/R1/R2 都是**拟实现恢复等级**。默认完整恢复架构对应 R0；R1/R2 需要额外的缓存/热备维护协议、资源和测试，不能只配置一个名称就获得目标。

**无 quorum 不承诺可写或强读可用，也不为了达到 RTO 目标切到旧 S3 状态。** 控制面无法完成 owner 编排、恢复链缺失、权限无法新鲜验证等故障应按既有合同拒绝；其等待时间仍进入实际事故恢复时间与总可用性记录。不能在报表中删除这些失败，只因其超出了上述单故障性能档的适用条件。

### 1.3 计划冷唤醒

| 完整数据库大小 | 唤醒任务完成 p95 | 唤醒任务完成 p99 | 限定条件 |
| --- | --- | --- | --- |
| ≤ 256 MiB | ≤ 8 s | ≤ 15 s | R0、单库恢复、有效恢复带宽 ≥ 100 MiB/s、tail ≤ 64 MiB |
| ≤ 1 GiB | ≤ 15 s | ≤ 25 s | 同上 |
| ≤ 10 GiB | ≤ 120 s | ≤ 180 s | 同上，tail ≤ 256 MiB；完整下载/校验/应用路径 |
| > 10 GiB | 逐库测量并单独准入 | 不给固定秒数 | 按实际数据量、对象数、增量链、带宽及执行恢复成本制定目标 |

唤醒任务时间从平台接受唤醒请求开始，包含任务排队、owner claim、恢复和激活；SQL 首次请求的端到端时间另记。请求因唤醒超过自身 deadline 而返回超时或 `WAKING`，**该请求仍是本次可用性失败**，不能因为后台稍后 ready 就改记为成功。需要长等待的客户应显式预热或使用约定的异步唤醒流程；不能给默认第三方 SDK 暗中加入无限等待或不安全写重试。

## 2. SLI、SLO、SLA 与计时边界

### 2.1 指标定义

| 名称 | 定义 | 不应混淆的值 |
| --- | --- | --- |
| SLI | 从真实请求、故障注入和恢复证据计算出的观测量 | 设计表格中的愿望值 |
| 内部 SLO / 验收目标 | 约定条件下需要达到的阈值；未达标则阻断相应档位发布 | 已经测得的性能或商业赔付承诺 |
| 对外 SLA | 发布后对客户的正式承诺及适用边界，另行制定 | 本文初始内部 99.9% 和 RTO 数字 |
| SDK 端到端延迟 | 单调时钟记录的 SDK 调用开始至最终确定结果；含客户端排队、连接建立、网络、服务端排队和有界重试 | 只计算 SQL 执行或最后一次重试 |
| 逻辑请求尝试延迟 | 开环负载计划发起时刻至本次结果/超时；客户端排队也算等待 | 客户端终于有空发出请求以后才开始计时 |
| 服务端延迟 | Gateway 收到完整请求至完整响应交给传输层；含限流排队、鉴权、路由、内部 RPC、读屏障/持久提交和结果处理 | 仅 worker 或 Raft 某一段耗时 |
| 提交确认延迟 | 从客户端提交操作发起到确定成功返回；对显式事务同时记录整个事务时长 | 向 Raft 发出 proposal 的时间 |
| `T_first_success` | 故障后第一次正确请求成功的时刻减故障时刻 | RTO；偶发一次成功不能证明恢复稳定 |
| RTO | 从故障发生到**满足后续连续稳定窗口的起点**的时长 | 检测后才开始计时，或只记录 Pod Ready |
| 确认恢复时间 | 连续稳定窗口结束，测试系统能够确认其起点合格的时刻 | RTO 本身；确认会比起点至少晚 30 秒 |
| RPO | 故障后可恢复的已确认提交与故障前已确认历史之间的缺口 | 最后一次 PUT 成功的时间 |

### 2.2 成功、超时、拒绝和 UNKNOWN 都要有分母

每个逻辑请求有稳定测试 ID，记录 `scheduled / invoked / result / deadline` 以及每次重试。最终结果至少分为：确定成功、预期业务拒绝、平台错误、超时、结果未知 `UNKNOWN`、准入拒绝、客户端主动取消。

内部请求可用性为：

```text
可用性 = 在 deadline 内返回正确确定结果的合格逻辑请求数
       / 全部合格逻辑请求数
```

- 无效 SQL、明确越权或客户超过事先分配配额的请求单列，不属于“平台本来应成功执行”的分母；排除理由必须随请求记录，不能事后调整。
- 平台容量不足、有效配额内被限流、无 quorum、cold wake 超时、计划维护中断都算平台未满足该次请求，不能任意剔除。
- `UNKNOWN` 即使随后查证已经提交，原请求在 deadline 内没有确定结果，仍记一次可用性失败；另记“结果解析时长”和最终业务状态，不能重写原始历史。
- 有界重试成功可以成为一个逻辑请求成功，但计时必须从首次调用开始；所有物理尝试、错误和成本另计。没有稳定幂等语义的未知写不自动重放。
- 单独公布“成功请求 p99”会隐藏超时。必须同时公布全部结果数量、超时/UNKNOWN 比例及全请求 deadline 达标率。超时属于右删失样本，保留 `≥ deadline` 的事实；不能把它们当作刚好在 deadline 成功。
- 若删失比例使某个分位数无法确定，报告该分位的下界或“无法证明达标”，不要只对幸存成功请求计算一个较小 p99。

30 天 99.9% 是初始内部运营目标，需要持续窗口数据；一小时压测不能证明一个月的可用性。按库、恢复档位、cell 和区域分组报告，避免大租户的健康流量掩盖少数库长期不可用。无 quorum 时保持安全拒绝与可用性目标未达标可以同时成立。

### 2.3 RTO 的稳定恢复窗口

对故障注入用独立控制器记录真实故障时刻 `t0`；对线上事故，记录最早可证明的故障时刻及时间不确定范围，不以告警到达代替故障开始。

设 `t*` 是最早满足以下条件的窗口起点：

1. `[t*, t* + 30s]` 内，预先固定的受影响库集合全部恢复读写；每库至少每秒一个点强读和一个带稳定测试身份的小写探针，30 秒内各至少 30 个样本。
2. 探针全部在 deadline 内取得正确确定结果，无 UNKNOWN、旧 writer 成功或 ACK 丢失；同时真实基准流量满足该档延迟与请求可用性目标。
3. 强读实际通过 cell 屏障，写入实际通过 quorum 与状态机接受；不能用本地静态健康页代替。
4. 不发生再次摘流、连续路由错误、重新选主导致的中断，归档和磁盘状态没有越过安全边界。

初始故障基准最多覆盖 100 个受影响库，使用第 4 节的 500 请求/秒、50/50 读写负载，探针包含在其中。这为每秒至少 100 读和 100 写探针保留份额；不从 90/10 热基准中假定自然会出现足够写样本。更大受影响集合需增加预先定义的探针/总负载并重新验证容量。

因此：

```text
RTO = t* - t0
恢复得到确认的时刻 = t* + 30s
T_first_success 单独记录，不替代 RTO
```

例如在故障后第 4 秒开始的窗口连续 30 秒合格，则 RTO 为 4 秒，在第 34 秒才能确认。这样“RTO 5 秒目标”与“连续 30 秒验证”不冲突。窗口探测间隔造成的时间分辨率必须报告。

批量受影响场景以预先确定集合的**最后一个库进入合格窗口**为该事件的整体 RTO，同时保留每库分布。故障后不能移除最慢库或只检查一个健康 canary。探针流量纳入总负载预算，不能无意中把恢复测试翻倍加压后再忽略新增请求。

## 3. 参考环境和性能前提

这是首批可复现基准的部署规格，实际实例型号可不同，但必须记录并通过预检；不能将这些要求当作云平台已保证的指标。

| 项目 | 初始参考规格 / 条件 |
| --- | --- |
| 故障域 | 一个区域、三个 AZ；每个 cell 一个 voter/AZ；无跨区域同步路径 |
| Cell 节点 | 3 × 独占 8 vCPU、32 GiB RAM、≥ 1 TiB 本地或等价持久 SSD；显式 fsync；记录 CPU 型号、vCPU/物理核对应及存储介质 |
| Worker 节点 | 至少 3 × 8 vCPU、32 GiB RAM、≥ 1 TiB SSD，跨 AZ；活跃库分散；R1/R2 另计缓存/备槽资源 |
| Gateway | 至少 2 副本，跨 AZ；基准建议 3 × 2 vCPU、4 GiB，避免单 AZ 仅剩一个饱和入口 |
| 控制面 | 多副本 controller、3 节点 etcd；与测量中的存储 CPU/I/O 隔离；鉴权/密钥依赖健康 |
| 负载机 | 独立于被测节点，至少两台；位于不被该次故障移除的 AZ；单调时钟、足够 CPU/网络；保留原始历史 |
| 网络预检 | 客户端至 Gateway RTT p99 ≤ 2 ms；AZ 内相关 RPC RTT p99 ≤ 1 ms；AZ 间 RTT p99 ≤ 5 ms；记录带宽、重传和丢包 |
| 持久化预检 | 在基准并发与批量大小下，cell 实际持久化操作 fsync p99 ≤ 3 ms；不能关闭 WAL/sync 或用空闲磁盘数字替代工作负载 |
| 恢复吞吐预检 | 完整下载、解压、校验、落盘和应用的有效速率 ≥ 100 MiB/s/恢复任务；测量至少 1 GiB 数据；不是仅测网络 GET 速率 |
| 日志追赶预检 | 已验证物理增量的读取、应用及本地持久化 ≥ 32 MiB/s/任务；记录小事务数量造成的额外成本 |
| 对象存储 | 同区域；实际实现、请求并发和限额固定；对象摘要验证开启；不以 mock 内存 S3 得到生产性能结论 |
| 版本 | Rust/toolchain、libSQL、Node.js SDK、Raft/store、压缩与对象格式、内核和容器限制全部锁定并记录 |

100 MiB/s 是完整恢复管线的有效速率目标，包含所有数据处理，不与 GET 带宽重复计算。预检必须用真实格式、真实对象数量和真实校验；1 GiB 单一大对象的成绩不能替代大量小对象场景。

先验证环境具备所选档位的条件，再固定测试清单运行。**运行中出现慢盘、带宽跌落或恢复超标，必须保留为失败样本。** 预检不达标时，该环境不能通过这一性能档，可以另设公开更低档位；不能在故障发生后重新分类并删除慢样本。

正常准入负载应不超过第 7 节测得的安全容量的 60%。单 AZ 目标还要求负载低于两 AZ 降级状态安全容量的 60%，并预留全部失效 owner 的接管空间；三个节点正常时空闲不自动证明失去一个 AZ 后有余量。

## 4. 标准负载与测试过程

### 4.1 基础负载

| 配置 | 初始值 |
| --- | --- |
| 热基准活跃库数 | 100 个逻辑库，共享一个 cell；数据库各 1 GiB，worker 均匀放置 |
| 冷目录规模 | 另有 10,000 个 Cold 库，独立身份/manifest，基础实验每库 1 MiB；不为每库常驻 worker |
| 热工作集 | 每活跃库约 64 MiB；预热 10 分钟；说明实际缓存命中率；不把热基准写成任意随机大数据查询性能 |
| 点读 | 主键/唯一索引定位，返回一行 ≤ 1 KiB；总返回 ≤ 16 KiB；始终是强读 |
| 小写事务 | 1–4 行修改与必要索引，最终完整物理变更 ≤ 64 KiB；输出 ≤ 16 KiB；不含 DDL |
| 并发 | 开环到达；总在途上限 128；每库至多一个正在执行的写事务，其余等待计入延迟 |
| 主基准读写比 | 90% 点读 / 10% 小写；另测 50/50、写密集与单热点场景 |
| 故障恢复基准 | 500 请求/秒、50/50 读写，最多 100 个受影响库；每库 1 读/秒及 1 写/秒探针包含在总流量中 |
| 初始 offered load | 500 个逻辑请求/秒，作为第一批验收实验起点；随后逐级寻找实际安全容量 |
| 稳态时长 | 每轮预热后至少 60 分钟；至少 3 轮独立重复；持续执行归档、常规快照和必要后台任务 |
| 数据正确性 | 同时启用验证计划中的 ACK 保留、原子性、线性化和幂等 oracle |

500 请求/秒是选择的初始实验输入，**不是已经达到的吞吐，也不是所有硬件的承诺**。如果它高于实测安全容量的 60% 或不满足延迟目标，首批性能门禁未通过，应优化、增加资源或明确缩小首发容量；不能默默把负载改为更小并保留“原目标通过”的报告。

每种输入形态要记录实际物理变更字节、Raft entry 字节、fsync 次数、状态机 apply 字节和 S3 写放大；“一条 SQL”不能当作恒定负载单位。

### 4.2 必须独立报告的扩展负载

- 1、10、100、1,000 个活跃库以及不同 Cold 基数，区分每库开销和共享瓶颈。
- 单热点库占 50% 和 90% 输入，验证共享 Raft 公平排队及控制记录预留。
- 数据库 256 MiB / 1 GiB / 10 GiB，工作集超过可用内存的随机读，分别报告；大库不继承热命中结果。
- 接近事务大小上限、批量写、DDL、长只读事务、取消、SDK 首次连接和连接池重建。
- 单库并发唤醒去重与多个库同时唤醒：1、4、16、64 个请求批次；报告排队、拒绝和每库完成时间，不套用单库唤醒目标。
- 一个 AZ 失效、一个 voter 慢盘、S3 限速/中断、控制面不可达，以及滚动升级时的混合版本。

开环调度按预定时间产生请求，不等待上一个请求结束才计算下一个到达。客户端在途上限或连接池满时，仍记录原定到达和排队；无法发出的请求记为负载端容量不足或到期，不能静默丢弃。这避免系统变慢时产生更少请求，从而得到虚假的好延迟。

## 5. 写者故障恢复分级

### 5.1 R0：经济档，完整恢复

默认架构中的 worker 文件是可丢弃副本。writer 节点和本地盘同时丢失后，目标 worker 需要取得完整基线、重放 tail、验证并激活。已有合法缓存可以加速，但 R0 不假定总能找到缓存。

在顺序执行的保守模型中：

```text
RTO_R0 ≈ 检测 + 调度/排队 + owner claim/fence
       + 完整基线恢复(D, 对象数, 有效带宽)
       + tail 追赶(W, 条目数, 应用速率)
       + 激活验证 + 路由/客户端重连
```

`D` 是需要恢复的真实基线字节，`W` 是该基线之后的已接受增量。恢复步骤并行时，按实际关键路径计时，不能机械相加重复的 I/O。即便不考虑固定开销，数据传输和校验量随库大小增长，因此**完整恢复无法对任意大小数据库承诺几秒 RTO**。

例如 1 GiB 在有效速率 100 MiB/s 时，仅完整恢复管线就需要约 10.24 秒；10 GiB 对应约 102.4 秒。这是按目标速率计算的数据量下界示例，不是实测恢复结果。固定调度、tail、激活和重连时间还需另外计入。

R0 适合长尾、可接受冷启动的库。≤1 GiB 的 20/30 秒故障恢复目标要求 tail ≤64 MiB、调度容量预留、恢复基线可读取和恢复并发受控；超过大小或 tail 范围，应在故障前就明确采用更慢档位或升级保护，而不是事故时才告知。

### 5.2 R1：完整文件预置缓存档

在另一个 AZ 预置完整、版本可验证的本地数据库文件，不必常驻活跃 SQL 执行上下文。后台只追踪/应用 cell 已接受的物理变更，维护 incarnation、revision、摘要和差距；不重新执行原始 SQL。

接管前仍需 `ClaimOwner → 重新读取权威 head → 追赶/验证 → ActivateOwner`。缓存本身不授予读写权，不能根据最后一次心跳直接开放服务。目标追赶差距 ≤64 MiB；参考追赶速率 ≥32 MiB/s。

成本至少包括额外一份完整数据、复制网络、增量重放 CPU/I/O、校验及需要预留的 worker 执行空间。它降低基线下载时间，但仍有执行上下文建立、追赶和缓存验证成本，因此初始故障恢复目标为 p95 8 秒 / p99 15 秒。

### 5.3 R2：热备执行档

在不同 AZ 持续维持已准备的执行槽与完整数据库副本，追赶 cell 已接受的物理变更。初始保护条件是字节差距 ≤16 MiB，并监测时间差距目标 ≤1 秒；长事务完成后也需满足字节上限。时间差距不能替代字节/条目数量上限。

热备只是**可快速接管的副本**：它不是第二个 writer，不独立决定提交，不对外提供绕过强读屏障的读取。热备可异步追赶，正常写 ACK 仍由原 cell quorum 判定；若热备落后，正确性保持，但快速恢复保护状态降级。

接管步骤不能省略：

1. 检测故障并确认当前故障域/候选节点可达；怀疑超时只是触发条件。
2. cell quorum 接受 owner claim/fence，使旧 writer 后续提案失效；没有 quorum 则不接管。
3. claim 完成后重新取得权威 head。不能使用故障前缓存的 head，因为旧 writer 在 fencing 之前仍可能合法提交。
4. 校验 standby 的数据库身份、运行代、基线及版本，追赶到权威要求的位置；重复私有 staged 数据不能作为已接受变更。
5. 按激活协议验证 owner/head，完成可用读屏障后才能 ready，再更新路由及恢复客户端。

额外成本包括常驻执行内存、完整数据副本、持续增量应用、保留日志读取、校验和故障时的 CPU/连接容量。若活跃 worker 与热备共享机器，仍必须预留整 AZ 失效后的接管峰值；不能以日常空闲 CPU 替代明确容量预算。

R2 配置成功前必须验证保护条件。保护副本不可用或落后应立即告警、暴露降级状态并修复；若一个已声明 R2 的库在故障时发现缓存损坏/落后，计为该档故障样本未达标，不能事后改标 R0 排除。

### 5.4 分级成本和适用范围

| 档位 | 正常驻留 | 失去原 worker 的主要工作 | 额外成本方向 | 初始用途 |
| --- | --- | --- | --- | --- |
| R0 | 当前活跃 worker + 共享 cell | 完整基线恢复 + tail | 冷恢复 I/O 与等待；平时附加副本开销最低 | 默认长尾库、允许十几秒至分钟级恢复的库 |
| R1 | 另一个 AZ 的完整文件缓存 | 有限追赶 + 建立执行上下文 | 额外完整数据、网络与后台重放 | 较活跃但希望控制内存成本的库 |
| R2 | 另一个 AZ 的完整副本和执行槽 | 有限追赶 + 权威激活 | R1 成本 + 执行内存/容量预留 | 明确需要数秒 writer failover 的重要库 |

不能同时要求所有长期冷库完全卸载到 S3、无额外驻留成本，并对任意大库保证 5 秒恢复。档位属于可观察的调度与资源政策，需明确升级/降级过程；这不是改变已确认事务 RPO 0 的安全合同。

## 6. 分段恢复预算与事件观测

### 6.1 R2 单 writer 故障的初始预算

以下是用于定位瓶颈的单次关键路径预算，合计 10 秒。**不是把各段 p99 相加来证明端到端 p99**；最终仍以实际事件 RTO 分布验收。

| 阶段 | 初始预算 | 事件边界与必须完成的工作 |
| --- | --- | --- |
| 故障检测 | 1.5 s | 从 `t0` 到疑似故障确认；拟采用 250 ms 心跳、约 1 s 怀疑窗口加调度余量；误判率须另测 |
| 选择预备节点与任务协调 | 0.5 s | 选择已预分配、跨 AZ 的候选，不等待创建新 VM 或拉取大镜像 |
| owner claim / fencing | 0.5 s | 以当前数据库身份进行 quorum 提交，并得到新的确定 owner/epoch |
| 重读 head、追赶及缓存验证 | 2 s | 捕获 fencing 后的权威位置，应用最多 16 MiB 差距并完成受保护缓存验证 |
| 激活与读屏障 | 0.5 s | 权威激活成功、本地 SQL 快照对齐、读屏障通过 |
| 路由刷新、连接与首批请求 | 2 s | 旧路由失效或被拒绝，真实 SDK 重连并发起正确请求 |
| 排队抖动与预留 | 3 s | 用于可观测的少量调度/重试波动；不能隐含额外完整恢复 |

1 秒怀疑窗口不能证明旧 writer 已失效，实际 fencing 仍由 cell 决定。若误判导致高频 owner 切换，需要调高检测阈值并重新分配整体预算，不能牺牲 fencing 来保住数字。

R2 的短验证预算要求缓存已经持续完成必要校验，接管时验证身份、版本和增量覆盖。如果实现必须在每次接管时扫描整个大文件做完整校验，就不能套用该预算；需测量扫描成本、调整档位或设计经证明的增量校验机制。

### 6.2 必需事件与指标

每个故障事件、库和恢复 operation 关联以下单调时间/因果事件：

- 故障注入或故障发生区间；第一次症状；检测确认。
- 调度开始、候选选择、claim 提案、claim 被接受；旧 writer 的最后合法提交。
- Raft tick 实际调度、选举开始/结束、`Ready` 排队与持久完成、`LightReady` 处理、状态机应用和 `ReadIndex` 屏障完成。
- 权威 head 查询；基线读取、解压、校验、落盘、tail 重放各段开始/结束及字节数。
- 激活接受、路由发布、客户端重连、第一次成功和稳定窗口开始/确认。
- 不成功请求的 timeout / UNKNOWN /拒绝理由，未知事务最终解析结果。

不同节点的 trace 不能未经校时就直接相减得微秒结论。客户端端到端时长和同进程阶段使用单调时钟；跨进程分解同时记录 clock offset/误差，必要时报告区间。Raft index/revision 用于因果和安全性判断，不依赖墙钟排列提交。

按照 [ADR 0006](../adr/0006-raft-rs-consensus-library.md) 采用 `raft-rs` 不改变本文件的数值目标，也不证明单 Raft leader 故障的 p95 / p99 2 / 5 秒已经达成。记录实际 tick 周期、选举配置、runtime / 持久化队列、apply 追赶和读屏障耗时；不能把配置的 election timeout 当成用户可恢复服务的 RTO。集成正确性先按 [raft-rs 集成门禁](raft-rs-integration.md) 验证，再用真实请求测量。

## 7. 容量目标、吞吐和资源余量

### 7.1 首批容量目标

以下同样是验收目标，不是已测可扩展上限：

1. 一个 cell 管理 **10,000 个 Cold 库 + 100 个活跃库**，符合第 4 节数据模型；Cold 库不产生常驻执行实例、专用线程或专用 Raft 组。
2. 活跃库集合不变时，把 Cold 库基数从 1,000 增至 10,000，分别报告 worker、cell、Gateway、目录的增量 RAM、fd、索引和后台扫描成本；worker 不应打开这些冷库的 SQLite 文件。
3. 初始开放的 R0 恢复并发为 **每 worker 1 个、每 cell 3 个**。超过配额的任务排队并计时，不能无界争抢带宽；这些值待测后可调整。
4. 正常运行磁盘目标低于 70%；沿用 70/80/90 的待测告警、限流、停用户写水位，同时满足更严格的绝对预留。恢复临时文件、compaction 和已受理事务不可消耗控制记录预留。
5. 采用 R2 的库须有跨 AZ 预备副本及接管资源；单 AZ 故障测试中，所有受影响库都达到该档 RTO。不能只为每次被测的一个库临时预热。

per-cell 数据库数和恢复并发都是首批容量边界，达到后通过新增 cell 或调度准入扩展；不把“逻辑上可创建更多名称”当作该负载可正常运行的证据。

### 7.2 吞吐以实测安全容量确定

从 100、250、500、1,000 请求/秒等阶梯开始，之后按 20%–25% 增量逐步提高 offered load。每档保持足够时间让日志、归档和 compaction 稳定，接近瓶颈时至少持续 60 分钟。真实上限由测试决定，不在本文凭空填写某个“每节点 TPS”。

定义 `Q_safe` 为满足以下全部条件的最高已验证持续 offered load：

- 该负载形态的端到端 p95/p99、请求可用性和 deadline 目标通过。
- ACK 保留、线性化、幂等与权限 oracle 无违反。
- 提交、apply、归档、唤醒队列不持续单调积压，空间预测保持安全。
- CPU、内存、I/O 和连接有足够余量，恢复/控制命令不会被用户负载饿死。
- 至少 3 轮独立重复成立，并记录读写比例、字节量、事务大小、库数和热点分布。

对每种读写比、事务大小和热点分布，分别测 `Q_safe_healthy` 和单 AZ 降级的 `Q_safe_one_az`；90/10 的容量不能直接给 50/50 故障基准使用。需要单 AZ 目标的部署，初始生产准入上限取：

```text
Q_admission ≤ 0.6 × min(Q_safe_healthy, Q_safe_one_az)
```

0.6 是初始资源余量政策，需要与真实成本/故障数据一起调整；不等于硬件利用率在所有层都恰好 60%。若吞吐提高导致 tail、归档或 restore 队列无法受控，该点不能算安全容量，即使短时间 SQL TPS 很高。

单库仍只有一个 writer。多个库共享一组 Raft 时，大事务和热点可能让其他库排队；必须同时公布每库尾延迟、公平性、控制命令延迟及被限流比例，不能只给一个 cell 总吞吐。

多个 cell 共用存储节点时，额外测量不同 cell 的 tick 延迟、持久队列和 snapshot / compaction 干扰，验证热点或恢复流量不会饿死其他组的选举、复制与安全控制。库数量、cell 数量和节点数量分别记录，不能把 TiKV 的多组能力直接算作 SCAP 的已测容量。

## 8. 故障样本、分位数与验收方法

### 8.1 样本数量和固定测试计划

- 每种故障类型 × 恢复档位 × 数据大小至少 **100 次独立故障样本**；writer 进程退出、节点/盘丢失、Raft leader 退出、单 AZ 分别统计，不混在一起凑样本。
- 100 次只足以给出较粗的尾部分位估计。用于正式 p99 验收和后续对外目标时，建议至少 **1,000 次/主要场景**，并报告分位数置信区间、最大值及超标次数。
- 随机化故障出现相对于请求/提交的时间，也包含确定性关键边界。控制故障次数、随机种子、负载和恢复档位必须在运行前确定。
- 每次故障完成安全校验、恢复冗余及资源稳定后再注入下一次；持续故障或叠加故障单列，不能让前一次积压在报告中消失。
- 失败、人工介入、超时未恢复和证据不完整都要记录，不能只统计自动恢复成功的样本。

报告 p50/p95/p99、最大观察值、样本数、超标次数和删失数。对尚未恢复事件保留 `RTO ≥ 已观察时长`；如果数量已经无法支持 p99 达标，应判定未通过，而不是用测试终止时间填成一个有限成功值。

### 8.2 场景和期望

| 场景 | 测量重点 | 安全与性能的共同门禁 |
| --- | --- | --- |
| worker kill / node lost | R0/R1/R2 各自分段 RTO | ACK 保留；旧 writer 拒绝；claim 后 head 正确；未知提交不重复执行 |
| writer 与 cell 分区 | 多数派和少数派的请求结果 | 少数派不得成功强读写；拒绝耗时单列；不把安全拒绝当可用成功 |
| Raft leader 失效 | 选主、apply 追赶和读屏障恢复 | 真正 durable quorum；无结果回退；持久化未被关闭 |
| 单 AZ 退出 | 受影响集合的整体 RTO、降级容量 | 剩余 quorum 和资源正常；所有声明 R2 库的保护仍有效 |
| S3 缓慢 / 不可用 | 热提交、空间倒计时、cold wake 失败 | 热写只在安全持久空间内继续；不为 cold wake 跳过缺失对象 |
| S3-only DR | checkpoint 验证、重建和目录对账时间 | 只使用完成态 DR checkpoint；披露数据缺口；不套用单 AZ RPO 0 / 热备 RTO |
| CP / 鉴权失联 | 已有 owner 继续服务窗口及新调度阻塞 | 60 秒权限新鲜度、auth_epoch 有序判定；没有新鲜权限不延长服务 |
| 恢复风暴 | 排队、公平性、超时与 tail 增长 | 保留全部输入；不剔除等待任务；不在无容量时启动无限恢复 |
| 版本升级 | 连接中断、格式兼容和稳定恢复 | 升级中保有 quorum；旧版本不读取不支持格式；维护请求进入可用性分母 |

### 8.3 正确性先于速度

单 AZ 对**已收到成功响应的事务**目标 RPO 0，是硬性安全要求，不允许“99% 的故障不丢数据”式分位承诺。任意 ACK 丢失、部分事务可见、旧 writer 越权、GC 破坏恢复或越权访问都阻断发布，与平均延迟是否很好无关。

仓库要求 100% 单元测试覆盖率作为代码门禁，超时、分级选择、预算、准入及状态转换应设计成可独立测试的逻辑。覆盖率数字不等于已穷尽所有状态组合或并发顺序，也不能替代 fsync、真实网络、冷下载和故障历史测试。模拟时钟中“5 秒内完成”不构成真实 RTO 证据；mock store 的高吞吐也不构成生产性能。

## 9. 发布门禁及证据模板

与 [实施路线](roadmap.md) 和 [验证计划](validation.md) 对齐：

| 阶段 | 本文要求 |
| --- | --- |
| G0 | 真实 WAL/SDK/store 可行性；建立端到端计时和结果分类；先确认正确边界，不发布 TPS/RTO |
| G1 | 单 cell 的持久提交、强读、fencing 与故障恢复 oracle；记录微观分段开销 |
| G2 | 多库、Gateway、权限、路由及公平调度；热请求性能目标和 Cold 目录规模测试 |
| G3 | 完整恢复、冷唤醒、PITR/DR、GC、Suspend/Cold；验证有效恢复带宽、大小分级和实际恢复链 |
| G4 | 三 AZ、至少 100 次/场景故障样本、持续容量与运营窗口、混合版本升级；R1/R2 在实现并验证后才可开放 |

每份报告必须包含：

1. 目标文档版本、被测 commit、依赖/格式、硬件、网络/磁盘预检与部署拓扑。
2. 档位、库大小/对象数/tail、负载与并发、权限和持久化配置、是否预热。
3. 所有输入请求和结果分母、超时/UNKNOWN、重试及删失样本；按库/档位/cell 拆分。
4. 客户端与服务端 p50/p95/p99、各恢复阶段、`T_first_success`、稳定窗口 RTO、确认时刻和超标计数。
5. 完整故障清单、100/1,000 样本的置信范围、原始历史、正确性 oracle 和未覆盖范围。
6. `Q_safe`、降级容量、准入上限、固定基础设施和各恢复档位的增量成本。
7. 明确结论：通过、未通过或证据不足；不得将尚未运行标为通过。

如未达到性能目标，应优先优化、限制库大小/并发、预留更多接管资源或采用更高恢复档位。修改初始数值需要保留前一次失败结果及决定依据；不可通过降低 quorum、停止 fsync、跳过权限/校验或允许陈旧读来达到指标。

## 10. 当前有界服务的独立诊断档（2026-11-02）

`scap-server` 已提供自动 leader-owned writer 恢复和有界冷唤醒，另有 [真实服务合同](../../experiments/service-network/README.md)。当前配置最多 32 库、单库 256 KiB；它不属于上表 GiB 级 R0，也没有 R1/R2。

诊断实验使用同机两库、4 req/s、8 秒 deadline，保留 30 秒热基线和故障后 60 秒共 360 次调用。每库每秒一条强读和一条稳定 ID 写，按本规范的 30 秒双库稳定窗口计恢复，并核对全部 ACK。8 秒是这项独立小库诊断的既定边界，不替代本规范 2 秒生产基准；失败请求没有被删除，也没有 UNKNOWN 自动重放。

[执行证据第 13 节](g0-evidence.md)保留 debug 排队失败、首轮 release 的 ACK 核对失败和修复后的完整结果。成功窗口与成功请求分位都有明确失败分母；同机单事件不是生产 RTO p99。当前热延迟高于原目标，原 50/100 ms、500 req/s、三 AZ 与长期可用性目标保持不变，尚未通过。
