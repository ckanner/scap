## 2. 本轮发现和修复

### 普通请求在 worker panic 时过早归还资源

原调度器把普通请求 Job 移入 `execute(worker, job)` 的栈帧。worker 内部 panic 时，
该 Job 先析构，intake/output 的实际工作持有量先归还，之后外层 worker/native/cache
才开始清理。reader 虽然继续保留活跃读计数，仍未保住这两项请求资源。组提交已有
先 worker、后 active Batch 的字段顺序保证。

修复使普通 actor、control、reader 的当前请求也由 owning worker 保留，执行期间
只借用 Job。Rust 的字段析构顺序保证 worker/native 清理先完成，才释放 Job 及其额度；
reader 的活跃计数与组的队列额度仍晚于 worker。正常响应、过期、断线、shutdown 和
已完成组的后缀保序不变；不增加 SQL 重试、不改对象格式或 ACK 协议。

独立复核又确认 catalogue/recovery 两条通道有相同 intake 生命周期缺口。它们没有
OutputContext，因此由 ReservedWorker 保留原 Job 的 intake reservation，直到 worker
析构完成后才释放；不虚构这两条通道的 output 配额。

单位回归使用五种正式 Scheduler 线程与受控 Worker，在 panic 后阻塞 Worker::Drop，
分别保留或关闭响应 receiver 来模拟客户端连接状态；它不冒充真实 HTTP 断线或 native
故障注入。前三条通道的 intake 和实际 4 字节 base64 输出 backing 仍占用，后两条
通道的 intake 仍占用，清理结束后才归还。两项新回归分别在旧实现上实际失败，再用
修复实现通过；测试不进入生产覆盖分母。

代码先行提交于 [PR #69](https://github.com/ckanner/scap/pull/69)：
`89d75247b0649d57007f188960f4ab6ce1f46594` 修复 actor/control/reader，
`d8a4fc2a3fc29ecc568edb768612a7aa92f2b0d8` 修复 catalogue/recovery。

### 提交顺序文档与 Turso 分层

[部署边界](../operations/sqlite-storage-safety.md)原来只描述普通提交前 gate，未说明
#68 先在不可见私有 staging 完成逐成员 COMMIT。已区分两条路径；两者的 ACK 均晚于
依赖、HEAD 和本地最终完成。私有 COMMIT 不能当作远端持久确认。

Rust MVCC 引擎的区分。SCAP 仍逐成员 FULL COMMIT，不能套用上游 group commit 倍数。

## 3. 性能验收设计

采用相同正式二进制和独立的新后端，按关闭／开启／开启／关闭执行两对；各轮事务
输入、队列和资源容量相同，仅 group_commit 配置不同。轻载为 32 个独立事务、每秒
4 个；竞争负载为 128 个、每秒 64 个；全套 640 个测量原事务身份，另有 4 个 seed
事务。原时间表不随响应移动。
不使用人为暂停来凑组，不自动 execute 重试，不以必须提速作为通过条件。

每个原身份保留完整 HTTP 终态并 lookup 核对原结果与随机值，最终行与 committed
集合一致。独立审计从实际 S3 HEAD PUT、序列差和原结果计算组大小，分别报告每档
成功／拒绝／UNKNOWN、计划到达至终态分位数、SDK 调用开始至记录终态分位数、对象请求和
字节。短样本 p99 只是样本分位；完整字节观察器也会增加开销，不能等同生产 TPS。

### 配对性能结果与取舍

冻结实验源码为 `b49f966994ccdb28769372908a31138f70426642`，使用上面的同一个正式
release；四轮使用独立的新后端、服务和私有缓存。`group-load-v2` 完成全部四轮，
独立 oracle 输出 PASSED，原账本的 25 个精确负控全部拒绝、原样正对照通过。
实际执行顺序是 off-1 → on-1 → on-2 → off-2，不把目录名当作顺序证明。

下表仅为竞争阶段：每轮固定 **128 个事务、64 次/秒、2 秒到达窗**。成功吞吐是
原 ACK 数除以完整到达窗及排空时间；拒绝始终保留在 128 个分母中。延迟从预定到达
计至 SDK 调用的记录终态，包含客户端、网络、服务排队与观察器开销。

| 轮次 | 成功 / 128 | 拒绝 | 成功事务/秒 | 成功 p95 / p99（毫秒） | HEAD PUT | 阶段 S3 请求/成功 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| off-1 | 64 | 64 | 14.833 | 2561.8 / 2597.7 | 64 | 18.0625 |
| on-1 | 58 | 70 | 15.638 | 2405.1 / 2426.8 | 9 | 15.5345 |
| on-2 | 63 | 65 | 16.720 | 2329.4 / 2368.6 | 9 | 15.4921 |
| off-2 | 63 | 65 | 13.798 | 2869.9 / 2937.4 | 63 | 18.0635 |

第一对成功吞吐增加 **5.43%**，但成功率从 **50% 降至 45.3125%**；更短排空时间
不能掩盖少了 6 个原 ACK。第二对成功数相同，成功吞吐增加 **21.18%**。这只是两组
本地短样本，不构成稳定容量、普遍提速或生产 SLO 证明。高到达率下两种配置都发生
大量 BACKPRESSURE；不能把最终 cancel 成功计为业务成功。
第一对成功请求的 p50 也从 1920.334 增至 2000.429 毫秒；快速拒绝占比增加会降低
混合全部请求的中位数，因此成功、拒绝各自分位数必须分别查看。

on-1 的实际发布宽度为 `1×2 + 8×7`，on-2 为 `1×1 + 6×1 + 8×7`，共 **118 个**
事务实际进入多成员组。按各自成功分母计算，阶段全部 S3 请求下降约 **14.00% /
14.24%**，HEAD PUT/成功下降约 **84.48% / 85.71%**。前者包含阶段 status 探针，
不包含测量窗外的 seed、lookup/cancel 与最终查询；不能把它当作完整账单下降。
本次固定负载的阶段原计数恰为 `15 × 成功事务数 + 3 × HEAD 发布数 + 4`，其中末项
是 status 探针；HEAD 摊薄后仍有大量逐事务工作。这是该样本的请求计数分解，不是
所有 SQL 的通用公式，也不能单凭次数判定 native、网络与记录器各自耗时。

完整轮次仍保留各自成本：off-1/on-1/on-2/off-2 总 S3 请求分别 **2962 / 2760 /
2774 / 2950**，其中 verify 为 **1197 / 1250 / 1189 / 1203**。全部四轮 **11,446**
次 S3 请求、376 个原业务 ACK 与 264 个原拒绝均被审计；无 UNKNOWN，最终每个原身份
都找到 committed 原结果或持久取消屏障。4 个窗外 schema 事务另计。

轻载四轮均为 **32/32 成功、约 4 次/秒、32 个单成员发布、580 次阶段 S3 请求**，
没有观察到多成员组；不能声称低载提速或成本下降。32 个控制探针全成功，最大的
预定到达至记录终态为 52.825 毫秒，但每档仅 4 个探针，不提供稳定控制 SLO。
所有 p99 只是 nearest-rank 样本分位；256 字节 payload 的小表与完整原字节记录器，
不能代表大库、长稳态、无观察器或真实 AWS 性能。

因此保留 **group_commit 默认关闭**。接下来先冻结目标业务负载、成功率与尾延迟
要求，在目标后端验证是否值得开启；不扩大队列、不删除 FULL/回读来美化这轮数字。
吞吐接续先增加按 queue/intake/output/engine 预算区分的拒绝与占用观测，再做更长的
固定到达率曲线。源码表明多成员组在可信 consumed boundary 返回前继续持有队列
额度，可能改变突发接纳节奏；本轮 trace 没有逐次拒绝来源和占用，不能据此确定
第一对少 6 个 ACK 的原因，也不能提前释放资源来换取更好数字。

### 审计器开发期发现的问题

独立审查发现，初版性能审计允许把真实 HTTP 成功改记成任意 SDK 失败、错误终态时间
缺少绑定、吞吐分母短于完整到达窗，并把 status 探针混入 SQL 发送延迟。已先用失败
回归复现前两项，再分别补原 envelope/receipt/时钟关系、完整窗口和精确 SQL 分母。
同时绑定 S3 phase 时段、配置及工具 hash，禁止未发送的新身份成为 committed，要求
原业务 POST 早于发布。它们是实验观察器缺口，不是已经观察到的产品丢提交；不得把
修正前样本作为正式性能结果。

## 5. 后续实施顺序

1. 收口本轮远端 CI，保留组提交默认关闭；基于目标业务负载和后端继续测量成功率、
   原对象请求、native 成本和尾延迟，不能由一次本地实验作生产默认决策。
2. 面向低频长尾库优先评估 lazy VFS：固定授权根、页身份、generation/GC、校验和
   有界在途 I/O 必须同时完成，再测试 1%/10%/100% 工作集的首读时间与下载量。
3. 需要降低多库对象成本时实施独立 pack 协议：共享索引、逐库独立 HEAD 发布、
   部分成功和共享对象 GC；不引入隐式跨库事务。
4. 任意时间 PITR 先建立连续提交历史、时间落点与保留协议。热点单库并行写采用
   新 MVCC 引擎时另做 SQL、约束、冲突、native hook、恢复与原结果兼容验收。
5. 生产出口独立验证目标 AWS、一致性/IAM/故障域、长运行 GC/成本、冷启动风暴和
   数字 SLO。S3 及其凭据不可用时仍失败关闭，不以本地成功降级冒充同一承诺。
