# 容量、成本与性能测量

状态：测量设计与初始验收目标。目标尚未实测，不代表已达到的容量、吞吐或云价格；具体性能条件见 [性能与恢复目标](performance-slo.md)。

## 1. 比较基线

用户当前是多个逻辑库共享数据库实例，不应只与“一租户独占一台服务器”比较。分别测量现有共享方案、原生 SQLite + 备份原型、SCAP 可靠 cell 的总成本与故障合同。

SQLite 降低单库执行与空闲驻留开销；共享复制池、控制面和运营仍有固定成本。应用若仍每租户常驻一个进程，其成本不会因为数据库变冷而自动消失。

## 2. 成本模型

```text
总成本 = 活跃 worker + 冗余日志池 + 控制目录与入口
       + 热数据与日志空间 + S3 数据/历史/请求/流量
       + 可选 R1/R2 预备副本、追赶与接管容量
       + 观测/备份/恢复演练 + 研发与运维
```

关键自变量包括数据库总数 N、同时活跃库数 A、每库大小分布 D、峰值写入 W、每次事务修改页字节 B、历史保留 H、冷启动频率 C、复制因子 R 和故障预留容量 F。

不能假设成本只随 A 增长：目录、幂等、manifest、对象数量、扫描任务和保留历史仍与 N 等参数相关。

R0 经济档对应完整恢复；R1 在另一 AZ 预置完整文件，增加数据、网络和后台重放成本；R2 再预留执行上下文、内存和整 AZ 接管余量。R1/R2 仅为 G4 拟实现选项，未实现并验证前不能以其 8/15 秒、5/10 秒的 writer 故障 p95/p99 目标计算“已提供服务”的性价比。库长期完全冷卸载与持续维持热备是不同成本政策。

## 3. 初始实验矩阵

以下是拟生成的实验负载，不是容量承诺：

| 维度 | 建议覆盖 |
| --- | --- |
| 库数量 | 小规模正确性集、千库、万库，逐级扩展 |
| 活跃比例 | 稀疏活跃、中等活跃、全部活跃三类 |
| 数据体积 | 空库、MB 级、小 GB 级和超过内存的库 |
| 请求形态 | 点读、小事务、批量更新、DDL、长读、接近事务上限 |
| 分布 | 均匀、少数热点、单租户持续写、集中冷唤醒 |
| 故障背景 | 正常、一个 AZ 失效、S3 限速、单盘慢、控制目录中断 |

用真实业务的 schema、索引、SQL 和 ORM 补充合成负载；合成数字不能代替迁移评估。

首批容量目标为每 cell **10,000 个 Cold 库 + 100 个活跃库**；参考数据体积、500 请求/秒的初始实验输入、并发与请求形态以 [性能基准](performance-slo.md) 为准，均不是已测吞吐。R0 恢复并发初始取每 worker 1 个、每 cell 3 个，排队时间进入恢复指标，不能无界并发后只报告完成最快的库。

## 4. 指标

- 每库 Suspended / Cold / Active 状态的内存、fd、目录和磁盘元数据，以及 R1/R2 可选预备副本成本。
- 热读、写提交、读屏障和首次唤醒的 p50 / p95 / p99。
- quorum network RTT、fsync、group commit、RocksDB stall 和写放大。
- 每提交上传字节、S3 PUT/GET/LIST 请求、恢复读取放大。
- 热事务与归档之间的时间 / 字节 / `db_seq` 距离。
- 失去一个故障域后的 CPU、空间、带宽和恢复余量。
- 每个成功事务成本、每月空闲库成本、单位数据历史保留成本。

## 5. 容量与背压

按实测峰值写入增长率估算 S3 故障时剩余安全时间：可用可靠日志空间除以未归档增长速率。该值只是预测，必须结合各副本磁盘、compaction、快照安装和绝对预留空间。

保留至少覆盖计划故障窗口与修复时间的安全余量，具体值由部署环境测定。不能用三个副本总剩余空间相加，忽略某个 quorum 必需副本已经无法落盘。

初期通过 batch / group commit 摊薄 fsync 和对象请求，但不让批处理等待无界。跨 AZ RTT 直接影响同步提交，不能同时承诺完全本地写延迟与跨 AZ 同步持久化。

吞吐上限以满足延迟、错误率、正确性和后台积压边界的实测 `Q_safe` 确定。针对同一读写比、事务大小和热点分布分别测健康及单 AZ 降级容量；需要单 AZ 目标时，初始准入取 `0.6 × min(Q_safe_healthy, Q_safe_one_az)`。60% 是待验证的余量政策，不是已有吞吐成绩；恢复有效带宽、磁盘水位和 R1/R2 的接管资源也须纳入余量，不能只观察正常平均 CPU。

## 6. 优化顺序

1. 有界连接、关闭闲库、清理无用缓存。
2. per-db 索引与受控唤醒队列。
3. 提交合并与对象段压缩，保持同一安全边界。
4. 热点迁移和独立资源池。
5. 验证需要后再做页面懒加载、跨库对象打包或更复杂分片。

成本报告必须同时展示可靠性合同与固定基础设施成本，不用单机异步备份的数字替代三可用区高可用平台的数字。
