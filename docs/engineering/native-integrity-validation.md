## 真实网络、schema 与保留结果

真实 HTTP/S3 后端只绑定本机私有端口。基础 10 类合同、原有扩展 4 类合同和新增 schema 合同共 **15 类**通过。基础 **4 条 ACK**、扩展 **61 条 ACK** 的完整 receipt 和原 encoded result 均无差异；扩展 **30 个场景**含一个依赖上传 pilot，结果查证也无差异。覆盖范围仍以原始合同清单为准，不声称全部 OT-01–08、全部 HTTP 错误或进程死后延迟转发矩阵已经测完。

schema 分别执行 `execute` 与 `session_execute`，每种模式实际完成 ALTER、带 view／trigger／index／foreign-key 的 schema 检查、全部计算进程丢失与新目录恢复。**12 条原始 ACK、12 次冷查证、12 次原请求重放**全部保持原 receipt 和结果；重放只取已保留结果，不能产生 PUT 或重新求值随机 SQL。调用前、丢失前和恢复后的 schema／数据均另有账本。

初始诊断曾在预期 foreign-key 拒绝之后遇到 `StaleSnapshot`。已用原夹具和原 worker 重现，原始失败记录保留。原因是夹具在 SQL 执行错误后继续查询已停止的 Session，而产品既有合同要求任何此类错误停止 writer 并回滚。修复后的夹具先要求准确的 `StaleSnapshot`、HEAD body／ETag 不变和零 PUT，再显式打开新 Session，继续检查既有数据。**被拒绝的 SQL 不重放，产品的停止语义没有放宽。** 此修正已在最终冻结 release 的完整网络实验中通过。

保留结果实验在当前世代和已关闭保留世代各注入六类内部编码损坏：魔数、尾字段截断、额外尾字节、未知类型、非有限实数和非法 UTF-8。外层 Result／Index 的摘要、HEAD 引用与窗口字节计数都合法，故障确实落在内部结果校验。**12 个场景、60 次全新 worker 入口**均返回准确 `Corrupt`，实际读到目标对象，HEAD 不变且不发布恢复结果。恢复原引用后，**30 条原始 ACK**及数据完整核对，0 差异。代理和资源清理均无错误。

另用不导入实验夹具的审核脚本重新核对这些原始账本：共 **146 条不同 ACK、170 次完整 receipt／encoded 比较**，包含 schema 各阶段及 typed 重放结果，全部相等。补充审核脚本首次把 execute 的嵌套字段当成 lookup 字段，触发 `KeyError`；该失败及修正通过记录均保留，期间没有修改生产或实验源码。

## 1 GiB 完整丢失与恢复

本次实际提交 **1,073,741,824 字节独立随机 BLOB**，共 **16,384 行、每行 65,536 字节**。输入先由客户端独立生成、持久化并哈希，然后调用产品；不是读取产品输出反推期望值。

实验杀掉全部计算进程并删除其本地缓存，停止并重启本地 S3 后端进程，再从远端权威恢复到新目录。恢复后的 SQLite 逻辑文件为 **1,082,163,200 字节**。全部 **39 条 ACK**的原 receipt 和完整结果、全部 **16,384 个 BLOB**的逐值哈希通过，ACK 与 BLOB 差异均为 0。独立审核随后用 Python SQLite 以 immutable read-only 打开已恢复且 WAL 为零的文件，再从原始 BLOB 字节重新计算全部哈希，与调用前账本推导的最终状态相等；这是额外的本地原始字节审计，不记作第二次 S3 恢复。

热 Session 仍按新 HEAD 重查权限与固定根；丢失 HEAD 成功响应通过原请求查证解决，没有 SQL 重放。HEAD 黑洞下热缓存查询约 **0.201 秒**失败关闭。1 GiB 上三个单点 64 KiB 更新的 PUT body 约为 **292,066／423,571／312,706 字节**，GET body 约为 **591,167／854,413／632,919 字节**；原始计量含实际请求数与传输字节，未把回读流量藏入零成本假设。

整套 1 GiB 实验用时约 **184.54 秒**；原网络含 schema 约 **48.97 秒**，保留结果矩阵约 **26.67 秒**。这些是本机选定合同的观测，不是生产延迟或吞吐 SLO。默认 10 GiB 配额、30 秒操作预算、30 分钟恢复预算和完整初始物化方式均未改变。
