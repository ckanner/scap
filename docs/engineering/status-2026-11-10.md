# 2026-11-10：SQLite on S3 的组合验收与后续实现

## 目标与当前判断

目标是 **S3 保存唯一持久权威、本地 SQLite 只负责执行与缓存的多租户数据库服务**。
大量独立数据库可以分散到多个计算实例；单个数据库由同一个 HEAD 的条件发布排序。
这条路线已经有正式 Rust/native/S3、HTTP 和 Node SDK 实现，并非只有设计。

它解决跨节点共享 `.db`/WAL/SHM 时对网络文件锁的依赖。执行目录仍必须是经过检查的
本地文件系统；不支持把 EFS/NFS/S3 FUSE 当成本地 SQLite 目录。它也不自动消除热点单库
的单写者限制、S3 往返、写放大、冷恢复或租户资源竞争。具体机制、代码对应关系、Turso
对照与吞吐改进顺序见[完整分析](../architecture/sqlite-s3-safety-and-throughput.md)。

## HEAD6：实际压实与物理回收

HEAD6 的 core/store/service/SDK 已形成冻结生产候选。整 workspace 的新单位与精确覆盖，
真实回收、资源与负载均按上方新记录完成各自验收，不能由单元覆盖替代。
它沿用逻辑 Scope，分离物理 storage generation，提供明确的管理员 Begin、Copy、
Promote、Abort 与有界 GC Prepare/Resume。普通短操作采用可中止旧世代的语义，
不创建崩溃后无法撤销的永久读 pin。

核心约束如下：

- 复制当前数据树、全部保留请求索引与原始结果；原 receipt 的历史 data_root 不是新增的历史快照承诺。
- 新代只在完整闭包验证和所有目标对象回读之后晋升；保持最新 ACL，晋升后先处于 inactive。
- 世代号只递增，放弃的目标也不复用；当前 active 和当前 copy target 永不成为回收候选。
- GC 把最多 32 项的原 key/ETag 与处理进度写入 HEAD。进程重启或响应丢失后按同一批次查证，不刷新旧候选的 ETag。
- 缺 key、缺 bucket、请求超时和已删除必须分开。迟到旧 PUT 产生的 orphan 由下一轮从起点重新扫描处理。
- 老读遇到已严格证明退休的世代可以失败为 SnapshotExpired；这不表示原 SQL 没有提交，也不允许自动重放 SQL。

真实验收已覆盖三代保留窗口、复制期间 ACL 更新、暂停旧 GET/PUT/HEAD CAS/DELETE、
checkpoint 重启、删除响应丢失、同字节不同真实 ETag，以及全缓存丢失后的原结果恢复。
有限模型、传输能力测试和新生产协议分别验收，不能互相替代。

固定本地小负载的单库 C1/C4 写入分别为 8.795/8.750 次每秒，四库 C4 为 14.376；同库
增加并发主要增加排队，多库本轮提高约 1.643 倍，并非线性扩展。32 MiB 冷恢复含人为
gate 为 1.746 秒，11 个热库/控制探针均在解除 gate 前完成，单请求最大 108.120 ms。
完整样本、分母、两种排队时延、S3 放大与资源采样局限见验收记录；没有 AWS 或生产 SLO。
