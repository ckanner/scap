# ADR-0020：有界管理操作序号与最近回执

- 日期：2026-11-05。
- 状态：实现中；完整本地单元、精确覆盖率与真实故障验证完成前不得视为可合入。
- 关联：[ADR-0019](0019-explicit-request-result-retirement.md)、[状态机](../engineering/cell-state-machine.md)、[故障矩阵](../operations/failure-matrix.md)。

## 1. 问题

请求结果窗口可以显式退休，物理历史也可以折叠，但成功的 Create、ClaimOwner、ActivateOwner、AuthFence、SuspendDb、PublishArchive、PruneArchive、HydrateArchive 仍逐条追加永久行政回执。一个完整的休眠、归档、唤醒和恢复周期通常产生六条记录，热库重新恢复 owner 产生两条。cell 达到 4096 条后，新建、唤醒和恢复都可能被拒绝；checkpoint 不能删除应用状态里的这些回执。

直接淘汰最旧的 operation ID 不安全。例如 Prune 成功后 Hydrate 恢复了页面，而 owner 仍保持同一个 suspended token；若删除原 Prune 回执，迟到的同一命令可能再次删除这些页面。提高计数上限只延后问题。

本决策为管理操作建立独立、持久、单调的每库序号，只保留最近一次成功操作的精确回执。旧格式回执继续保留为固定升级成本。SQL 请求身份和显式确认合同保持独立。

## 2. 完整控制身份

新管理操作绑定 cell、数据库 ID/incarnation/placement generation、`expected_control_revision`、operation ID、原主体和规范化意图。第一次提交前通过经过权限校验的新鲜视图捕获序号；后续重试必须保留原序号、ID 和意图。刷新凭据、admission ID 或当前 auth epoch 不会刷新控制身份。

控制序号不等于 SQL revision、owner epoch、auth epoch、request epoch 或 Raft term/index。它只随新接受的管理操作增加。一般 SQL、强读、请求确认与请求窗口退休不消耗控制序号。

`Command.control_revision = None` 表示旧命名空间；`Some(n)` 表示独立的新控制命名空间。后者只允许八种管理动作，不能给普通事务套控制 envelope 来改变其身份或绕过门禁。

## 3. 有序接受与结果保留

当前序号为 `r` 时，新意图必须绑定 `expected_control_revision = r`。权限与原有动作条件全部通过后，序号 checked-add 到 `r + 1`，动作变更和最近回执在同一候选状态中原子保存。回执包括原操作 ID、主体与意图摘要、原准入、原成功结果、原提交位置以及新的控制序号。

| 输入 | 结果 |
| --- | --- |
| 当前序号的新有效动作 | 执行动作，增加序号，替换最近回执 |
| 最近成功动作的完全相同原身份 | 在当前授权仍有效时返回原成功结果、原位置和原序号，不再次执行 |
| 最近序号但主体、ID 或意图冲突 | 明确冲突，无动作变更 |
| 早于最近回执的序号 | `ControlRetired`，永久禁止重新执行 |
| 未来序号 | 明确冲突 |
| 无法增加序号、预算不足或动作条件失败 | 原子拒绝，不替换最近回执 |

`ControlRetired` 只说明该控制身份已不能再接受，原精确回执已不在保留范围。它不证明原动作未执行，不代表取消，更不能授权把同一意图换成当前序号重发。请求级 `Retired` 与控制级 `ControlRetired` 分开表达。

创建不存在数据库使用序号 0，成功后为 1。旧数据库在独立激活后从 0 开始且没有新命名空间回执。数据库身份检查继续生效；本次没有删除或复用数据库 ID 的入口。

## 4. 容量与升级

新格式每库最多一个最近回执，随数据库数量有界，管理操作总数不再消耗原 4096 条旧记录额度。状态预算预留最大控制回执空间，避免普通成功写耗尽未来 fencing、确认或控制动作所需的元数据空间。计数常数、状态上限与数据库容量不提高。该预留不保证任意扩大 policy、引入新对象数据或新建数据库在满预算时一定成功。

新控制 Hydrate 命令需要 202 字节的完整 envelope 开销；旧阶段按原 192 字节容量判断继续重放。新归档生成、Publish 与状态校验使用新格式的真实大小。v5 激活还检查每一个已有 Hot/Cold 归档引用：若原对象无法装入今后的控制 Hydrate 命令，原子拒绝激活并保留 v4 的恢复路径，不能先升级后让冷库永久无法水合。

升级采用独立有序 v5 激活。正式 genesis 继续使用原固定 v2 字节，新节点先按旧阶段规则追赶历史，再依次完成 v3 物理历史、v4 请求退休、v5 管理控制激活。不能在 decode 时擅自切换裁决规则。

v5 激活后：

- 已存在的旧管理 ID 仍可按原主体、数据库、意图和当前权限返回原回执；旧表不再增长。
- 未记录的旧管理 ID 永久拒绝；不得用空表项推断旧操作未执行。
- 新命名空间与旧表容量解耦；即使旧表已满，新管理操作仍可在状态预算内继续。
- 服务须在同一个原 deadline 内观察到已持久应用的激活结果及新鲜 v5 ReadIndex，才能打开数据库准入。

状态格式为 v5；新控制 command/outcome 使用独立的业务 envelope v4。peer envelope 升为 generation 4，旧 1/2/3 不能参与当前复制、投票或 snapshot。升级要求停止全部旧 voter 后原盘打开，不声称支持混合版本滚动升级。旧二进制必须拒绝新状态，而不是重建空库。

## 5. 恢复与归档调用链

owner 恢复先捕获控制序号，ClaimOwner 使用固定身份。只有精确确认的 Claim 回执及随后匹配的新鲜视图才能授权下一步 ActivateOwner。Activate 使用 Claim 对应的下一序号和固定意图；恢复期间若出现其他控制转移，旧恢复工作被 fence，不能仅刷新序号继续激活。

后台归档任务保留原数据库视图、原 deadline 和固定 Publish/Prune ID。Publish 的精确成功回执确定 Prune 的下一序号；未知 Publish 不进入 Prune。发布后若有其他控制转移，旧 Prune 明确拒绝。Hydrate 同样绑定原冷库视图和控制身份。

`publish_bound` 是一次性的归档构造与提交助手，不是可用相同参数重复调用的精确重试句柄。单次调用固定其生成的对象字节和 Publish 意图，并至多提交一次；每次重新调用都会读取当前 cell 应用位置，其他数据库的进展也可能改变生成对象。返回 UNKNOWN 后，调用方必须保留未知结论，不得据此进入 Prune，也不得以相同 operation ID 再调用本方法来重建原意图。后续独立维护须重新评估状态并使用新 operation ID；精确重放原 Publish 则必须保留原完整 Command 和对象，不能仅保留 DatabaseView。如果原命令尚未接受，重新构造的不同意图仍可能在同一控制序号先被接受，因此不能依赖序号检查来保证这种错误用法总是被拒绝。

同一进程内，每库使用有界的共享执行权，把后台完整 Publish → Prune 与前台完整 Hydrate → Claim → 原生构造 → Activate 串行执行。恢复先在原 deadline 内取得执行权，再读取第一个权威视图并捕获控制身份；不能先捕获序号、等待已有归档改变状态，再继续提交旧视图。已经排队的归档仍保留自己的原视图，取到执行权后若它已过时，就按原协议拒绝，不能刷新。不同库不共用这把执行锁；队列表锁只保护有界内存记账，不跨对象存储或 cell I/O。

在等待执行权期间，原请求的期限和取消标志保持不变。取到执行权后的同一新鲜状态还要重新检查原租户准入、权限与请求世代；服务的内部 ADMIN 凭据不能代替一个已经被撤权的调用方继续唤醒。该检查成功后才建立本次恢复的管理意图。成功 Hydrate 的后续确认视图可以建立独立的 Claim 意图；失败或 UNKNOWN 不触发刷新和重试。

这项本地协调解决服务自己启动的归档与唤醒竞争，不是分布式租约。旧 leader、其他节点、授权变更以及已经返回 UNKNOWN 的迟到命令仍由持久控制序号、owner token、当前授权和新鲜 ReadIndex 裁决；发生这种竞争时仍须明确失败，不能因为持有本地锁就放宽状态机检查。

不可变归档是物理恢复来源，不是最新控制状态来源。即使 cell 状态使用 v5，物理对象继续使用 v4 格式；v2/v3/v4 旧对象仍按原格式核验。Hydrate 只能恢复精确发布对象覆盖的物理 bytes，不能把归档中的旧 owner、policy、request ACK 或控制序号覆盖到最新元数据。

服务移除了原来在单次恢复内遇到 Cold 后刷新一次的路径。Prune 先于 Claim 等控制交错会使本次恢复在 SQL 执行前明确失败；服务不会在这个调用内替换控制序号或 operation ID。后续独立请求或自动维护可以在新鲜视图下建立一个新的恢复任务；这不能改写以前一次 UNKNOWN 的结论，也不能把旧 SQL 或旧管理命令偷偷改成新身份再次执行。

## 6. 验证与范围

单元合同需要覆盖八种动作的精确最近重放、退休日志身份、未来/冲突序号、当前权限、溢出和预算原子性、状态快照、旧表满容量升级、旧前缀确定性、归档水合不回滚控制元数据，以及超过 4096 个新动作后的有界状态。

独立真实合同需要覆盖真实三节点 quorum、RocksDB、TCP/mTLS、进程退出和 SeaweedFS：超过原管理额度的成功控制操作，实际冷生命周期，Hydrate 后迟到 Prune，Publish/Hydrate 响应丢失，Claim/Activate 间故障，snapshot/重启，真实 v4 生产者原盘升级与旧二进制拒绝新盘。原始失败和 UNKNOWN 必须保留；不能把这些 profile 用来填补单元覆盖率。

首轮真实服务验证暴露了同进程归档竞争：已有提交前缀包括 Create → Publish → Claim Conflict → Prune，以及 Hydrate → Publish → Claim Conflict。复制原盘并重放正式状态机确认了这些顺序；SQLite 构造、SQL 执行和期限耗尽都不是这两次失败的原因。必须保留首轮失败，并在加入上述协调后重新执行原先的一次性请求断言。不得用忽略恢复错误、扩大成功范围或重发未知 SQL 代替生产修复。

本决策只解除长期管理记录累计阻塞。旧记录固定成本、S3 对象保留、逻辑编码与 checkpoint 放大、多 cell、公平调度、GiB 级数据库、PITR/区域灾备和三 AZ 生产 SLO 仍分别需要后续实现与验收。管理元数据有界不等于对象存储已实现 GC。
