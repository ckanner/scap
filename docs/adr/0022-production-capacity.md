# ADR-0022：单库容量配置、分块数据树与可复用 SQLite 会话

- 日期：2026-11-06。
- 状态：实现候选；容量、真实对象服务与生产阶段的验收结果分别记录。
- 范围：替代 [ADR-0021](0021-object-native-runtime.md) 中用于首轮验证的 256 KiB 单库 profile、逐页对象和完整页列表；继续遵守 [ADR-0020](0020-object-storage-native-authority.md) 的唯一对象权威与无旧版本兼容要求。
- 实现入口：[运行时与会话](../../crates/scap-object/src/lib.rs)、[配置](../../crates/scap-object/src/options.rs)、[格式](../../crates/scap-object/src/format.rs)、[数据树](../../crates/scap-object/src/data_tree.rs)、[原生 SQLite](../../crates/scap-object-sqlite/src/lib.rs)。

## 1. 问题与目标

首轮运行时以完整小型映像恢复、完整页列表和严格的小预算验证提交顺序。这些选择不能通过放大页数常量直接变成 GiB 级实现：整库字节的多次复制会使内存随数据库大小增长，逐页 GET 和完整 manifest 重写会放大对象请求；每个操作重新恢复、每次发布重新读取所有历史结果，也会使热操作随着库或保留窗口增长而失去可用性。

本轮将单库容量与单次执行预算分开，提供明确的持久配额，并移除整库内存恢复路径。容量配置、已经完成的容量实验和生产服务承诺是三件分别记录的事实。默认允许 10 GiB 不构成 10 GiB 实测结果，也不构成延迟、吞吐、成本或可用性承诺。

## 2. 持久配额与运行时预算

单库默认逻辑文件配额为 **10 GiB = 10 × 1024³ 字节**，按 4096 字节页计量。配额包含 SQLite 文件内已经分配的页，不能用用户行或 BLOB 的总长度代替；删除行未必缩小文件。对象历史、原结果、本地 WAL、临时文件和 orphan 不在这项逻辑文件配额中。

`Head.quota.max_bytes` 持久保存配额。`Some(bytes)` 必须为正、按页对齐且不超出格式允许范围；`None` 取消 SCAP 的业务容量配额，仍受固定 SQLite 内核的页号边界约束。创建配置只用于新数据库，重开旧库不能用本地默认值覆盖其 HEAD 配额。`set_quota` 与数据写入在同一 HEAD 上按原 revision/ETag 排序；降低配额不得截断已有页，也不得低于当前文件大小。配额改变后，现有 Session 需要重新恢复并配置原生连接。

运行时默认值如下，数值取自配置实现，不代表实测性能：

| 项目 | 默认值 | 作用范围 |
| --- | ---: | --- |
| 单库逻辑文件配额 | 10 GiB | 持久 HEAD，可设为 `None` |
| 单事务变化页 | 16,384 页，即 64 MiB | 最终增量页捕获与执行准入 |
| SQLite page cache | 64 MiB | 缓存目标；不是进程内存硬上限 |
| SQL 文本 | 1 MiB | 同一事务全部语句的 UTF-8 字节总和 |
| 输入请求 | 64 MiB | SQL、参数及编码开销的聚合预算 |
| 原始结果 | 50 MiB | 完整事务编码结果 |
| 单个值 | 2 MiB | 文本、BLOB 或列名 |
| 语句 / 参数 / 列 / 行 | 256 / 每语句 32,766 / 2,000 / 共 1,000,000 | 单次执行 |
| SQLite VM 步数 | 100,000,000 | 单次执行 |
| 操作期限 | 30 秒 | 与调用方原绝对 deadline 取较早者 |
| 冷恢复期限 | 1,800 秒 | 显式恢复阶段，与调用方原 deadline 取较早者 |
| 每窗口结果保留 | 4,096 条、256 MiB | 持久 HEAD；按任一预算关闭 |
| 完整 closed 窗口 | 最近 2 个 | 与 current 窗口一起查证原结果 |

这些配置具有各自的边界，不按数据库总页数增加 SQL、结果或一次事务的预算。大库批量导入仍须拆成多个有界事务。期限用于阻断已经过期的操作并中断原生扫描和执行；本轮没有提供可抢占任意文件系统调用的执行隔离。

格式硬限独立于当前准入值：物理页号最多 `2^32 − 2`，单条持久原结果编码最多 64 MiB，单个窗口最多 65,536 条终态。降低当前调用方的结果或输入准入预算，不能让已提交回执按新预算解码失败；原请求指纹与保留结果使用稳定的格式能力校验。格式可表示的上界也不能作为已验证容量发布。

## 3. v2 对象布局

HEAD 与不可变对象采用严格 v2 编码，继续拒绝错误 scope、摘要、长度、版本和未知字段。HEAD 的身份 key 保持绑定原 deployment/tenant/database；格式升级不能通过换 key 绕过既有 tombstone。没有 v1 数据自动迁移、双格式读取或旧库兼容路径。

数据页按 **32 页、128 KiB** 分块，尾块按实际页数编码。块主体和原结果使用带长度的二进制 frame，避免 JSON 字节数组放大。Manifest 只保存总页数和数据树根；内部节点具有固定 256 分支上界和有界深度。增量提交只重建受变化页影响的块和树路径，未变化子树保留原内容地址。缺失的新增页必须拒绝，不能以稀疏文件的零页或自动补零代替。

请求结果索引仍是按世代有界的写时复制对象；本轮没有把它描述为只随新增条目增长的索引。当前窗口的索引读取、复制和上传仍有与窗口条目数相关的开销，须计入容量及延迟证据。旧结果的数据根属于原回执的一部分，不因此提供历史快照读取或 PITR；完整闭包的遍历不递归下载每个历史结果引用的旧数据库映像。

## 4. 流式冷恢复与 Session

冷恢复先读取授权 HEAD，再验证 Manifest、树节点和每个块的内容地址及几何关系。`ImageBuilder` 将已经验证的连续页面直接写入全新私有目录；`PreparedImage` 只在全部页面完整写入并同步后产生。原生打开执行一次完整 `integrity_check`，其 progress callback 继承原恢复 deadline。生产路径不持有整库 `Vec<u8>`，也不为提交复制整库基线。

这是完整文件恢复：冷恢复需要 O(数据库大小) 的对象读取和本地文件空间，之后还要进行完整结构扫描。本轮没有按需 VFS、稀疏读取、部分数据热启动或缓存页淘汰后远端按需回填。能用有限内存恢复大文件，不等于冷启动只需读取少数页。

`Session` 持有已验证数据根的私有 SQLite 连接，连续执行事务和查询，避免每个操作重新下载整库。每次公开操作仍重新 exact GET HEAD，并检查当前权限、生命周期和对应的数据根；写入还要符合当前 owner 约束。根或配额不一致时返回过期快照错误，原生执行失败后的连接不能继续执行 SQL。接管恢复可以保留刚验证的文件，避免激活完成后再下载一次。

本地文件不是授权租约或权威。无法获得当前 HEAD 时，热缓存不能成功降级。Session 释放时关闭连接并清理所属目录；清理失败是缓存 orphan，不改变对象端的提交事实。常规 GiB 级操作应显式准备并复用 Session；一次性 `execute` / `query` 的完整恢复仍计入该次操作期限。

## 5. 增量发布的依赖证明

热发布不再主动读取所有未变化数据块和所有历史结果。它继承先前已发布 HEAD 的不可变依赖，并验证本次新增对象。该规则对数据树和结果保留采用同一证明条件：

1. 初始 HEAD 的全部依赖经过持久化和回读校验。
2. 后续每个新块、节点、Manifest、Result 和 Index 都使用条件创建，并在发布 HEAD 前 exact GET 核对编码字节。不可变 key 不能被覆盖。
3. 未变化引用指向前任 HEAD 已经持久化的对象；在这些引用仍被保留期间，GC 和其他主体不会删除它们。
4. HEAD 只使用同一次 exact GET 获得的 body 和 ETag 执行条件替换；旧候选不能更换 ETag 重试。

在这些条件下，可对成功 HEAD 转换归纳证明全部新旧依赖已经持久化。Session 缓存只减少重复校验的 I/O，不产生第二套提交权威。AWS 对象合同、凭据权限和可达对象生命周期必须分别验证，不能由归纳条件的文字声明替代。

完整校验与目标查证的时点如下：

| 路径 | 必须验证的依赖 |
| --- | --- |
| 冷激活 | 当前数据树、全部块、全部保留窗口 Index 和 Result；激活前重新核对 HEAD |
| 首次准备可写会话 | 当前数据完整恢复，首次写前完成保留结果闭包校验 |
| 已验证会话的后续写入 | 当前授权 HEAD、当前请求索引及新依赖；不主动扫描无关历史结果或 closed 索引 |
| `lookup` / 重复 `execute` | 当前授权 HEAD、目标窗口索引、目标结果的实时内容与请求绑定 |
| 普通只读查询 | 当前授权 HEAD 和当前数据快照；不依赖历史结果全集 |

冷恢复发现缺失或损坏的可达依赖必须失败。查证某个原请求时，其索引或结果缺失也必须失败，不能生成空结果、取消证明或重新执行 SQL。已验证热会话不会在每次无关写入时主动发现旧对象被外部删除；这一检测边界必须写入故障回归，不能同时宣称已移除热路径全量读取和每次提交都会检查全部历史对象。

首次闭包验证属于恢复工作，须使用可完成该工作的恢复阶段；不能把数百 MiB 的冷验证隐藏为已满足 30 秒热操作预算的事实。新结果上传或回读失败仍禁止 HEAD 发布，HEAD GET 失败仍阻断所有公开 Session 操作。

## 6. 原生内存、WAL 与成功返回顺序

原生连接设置实际 page-cache 目标并开启 `cache_spill`。缓存目标同时受事务变化页预算约束；当前不支持未提交的 WAL spill，遇到非 commit `xFrames` 时在原生执行期间安全拒绝，不能先泄漏未发布页面。最终提交仍独立核对变化页数量、页号、长度和完整增长几何。

`cache_size` 是软目标，Rust 结果值、SQLite 临时工作区、输入、增量页和对象编码也会占用内存。64 MiB cache 和 64 MiB dirty 都不是 64 MiB RSS 承诺；本轮没有全进程 `hard_heap_limit`、容器硬隔离、多库公平调度或完整临时磁盘配额。

写入的成功顺序保持为：执行并缓冲结果、验证新依赖、原 ETag 的 HEAD 条件发布、native publication、检查本地 checkpoint 完成、返回成功。每次成功 native commit 后执行 `wal_checkpoint(TRUNCATE)` 并核对实际 busy 与 frame 状态，使复用 Session 的 WAL 不按事务次数持续增长。checkpoint 不调用对象提交门，也不改变远端权威。

HEAD 已接受后，native publication、checkpoint 或最终交付边界失败，返回携带原回执的 `CommittedButUnavailable`，停止本地连接；不能解释为回滚。会话只有完整成功后才更新本地数据根。后续原请求可实时查证原结果，但不能借失败会话重放 SQL。HEAD 响应丢失仍保留 UNKNOWN，遵守原请求身份与 lookup/cancel 规则。

## 7. 结果保留与总存储

默认每个窗口最多 4,096 条终态和 256 MiB 原结果，保留 current 及最近两个完整 closed 窗口。窗口为格式允许的最大单个结果预留空间；条目数或剩余字节空间不足时，先拒绝新准入，再由可信协调器关闭满窗口。不同实际结果大小会使窗口在不同条目数关闭，不承诺正的墙钟留存时间。

关闭窗口只推进请求身份屏障和逻辑引用，不删除对象。取消终态、已提交终态、closed 和 retired 的含义保持不同；退休身份不能重新接受。物理 GC、历史根 pin、PITR 与长期压缩尚未实现，成功变更、冲突和中断上传均可能增加历史对象或 orphan。逻辑数据库 10 GiB 和结果窗口有界，不能推出 bucket 总量、磁盘峰值或长期账单有界。

## 8. 官方容量对照

以下仅用于判断配置量级，按 2026-11-06 查阅的官方公开资料记录；厂商的产品合同不证明 SCAP 的实现、正确性或成本。

- [Cloudflare D1 limits](https://developers.cloudflare.com/d1/platform/limits/)：Workers Paid 的单库上限为 **10 GB**，Free 为 **500 MB**；Paid 账户存储上限列为 **1 TB**。单库上限与账户总量是不同指标。这里保留官方 GB/MB/TB 单位，不将其改写为 SCAP 的 GiB。
- [Turso 官方定价](https://turso.tech/pricing)及[官方用量说明](https://turso.tech/blog/tips-for-maximizing-your-turso-billing-allowances-48a0fca163e9)：套餐 Storage 是数据库组合的存储用量额度，不能当作单库硬上限。当前引用的公开资料未给出可据以承诺的统一单库硬上限，记为**未知**，不从套餐总量反推。

本轮选择 10 GiB 为可调默认业务配额，同时保留 `None`；没有复制其他产品的限制集合，也没有声称复现 Turso Cloud 的闭源提交或按需读取实现。

## 9. 验收边界

本 ADR 记录设计决定，不填写尚未产生的容量结果。单元四维覆盖、独立模型、真实本地 S3 故障合同、GiB 级容量和 AWS Standard 必须使用相应冻结源码与实际执行证据分别验收，见[验证规范](../engineering/validation.md)。

容量验收应通过正式请求与参数生成非零、不可由零填充冒充的数据库数据；在会话复用和全部本地缓存丢失两种路径下核对独立成功账本、原回执、原结果以及恢复后的全部业务值。配额边界须区分同尺寸更新与继续增长，并记录峰值 RSS、主文件与 sidecar、对象请求量、上传放大、恢复时间和未回收存储。达到 1 GiB 不代表达到 10 GiB；文件预分配、配置回读或 sparse 文件长度不能替代业务数据和恢复验证。

本地 S3 兼容端点的成功不表示 AWS Standard 已通过。AWS gate、生产 SLO、多库长时间容量、GC/PITR 和成本验收仍须各自提供证据；未执行项保持 `NOT_RUN`，N1 整体和生产发布不能由本 ADR 宣告完成。

## 实现复核补充

实际跨越 1 GiB 时，固定 SQLite 内核不会为第 262145 页锁字节保留页提供 WAL frame。native adapter 仅在首次跨越时显式补入这个确定的零字节页并计入变化页预算；既有权威页保持原字节，普通增长缺页仍拒绝，数据树不隐式补页。这一边界必须在真实容量实验中重现并验证修复，不能只把页数上界调大。

64 MiB 脏页预算不等于总对象流量：分散的一页修改可触及整个 128 KiB 块，最坏块数据重写约 2 GiB，另有元数据和回读。2 MiB 单值预算对应请求参数与返回值，不是所有数据库内存储值或整行的 2 MiB 上限。

热路径复用不可变引用后，同一 Database 及 clone 仍记忆已观察到的对象/语义损坏，在新写和最终 HEAD CAS 前拒绝发布。目标查证、当前索引/结果语义及冷树校验的已知损坏不能被后续成功掩盖。此共享隔离只存在于进程内，不能声称是跨 worker 持久仲裁；不恢复逐次全历史扫描，也不改变不可变对象、无可达对象删除的协议前提。

隔离范围明确为后续 HEAD 发布。已验证本地快照仍可在 fresh HEAD、当前权限和准确根匹配下只读，status/lookup 保留诊断能力；它不是自动维护模式，也不能撤回已发出的在途 CAS。HEAD 不可达时读写均失败关闭。
