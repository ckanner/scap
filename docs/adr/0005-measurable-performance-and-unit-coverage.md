# ADR 0005：性能验收与 100% 单元覆盖率驱动架构

状态：接受为工程约束；性能数字尚未实测，恢复等级尚未实现。

## 背景

用户要求明确正常延迟、写者故障后的接管和恢复时间，并以 100% 单元覆盖率驱动松耦合、高内聚及开闭原则。单独写“高可用”无法判断故障后多久能服务；只报告覆盖百分比也无法判断模块是否可替换或数据是否正确。

## 决策

1. 性能采用 [明确目标、负载和故障条件](../engineering/performance-slo.md)，同时记录全请求结果。RTO 从故障发生计算到可被后续稳定窗口证实的恢复起点，第一次偶发成功单列。
2. 保留完整恢复的 R0 基线；为低 RTO 定义 R1 完整缓存与 R2 跨 AZ 热备，但它们属于 G4 待实现能力。额外副本与执行槽需要明确成本、身份校验和失效状态，不能由超时租约授予写权。
3. 第一方运行时代码采用独立单元测试的 100% 行、函数和分支门禁；Rust 同时检查 region。工具未产生可靠计数、缺源码、空分母或低于目标都阻断合入。
4. 状态与决策尽量纯化，真实副作用通过窄接口接入。实现只依赖端口合同，不直接依赖网络、磁盘、系统时钟或随机全局状态。测试替身和真实适配器接受相同合同约束。
5. 集成、真实引擎、进程退出、Raft 故障与性能测试分别报告，不能混进单元 profile。研究探针不是运行时组件，迁入产品后必须进入产品覆盖分母。

## 代价与边界

100% 覆盖需要额外的错误注入、接口设计和报告维护；不能为数字写无断言测试，也不能用难以达到覆盖为理由删掉必要防御。工具能测得的分支并不代表所有条件组合、MC/DC 或分布式交错；这些仍需要状态机、属性与故障测试。

性能目标可能要求更多空闲接管容量和热备资源。测试未达标时记录差距，调整实现、资源或通过新的明确决策修改目标；不能丢弃慢样本或弱化持久性来达标。

## 本次落地

`scap-core` 实现提交完成顺序的窄策略；真实 libSQL WAL 探针独立验证受限引擎路径；覆盖率脚本核对全部运行时源码和精确计数。详见 [G0 执行证据](../engineering/g0-evidence.md)。这些不等于完整 G0 或分布式平台已经通过。
