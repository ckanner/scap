# 需求、假设与故障合同

状态：设计基线。日期：2026-10-27。可靠性目标尚未经过实现验证。

## 1. 使用场景

SCAP 在同一云环境中服务多个租户。每个租户可有多个 workspace / Agent 数据库；库的创建数量远高于同时活跃数量。应用主要使用 Node.js，希望保留 SQLite SQL、现有 ORM，以及尽量接近现有驱动的访问方式。

数据库划分以权限、独立恢复和生命周期边界为依据，不强制每个 Agent 都创建新库。跨库原子事务不在初始范围；需要同一事务的数据放在同一个数据库。

## 2. 初始交付范围

- 单区域、三个独立可用区的复制与故障切换。
- 每库单写者，按数据库分散到多个共享 storage cell。
- SQLite / libSQL 服务化接口；原生 Node 同步接口通过经验证的兼容驱动作为可选入口。
- 写入成功以同步复制后的权威提交为依据。
- 默认强一致主库读取；显式长读事务维持 SQLite 快照语义。
- 空闲关闭、可验证归档、冷库卸载、访问唤醒。
- 数据库创建、配置、配额、删除、历史恢复、离线迁移。
- 故障观测、恢复演练和版本升级门禁。

## 3. 初期不承诺

- 任意原生 SQLite 驱动二进制无需修改即可远程访问。
- SQLite 全部扩展、所有 `PRAGMA`、任意文件格式 / page size 与现有应用 100% 兼容。
- 跨数据库事务、跨区域同步多主、网络两侧同时可写。
- 客户端离线多写者合并、透明迁移进行中的事务或会话。
- 首版按页直接远读 S3、自定义通用 VFS、无限大小事务。
- 区域灾难下零丢失、永久多数副本丢失后的自动零丢失恢复。
- 冷数据库完全没有成本；目录、对象、历史和共享日志池仍有成本。

## 4. 术语

| 术语 | 含义 |
| --- | --- |
| tenant | 客户级权限与配额边界 |
| database / `db_id` | 不可变的数据库身份，名称只是别名 |
| incarnation | 数据库生命周期代次；删除重建或灾难分叉不能沿用旧代次 |
| owner | 获准执行当前数据库写事务的 worker 实例 |
| epoch | cell 状态机授予的写者代次，用于拒绝旧写者 |
| `db_seq` | 同一数据库代次内单调增加的已接受提交序号 |
| cell | 一个共享 Raft 组及其状态机，初始三个 voter，管理多库 |
| Raft commit | 一条日志得到共识提交；其命令还可能被状态机拒绝 |
| accepted commit | 状态机校验身份、epoch、前序版本、幂等等后接受的数据库事务 |
| ACK | 服务向客户端明确返回该写事务成功 |
| manifest | 指向某一数据库恢复链的不可变清单及校验信息 |
| RPO | 在约定故障场景下允许损失的已确认数据范围 |
| RTO | 从故障发生到连续稳定恢复窗口起点的时长；后续连续 30 秒验证通过才确认该起点，第一次成功另记 |

各实现文件可采用不同语言命名，但不得混淆 Raft 日志索引与 `db_seq`，也不得把 worker 的本地文件进度当作全局提交点。

## 5. 安全性合同

### 5.1 提交成功

对返回成功的写事务，数据变更和必要的恢复元数据必须已在 cell 多数副本持久化，且状态机已接受命令。回复成功不能只依赖本地 SQLite 文件、内存复制、S3 上传队列或 etcd lease。

若要求稳定重试，则请求标识和结果摘要也必须与事务结果处于同一权威提交记录中。第三方 SDK 未提供稳定标识时，平台不承诺跨请求 exactly-once。

### 5.2 故障范围

| 故障 | 目标行为 |
| --- | --- |
| 网关 / 控制服务进程退出 | 由其他实例接替；已有请求可能失败或结果未知 |
| worker 退出 / 计算节点丢失 | 新 owner 从权威恢复链重建；已 ACK 提交保留 |
| 单个 voter / 单可用区丢失 | 剩余两个有效副本形成多数派，恢复服务后保留全部 ACK |
| cell 暂时失去多数派 | 暂停该 cell 的新强一致读写，等待多数派恢复 |
| S3 不可用 | 可恢复的热库在可靠日志容量内继续；冷恢复、归档、GC 等暂停 |
| 多数副本永久损毁 | 不宣称自动零丢失恢复；进入受控灾难恢复 |
| 误删 / 错误 SQL | 复制会传播逻辑错误；使用独立历史恢复流程 |

单可用区零丢失目标依赖正确的副本放置、存储设备持久化、fsync 契约、成员变更和恢复实现。三副本不代表任意同时丢失两个副本仍保证全部已 ACK 事务。

### 5.3 分区选择

系统选择一致性优先：只有可取得 cell 权威多数派的一侧可接受新的强一致操作。少数派不能靠超时、自认为 leader、旧 etcd 路由或旧租约继续成功写入。超时不能被解释为“对端已经死亡”。

已在分区前完成合法读屏障的有限读事务，可以按既定快照结束；不以此允许隔离侧开始无限的新强一致读。

## 6. 性能与资源目标

初始内部验收目标已在 [性能与恢复目标](../engineering/performance-slo.md) 中定义，**均尚未实测，不是对外 SLA 或现成吞吐承诺**。在其指定的三 AZ、请求形态、数据库大小、网络/磁盘和负载条件下：

| 指标 | 初始 p95 / p99 目标 |
| --- | --- |
| 热库点强读，SDK 端到端 | 20 / 50 ms |
| 热库小写事务，SDK 端到端 | 50 / 100 ms |
| writer 故障 R0 经济档，完整恢复 ≤1 GiB | 20 / 30 s；有效恢复速率 ≥100 MiB/s，tail ≤64 MiB |
| writer 故障 R1 完整文件预置缓存档 | 8 / 15 s |
| writer 故障 R2 跨 AZ 热备执行档 | 5 / 10 s |
| 单 AZ 故障，受影响库采用 R2 | 10 / 20 s |

R0 对应当前完整恢复设计；R1/R2 是 **G4 拟实现并验证的选项**，需要额外数据副本、追赶和接管容量，不属于已存在能力。完整恢复不能对任意大小库承诺几秒 RTO，热备也不能在无 quorum 时越过 fencing。初始内部可用性目标为 30 天滚动窗口 99.9%，冷唤醒超时、UNKNOWN 和计划维护中断计入失败。

首批容量验收目标为每 cell 10,000 个 Cold 库及 100 个活跃库；具体数据量和负载取性能文档的基准，不能扩展为任意数据库体积的容量上限。第一轮必须测量：

- 每个活跃库和空闲库的固定内存、文件句柄和元数据开销。
- 热读、跨 AZ 提交、冷恢复和集中唤醒的 p50 / p95 / p99。
- 单热点库与大事务对同 cell 其他数据库的影响。
- S3 中断时日志增长、磁盘剩余安全时间和恢复速度。
- 单 voter 故障、worker 故障与控制面故障的实际 RTO。
- 数据库体积、事务变更大小、事务持续时间、并发连接的可执行限额。

初始实验矩阵与测量口径见 [成本与容量](../engineering/capacity-cost.md)。

## 7. 不变量

1. 任何 ACK 都有权威且可恢复的 accepted commit。
2. 同一数据库代次同时最多一个 epoch 可以继续产生 accepted commit。
3. 旧 worker 的本地成功和缓存内容不能越过 cell 仲裁。
4. 新 owner 必须恢复到至少权威 head 后才接收新操作。
5. 归档、日志截断和删除均须有覆盖证明，不能用时间或文件存在推断。
6. 显式失败和结果未知分开返回；未知结果不能被自动当作未提交重试。
7. 任何降级都不能改变已经公开的提交合同。
